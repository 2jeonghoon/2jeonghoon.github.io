실시간 게임 네트워킹은 모든 클라이언트에 완전히 같은 화면을 즉시 보여주는 일이 아니다. 물리적 지연이 존재하는 상황에서 플레이 감각을 유지하면서도 서버의 판정과 상태를 수렴시키는 일이다. 장르와 이벤트의 중요도에 따라 다른 동기화 전략을 선택해야 한다.

## 지연을 다루는 방법

왕복 시간보다 빠른 반응을 보여주려면 클라이언트가 입력 결과를 먼저 예측할 수 있다. 서버는 입력을 검증해 권위 있는 상태를 보내고, 클라이언트는 차이가 작으면 부드럽게 보간하고 크면 빠르게 보정한다. 원격 플레이어의 이동은 최근 속도와 방향으로 잠시 추정하는 추측 항법을 사용할 수 있다.

예측은 지연을 없애는 것이 아니라 사용자가 느끼는 시점을 바꾸는 기법이다. 충돌, 보상, 공격 판정처럼 되돌리기 어려운 결과는 서버 확인 전 표현 범위를 신중하게 정해야 한다. 반대로 발사 효과나 UI 반응은 즉시 보여준 뒤 실패 시 취소할 수 있다.

## 대규모 월드와 동기화

모든 객체의 상태를 모든 사용자에게 보낼 필요는 없다. 공간을 셀이나 영역으로 나누고 플레이어가 관심을 가질 수 있는 객체만 전송하면 CPU와 대역폭을 줄일 수 있다. 경계 이동, 빠른 순간 이동, 시야 밖 상호작용처럼 관심 집합이 급변하는 상황을 따로 시험해야 한다.

RTS처럼 결정론적 시뮬레이션이 가능한 장르는 명령만 공유하는 락스텝을 사용할 수 있다. 대역폭은 작지만 모든 참여자가 같은 순서와 결과를 만들어야 하며, 느린 참여자가 전체 진행을 지연시킬 수 있다. 부동소수점, 난수 시드, 실행 순서가 결정론을 깨뜨리는 대표 요소다.

## 프로토콜과 서비스 흐름

최신성이 중요한 이동 정보에는 유실을 허용하는 전송을, 반드시 처리되어야 하는 로그인·채팅·아이템 변경에는 신뢰성 있는 전송을 사용할 수 있다. 패킷을 너무 자주 보내면 헤더와 시스템 호출 비용이 늘지만, 지나치게 모으면 대기 시간이 늘어난다.

게임 플레이 밖에서도 로그인, 캐릭터 선택, 매치메이킹, 아이템 사용이 연속된 상태 기계를 이룬다. 각 단계에 인증, 중복 요청 방지, 타임아웃, 취소, 재접속 규칙이 필요하다. 서버는 클라이언트가 보내는 좌표나 결과를 그대로 신뢰하지 않고 가능한 입력인지 검증해야 한다.

## 원문별 상세 정리

### 5.1 UML

UML은 구조와 상호작용을 공통 표기로 설명하는 도구다. 클래스 다이어그램은 타입과 관계를, 시퀀스 다이어그램은 시간 순서의 메시지를, 상태 다이어그램은 상태와 전이 조건을 표현한다. 게임 서버에서는 로그인, 매치 참가, 전투 결과 저장처럼 여러 컴포넌트가 얽힌 흐름을 코드 전에 검토하는 데 특히 유용하다.

다이어그램을 모든 구현 세부로 채우면 금방 낡는다. 누가 상태를 소유하는지, 동기·비동기 경계가 어디인지, 실패와 타임아웃 뒤 어떤 상태가 되는지를 중심으로 그린다. 정상 경로뿐 아니라 중복 요청, 서버 응답 유실, 연결 종료를 별도 흐름으로 표시한다. 그림은 설계의 근거와 최신 상태를 연결할 때 가치가 있다.

### 5.2 게임 플레이 네트워킹

게임 플레이 네트워킹은 입력과 세계 상태를 제한된 대역폭 안에서 충분히 빠르게 공유하는 일이다. 서버 권한 방식에서는 클라이언트가 이동 결과보다 입력이나 의도를 보내고 서버가 시뮬레이션한 결과를 전파한다. 스냅숏, 상태 변화 이벤트, 입력 스트림 중 무엇을 보낼지는 게임 규칙과 복구 요구에 따라 달라진다.

전송 빈도를 높이면 최신성은 좋아지지만 트래픽과 처리 비용이 커진다. 모든 객체의 전체 상태 대신 변경분, 양자화된 값, 관심 영역 안의 객체만 보낸다. 패킷마다 서버 틱이나 시퀀스 번호를 넣어 시간축을 맞추고 오래된 상태를 구별한다. 결정적 사건과 보간 가능한 시각 상태의 신뢰성 요구를 분리한다.

### 5.3 레이턴시 마스킹

물리적 왕복 지연을 없앨 수 없을 때 클라이언트 예측은 입력을 즉시 적용해 조작 반응을 보여준다. 나중에 서버 상태가 도착하면 저장해 둔 미확인 입력을 기준으로 재적용하고 오차를 보정한다. 보정을 한 프레임에 순간 이동처럼 보여 줄지 여러 프레임에 부드럽게 나눌지는 정확성과 시각적 안정성의 절충이다.

다른 플레이어는 미래 입력을 알 수 없으므로 과거 스냅숏 사이를 보간해 매끄럽게 표시한다. 이는 약간의 의도적 표시 지연을 추가한다. 탄환 판정에서는 서버가 공격 시점의 과거 위치를 복원하는 지연 보상을 쓸 수 있지만, 높은 지연 사용자에게 지나친 이점을 주지 않도록 되감기 한계를 둔다. 마스킹은 지연을 숨기는 기술이지 서버 검증을 생략하는 근거가 아니다.

### 5.4 넓은 월드와 많은 캐릭터 처리

모든 플레이어에게 월드의 모든 객체를 전송하면 객체 수와 접속자 수의 곱으로 비용이 커진다. 관심 영역 관리는 플레이어가 실제로 볼 수 있거나 상호작용 가능한 주변 객체만 구독하게 한다. 격자, 쿼드트리, 공간 해시 같은 구조로 근처 후보를 찾고, 시야·팀·게임 규칙으로 다시 걸러낸다.

경계에서 객체가 조금 움직일 때마다 생성과 삭제가 반복되지 않도록 진입·이탈 범위에 여유를 두거나 최소 유지 시간을 사용할 수 있다. 중요도와 거리, 변화량에 따라 갱신 빈도를 낮추고 멀리 있는 객체는 더 거친 표현을 보낸다. 관심 목록 변경 자체도 비용이므로 한 틱에 처리할 양과 폭주 시 정책을 정한다.

### 5.5 RTS 게임의 네트워크 동기화

RTS처럼 객체가 매우 많으면 모든 유닛 상태를 매 틱 전송하기 어렵다. 결정적 락스텝은 각 참가자의 명령만 공유하고 모두가 같은 초기 상태와 규칙으로 같은 결과를 계산한다. 네트워크 사용량은 줄지만 한 참가자의 명령이 늦으면 진행이 기다릴 수 있고 작은 비결정성도 시간이 지나며 큰 불일치가 된다.

부동소수점 차이, 컨테이너 순회 순서, 난수 호출 횟수, 플랫폼별 라이브러리 동작을 통제해야 한다. 틱별 상태 해시로 동기 불일치를 발견하고, 재접속이나 불일치 복구를 위한 스냅숏을 준비한다. 현대 구조에서는 서버가 명령을 검증하고 일정 입력 지연을 두어 명령을 묶어 처리하는 혼합 모델도 고려할 수 있다.

### 5.6 실제 레이턴시 줄이기

지연을 실제로 줄이려면 먼저 DNS, 연결 수립, 클라이언트 프레임, 업링크, 서버 큐, 게임 틱, 다운링크, 렌더링으로 전체 경로를 나눠 측정한다. 서버를 사용자와 가까운 지역에 배치하고 좋은 피어링이나 중계망을 선택하면 전파·라우팅 지연을 줄일 수 있다. 연결을 재사용하고 필요한 주소를 미리 해석하는 것도 초기 요청에 도움 된다.

서버 내부에서는 큐 대기와 락 경쟁, 긴 틱이 네트워크보다 큰 지연을 만들 수 있다. 작고 자주 보내는 패킷은 최신성을 높이지만 헤더와 시스템 호출 비용이 늘며 혼잡을 악화할 수 있다. 메시지를 무조건 모으거나 즉시 보내는 대신 우선순위와 지연 예산을 기준으로 배치한다. 변경 전후에는 실제 사용자 지역에서 상위 백분위까지 측정한다.

### 5.7 게임 플레이 이외의 네트워킹

로그인에서는 자격 증명을 안전한 채널로 보내고 인증 성공 뒤 짧은 수명의 세션 토큰을 사용한다. 캐릭터 선택은 소유권과 접속 상태를 검증하고, 매치메이킹은 실력·지역·파티·대기 시간 조건을 조정해 세션을 만든다. 아이템 구매와 보상은 중복 요청에 안전하고 감사 가능한 기록을 남겨야 한다.

이 기능들은 실시간 위치 갱신보다 지연 허용치는 크지만 정확성과 내구성이 더 중요하다. 요청 ID, 상태 전이, 트랜잭션, 타임아웃 후 조회 API를 활용한다. 예를 들어 결제 응답이 유실됐을 때 다시 결제하기보다 거래 ID로 결과를 조회해야 한다. 채팅과 친구 목록에도 속도 제한, 차단, 신고, 개인정보 정책이 필요하다.

### 5.8 해킹과 보안

클라이언트는 공격자가 수정할 수 있다고 가정한다. 이동 좌표나 피해량을 결과로 믿지 말고 속도, 쿨다운, 자원, 현재 상태를 서버가 검증한다. 패킷 암호화는 도청과 변조를 줄이지만 정상 클라이언트가 가진 키와 코드가 분석될 가능성을 없애지 못하며, 서버 측 권한 검사를 대체하지 않는다.

메시지 길이와 배열 수, 문자열 인코딩, 압축 해제 크기에 상한을 두고 파서는 잘못된 입력에서도 안전하게 실패해야 한다. 로그인과 채팅, 비용이 큰 요청에는 사용자·IP·세션 기준 속도 제한을 적용한다. 비밀 키는 코드 저장소와 로그에서 분리하고 정기 교체한다. 치트 탐지는 단일 임계값보다 불가능한 상태 전이, 통계적 이상, 반복 패턴을 함께 보되 오탐에 대한 검토와 제재 절차를 둔다.

### 스냅숏과 보간

서버는 상태에 틱 번호를 붙여 보내고 클라이언트는 표시 시각 앞뒤의 스냅숏을 찾는다.

```cpp
struct PlayerSnapshot {
    std::uint32_t serverTick;
    Vec3 position;
    Vec3 velocity;
};

Vec3 Interpolate(const PlayerSnapshot& a,
                 const PlayerSnapshot& b,
                 float alpha) {
    return a.position * (1.0f - alpha) + b.position * alpha;
}
```

```text
서버 시간:      A -------- B -------- C
클라이언트 표시:      ^
                 A와 B 사이를 보간
```

작은 지터를 흡수하려면 클라이언트가 현재보다 약간 과거를 표시한다. 버퍼를 크게 잡으면 움직임은 안정되지만 표시 지연이 늘어난다.

### 클라이언트 예측과 재조정

```text

2. 서버가 입력 39까지 반영한 권위 상태를 보낸다.
3. 클라이언트는 서버 위치로 돌아간다.
4. 아직 확인되지 않은 입력 40, 41을 순서대로 다시 적용한다.
5. 화면에는 차이를 여러 프레임에 걸쳐 부드럽게 보정한다.
```

입력마다 증가하는 번호를 넣어야 어떤 입력까지 서버가 처리했는지 알 수 있다. 서버가 허용하지 않은 이동은 재적용하지 않는다.

### 결정적 락스텝

```text
플레이어 명령 수집 ──> 틱 N 명령 묶음 방송 ──> 모든 참가자가 틱 N 실행
                                   │
                                   └─ 상태 해시 비교로 불일치 감지
```

전송량을 줄일 수 있지만 난수 시드, 부동소수점, 실행 순서가 모두 결정적이어야 한다. 늦은 참가자를 무한히 기다리지 않도록 입력 마감과 이탈 정책도 필요하다.

## 공부할 내용

1. 100~200ms 지연과 패킷 유실을 인위적으로 주고 이동 예측·보정을 관찰한다.
2. 공간 그리드 기반 관심 영역을 구현하고 사용자 수에 따른 전송량을 측정한다.
3. 로그인부터 배틀 입장까지 시퀀스 다이어그램과 실패 분기를 그린다.
4. 이동, 채팅, 공격, 구매 메시지의 신뢰성·순서·최신성 요구를 표로 정리한다.
