게임 서버는 여러 사용자의 요청을 동시에 처리한다. 하지만 스레드를 늘리는 것만으로 처리량이 자동으로 증가하지는 않는다. 공유 상태, lock contention, context switch, 순차(serial) 실행 구간이 함께 늘어날 수 있기 때문이다. 이번 단원의 목표는 **병렬화할 작업과 보호할 상태(state)를 구분하는 기준**을 세우는 것이다.

## 핵심 개념

프로세스는 독립된 주소 공간과 운영체제 자원을 가진 실행 단위다. 한 프로세스 안의 스레드들은 코드와 힙 같은 자원을 공유하지만 각자의 스택과 실행 흐름을 가진다. 공유가 빠른 대신 한 스레드의 잘못된 메모리 접근이 프로세스 전체에 영향을 줄 수 있다.

멀티스레딩은 CPU 작업을 병렬화하거나 I/O를 기다리는 동안 다른 작업을 진행할 때 유용하다. 반면 코어 수보다 지나치게 많은 실행 가능 스레드는 context switch overhead를 키운다. 프로그램 속도는 병렬 구간뿐 아니라 순차 구간의 비율에도 제한되므로, 스레드 수를 정하기 전에 병목을 측정해야 한다.

## 공유 상태와 동기화

`value++`처럼 단순해 보이는 코드도 읽기, 계산, 쓰기로 나뉠 수 있다. 두 스레드가 같은 값을 동시에 변경하면 race condition이 생긴다. 컨테이너의 크기 변경과 메모리 재할당은 더 복잡한 corruption(데이터 오염)을 만들 수 있다.

- 뮤텍스는 한 번에 하나의 실행 흐름만 임계 영역에 들어가게 한다.
- RAII 방식의 잠금 객체를 사용하면 예외나 조기 반환에서도 잠금 해제를 보장하기 쉽다.
- 세마포어는 동시에 통과할 수 있는 작업 수를 제한하는 데 적합하다.
- 이벤트나 조건 변수는 상태가 바뀔 때까지 스레드를 재우고 깨우는 데 사용한다.
- 원자 연산은 작은 상태 변경에 유용하지만 여러 값이 함께 만족해야 하는 불변식(invariant)까지 자동으로 보호하지는 않는다.

교착 상태(deadlock)는 여러 실행 흐름이 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상황이다. 모든 잠금에 전역 순서를 부여하고, 잠금 중 느린 I/O를 피하며, 임계 영역을 작게 유지하는 습관이 중요하다. 단, 임계 영역을 무작정 쪼개면 하나의 논리적 변경이 중간 상태로 노출될 수 있다.

## 게임 서버의 실행 모델

싱글스레드 서버는 상태 변경 순서가 명확해 디버깅하기 쉽지만, 한 작업이 오래 걸리면 전체 진행을 막는다. 멀티스레드 서버는 네트워크 I/O와 게임 로직을 분리하고 여러 코어를 활용할 수 있지만 소유권 규칙이 필요하다. 실전에서는 고정된 워커 스레드가 작업 큐에서 태스크를 가져가는 스레드 풀이 흔하다. 클라이언트마다 스레드를 만드는 방식보다 생성 비용과 최대 동시성을 통제하기 쉽기 때문이다.

## 원문별 상세 정리

### 1.1 프로그램과 프로세스

프로그램은 디스크에 저장된 명령과 데이터의 묶음이고, 프로세스는 운영체제가 그 프로그램을 실행하기 위해 만든 자원 컨테이너다. 프로세스마다 가상 주소 공간, 핸들 테이블, 보안 정보 등이 분리되며 코드·전역 데이터·힙·스택 같은 메모리 영역을 사용한다. 같은 실행 파일을 두 번 실행해도 서로 다른 프로세스이므로 한쪽의 일반 메모리 변경이 다른 쪽에 곧바로 보이지 않는다.

멀티프로세스 구조는 장애 격리와 보안 경계가 뚜렷한 대신 프로세스 간 통신과 데이터 복사가 필요하다. 게임 서버를 인증·월드·채팅 프로세스로 나누면 한 기능의 충돌이 전체 서비스로 번지는 범위를 줄일 수 있지만, 상태 전달과 장애 복구 프로토콜까지 설계해야 한다. 프로세스를 나누는 결정은 단순한 성능 최적화가 아니라 소유권과 실패 영역을 정하는 일이다.

### 1.2 스레드

스레드는 프로세스 안에서 실제 명령을 실행하는 흐름이다. 같은 프로세스의 스레드는 코드와 힙을 공유하지만 각자 레지스터 상태, 명령 포인터, 호출 스택을 가진다. 공유 메모리로 빠르게 협력할 수 있는 대신 한 스레드가 잘못된 포인터를 쓰거나 공유 객체의 규칙을 깨면 프로세스 전체가 영향을 받는다.

스레드는 생성 비용과 스택 메모리를 소비하며, 실행 가능한 스레드가 CPU 코어보다 많으면 운영체제가 번갈아 실행한다. 따라서 “연결 하나당 스레드 하나”처럼 개수가 사용자 수에 비례하는 모델은 규모가 커질수록 부담이 된다. 실무에서는 소수의 I/O 스레드와 고정 워커, 작업 큐를 조합하고 어느 스레드가 어떤 상태를 변경할 수 있는지 명시한다.

스레드의 상태 변화는 다음처럼 생각할 수 있다. API와 운영체제에 따라 정확한 상태 이름은 달라도, 실행할 준비가 된 상태와 어떤 조건을 기다리는 상태가 구분된다는 점은 같다.

```text
생성 ── 시작 ──> 실행 가능(Runnable) ── 작업 완료 ──> 종료
                    │       ▲
                    │       │
                 대기 진입   깨우기
                    ▼       │
                  대기(Blocked)
```

새 스레드를 만든 뒤 메인 스레드가 `join`을 호출하면, 메인 스레드는 새 스레드가 끝날 때까지 기다린다.

```text
메인 스레드:  생성 ── 다른 작업 ── join에서 대기 ── 종료
새 스레드:           └── 작업 실행 ── 종료 ────────┘
```

운영체제 또는 언어별 생성 코드는 다음과 같다. 아래 코드는 차이를 보여 주기 위한 최소 예제다.

**Windows API**

```cpp
#include <Windows.h>

DWORD WINAPI ThreadProc(LPVOID parameter) {
    const int value = *static_cast<int*>(parameter);
    // value를 사용하는 작업
    return 0;
}

int main() {
    int value = 123;
    DWORD threadId = 0;
    HANDLE thread = CreateThread(
        nullptr, 0, ThreadProc, &value, 0, &threadId);

    if (thread != nullptr) {
        WaitForSingleObject(thread, INFINITE);
        CloseHandle(thread);
    }
}
```

`CreateThread`는 운영체제 핸들을 반환한다. 종료를 기다린 뒤 `CloseHandle`로 핸들 자원을 정리해야 한다. `&value`가 가리키는 객체는 새 스레드가 읽을 때까지 살아 있어야 한다.

**Linux·Unix POSIX Threads**

```cpp
#include <pthread.h>

void* ThreadProc(void* parameter) {
    const int value = *static_cast<int*>(parameter);
    // value를 사용하는 작업
    return nullptr;
}

int main() {
    int value = 123;
    pthread_t thread{};

    if (pthread_create(&thread, nullptr, ThreadProc, &value) == 0) {
        pthread_join(thread, nullptr);
    }
}
```

`pthread_create`의 시작 함수는 `void*`를 받고 `void*`를 반환한다. 종료된 joinable 스레드를 `pthread_join`으로 회수하지 않으면 관련 자원이 남을 수 있다.

**Modern C++**

```cpp
#include <thread>

void ThreadProc(int value) {
    // value를 사용하는 작업
}

int main() {
    std::thread worker(ThreadProc, 123);
    worker.join();
}
```

이식성이 필요하면 일반적으로 `std::thread`가 더 적합하다. `std::thread` 객체가 joinable인 채 파괴되면 `std::terminate`가 호출되므로, 모든 경로에서 `join` 또는 의도적인 `detach`가 이루어져야 한다. 프로세스가 정상적으로 종료되면 그 프로세스의 다른 스레드도 함께 끝난다. 이를 곧바로 “좀비 프로세스”라고 부르는 것은 정확하지 않다.

### 1.3 멀티스레드 프로그래밍은 언제 해야 할까?

멀티스레딩이 유용한 첫 번째 경우는 긴 작업이 진행되는 동안 짧고 중요한 작업의 응답성을 유지해야 할 때다. 예를 들어 저장이나 경로 탐색이 끝날 때까지 네트워크 수신 루프까지 멈추면 모든 사용자가 지연을 겪는다. 두 번째는 서로 독립적인 CPU 작업을 여러 코어에서 병렬로 처리해 총 실행 시간을 줄일 수 있을 때다.

단, 작업을 스레드로 옮겼다는 사실만으로 빨라지지는 않는다. 작업 분할, 큐잉, 동기화, 캐시 미스, 결과 합치기 비용이 추가되고 순차 구간은 그대로 남는다. 먼저 프로파일링으로 CPU 대기와 I/O 대기를 구분하고, 입력과 출력이 명확하며 공유 상태가 적은 작업부터 병렬화해야 한다. 작은 요청마다 새 스레드를 만들기보다 충분한 크기의 작업 단위와 재사용 가능한 스레드 풀을 선택한다.

### 1.4 스레드 정체

운영체제는 실행 중인 스레드의 레지스터와 명령 위치를 저장한 뒤 다른 스레드의 상태를 복원하는 컨텍스트 스위치를 수행한다. 이 전환 동안 애플리케이션 로직은 진행되지 않으며 캐시와 TLB의 지역성도 약해질 수 있다. 짧은 타임 슬라이스 안에서 많은 스레드가 경쟁하거나 잠금에서 자주 자고 깨면 실제 계산보다 전환 비용이 커진다.

소스 코드 한 줄은 여러 기계 명령으로 나뉠 수 있고 전환은 그 사이에도 일어난다. 따라서 “한 줄이라 안전하다”는 판단은 성립하지 않는다. CPU 사용률이 높은데 처리량이 늘지 않는다면 실행 스레드 수, 컨텍스트 스위치 횟수, 잠금 대기 시간을 함께 관찰한다. 해결책은 무조건 스레드를 줄이는 것이 아니라 긴 임계 영역, 과도하게 잘게 쪼갠 작업, 불필요한 깨우기를 찾아 실행 모델을 정리하는 것이다.

### 1.5 스레드를 다룰 때 주의 사항

경쟁 상태는 실행 순서에 따라 결과가 달라지는 상황이고, 데이터 레이스는 동기화되지 않은 동일 메모리에 여러 스레드가 접근하며 적어도 하나가 쓰기를 수행하는 문제다. `num++`은 읽기·증가·쓰기 단계로 나뉘므로 두 스레드가 같은 이전 값을 읽으면 증가 한 번이 사라질 수 있다. 벡터에 동시에 원소를 추가하면 크기뿐 아니라 재할당과 내부 포인터까지 손상될 수 있다.

동기화의 목적은 단순히 충돌을 막는 것이 아니라 프로그램의 불변식을 유지하는 것이다. “재화가 0 이상”, “목록 크기와 별도 카운터가 일치”처럼 함께 지켜야 하는 조건을 먼저 적고, 그 조건을 변경하거나 관찰하는 모든 경로에 같은 규칙을 적용한다. 실행을 여러 번 해도 재현되지 않을 수 있으므로 스트레스 테스트, 스레드 검사 도구, 상세 로그를 함께 사용해야 한다.

`value++`에서 갱신이 사라지는 과정을 단순화하면 다음과 같다.

```text
초깃값 value = 10

스레드 A: value 읽기(10) ── 11 계산 ────────── 11 쓰기
스레드 B:          value 읽기(10) ── 11 계산 ── 11 쓰기

기대 결과: 12
실제 가능 결과: 11
```

두 스레드가 각각 한 번 증가시켰지만 같은 이전 값을 기준으로 썼기 때문에 한 번의 증가가 사라졌다.

### 1.6 임계 영역과 뮤텍스

임계 영역은 공유 불변식을 보호하기 위해 한 번에 제한된 실행 흐름만 들어가야 하는 코드 구간이다. 뮤텍스를 잠근 뒤 작업하고 반드시 해제해야 하며, 예외나 조기 반환이 있어도 해제를 놓치지 않도록 C++의 `lock_guard`나 C#의 `lock`처럼 범위 기반 수명 관리를 사용한다. 재귀 뮤텍스는 같은 스레드의 재진입을 허용하지만 잘못된 호출 구조를 숨기고 잠금 횟수 관리를 복잡하게 할 수 있어 기본 선택으로 삼지 않는다.

잠금을 세분화하면 병렬성이 늘 수 있지만 여러 잠금을 획득하는 경로와 일관성 범위도 복잡해진다. 반대로 하나의 거대한 잠금은 안전하기 쉬운 대신 모든 작업을 직렬화한다. 보호 대상 데이터, 잠금 소유자, 허용되는 획득 순서를 문서화하고 잠금 안에서 파일·DB·네트워크 같은 느린 작업을 피한다. 실제 성능은 코어 수만 보지 말고 잠금 경쟁과 메모리 대역폭까지 측정해야 한다.

직접 `lock()`과 `unlock()`을 짝짓는 대신 범위를 벗어날 때 자동으로 해제되는 RAII 객체를 사용한다.

```cpp
#include <mutex>
#include <vector>

std::mutex playersMutex;
std::vector<int> playerIds;

void AddPlayer(int playerId) {
    std::lock_guard<std::mutex> guard(playersMutex);
    playerIds.push_back(playerId);
} // 예외나 조기 반환이 발생해도 guard가 잠금을 해제한다.
```

잠금은 `playerIds`라는 데이터뿐 아니라 “벡터 변경 중 다른 스레드가 내부 상태를 관찰하지 않는다”라는 규칙을 보호한다. 같은 벡터를 읽는 코드도 동일한 동기화 정책을 따라야 한다.

### 1.7 교착 상태

교착 상태는 둘 이상의 실행 흐름이 상대가 가진 자원을 기다려 누구도 진행하지 못하는 상태다. 대표적으로 스레드 A가 플레이어 잠금을 가진 채 길드 잠금을 기다리고, 스레드 B가 길드 잠금을 가진 채 플레이어 잠금을 기다릴 때 발생한다. CPU 사용률이 낮은데 요청이 멈추고 스레드들이 잠금 함수에서 대기한다면 교착을 의심할 수 있다.

진단할 때는 멈춘 프로세스의 모든 스레드 호출 스택과 각 잠금의 소유·대기 관계를 수집해 대기 사이클을 찾는다. 타임아웃은 영구 대기를 감지하는 장치일 뿐, 이미 절반만 반영된 상태를 자동 복구하지 않는다. 가장 강한 예방책은 전역 잠금 순서를 정하고 중첩 잠금을 줄이며, 여러 자원이 필요하면 안전하게 한꺼번에 획득하는 표준 도구를 사용하는 것이다.

```cpp
std::mutex accountMutex;
std::mutex inventoryMutex;

void SavePlayer() {
    // 두 뮤텍스를 교착 없이 획득한 뒤 각 lock_guard에 소유권을 넘긴다.
    std::lock(accountMutex, inventoryMutex);
    std::lock_guard<std::mutex> accountLock(accountMutex, std::adopt_lock);
    std::lock_guard<std::mutex> inventoryLock(inventoryMutex, std::adopt_lock);

    // 계정과 인벤토리를 하나의 일관된 상태로 저장한다.
}
```

C++17 이상이라면 `std::scoped_lock lock(accountMutex, inventoryMutex);`로 더 간결하게 표현할 수 있다. 중요한 점은 다른 코드 경로에서도 두 잠금의 획득 규칙을 일관되게 유지하는 것이다.

### 1.8 잠금 순서의 규칙

잠금마다 계층이나 고유 순서를 부여하고 여러 잠금이 필요할 때 항상 낮은 순서에서 높은 순서로 획득하면 순환 대기를 구조적으로 막을 수 있다. 예를 들어 계정 → 캐릭터 → 인벤토리 순서를 정했다면 어느 호출 경로에서도 역순으로 잠그지 않는다. 코드 리뷰와 디버그 빌드에서 현재 보유 잠금의 계층을 검사하면 규칙 위반을 일찍 발견할 수 있다.

재귀 호출은 같은 잠금을 다시 얻을 수 있어 순서 검사를 어렵게 만든다. 재귀 뮤텍스로 증상을 없애기보다 잠금이 필요한 공개 함수와 이미 잠금이 잡혔다고 가정하는 내부 함수를 분리하는 편이 의도가 분명하다. 외부 콜백이나 가상 함수를 잠금 안에서 호출하면 내부에서 어떤 잠금을 얻을지 알 수 없으므로, 필요한 값을 복사한 뒤 잠금을 풀고 호출하는 패턴도 고려한다.

### 1.9 병렬성과 시리얼 병목

병렬화 가능한 계산이 많아도 입력 준비, 작업 분배, 공유 결과 병합이 순차라면 전체 속도 향상은 제한된다. 암달의 법칙은 순차 비율이 남아 있는 한 코어를 무한히 늘려도 최대 가속도에 상한이 있음을 보여준다. 따라서 평균 CPU 사용률이 낮다고 곧바로 스레드를 추가하지 말고 특정 잠금, 단일 큐, 메모리 할당기, 한 코어에 몰린 로직을 확인해야 한다.

프로파일링에서는 벽시계 시간과 CPU 시간을 구분한다. `Sleep`, 디스크, 네트워크, 잠금 대기에 쓴 시간은 사용자가 느끼는 지연에는 포함되지만 CPU가 계산한 시간과 다르다. 타임라인에서 각 스레드가 실행·대기·준비 상태였던 구간을 보고, 처리량과 상위 백분위 지연을 함께 측정한다. 병목을 옮겼을 뿐 전체 성능이 개선되지 않은 경우도 있으므로 변경 전후 동일 부하로 비교한다.

### 1.10 싱글스레드 게임 서버

싱글스레드 서버는 네트워크 이벤트와 게임 명령을 한 실행 흐름에서 순서대로 처리한다. 동시에 두 로직이 같은 상태를 고치지 않으므로 잠금이 적고 재현 가능한 순서를 만들기 쉽다. 턴제 게임, 작은 룸, 하나의 틱에 계산이 충분히 끝나는 인스턴스에서는 단순성과 안정성이 큰 장점이다.

그러나 하나의 느린 명령이 뒤의 모든 명령을 막고 단일 코어 처리량을 넘을 수 없다. 해결책은 곧바로 내부 상태를 멀티스레드화하는 것만이 아니다. 방이나 월드를 여러 단일 스레드 인스턴스로 나눠 코어에 배치하고, DB·로그 같은 외부 작업을 비동기로 보내는 구조가 상태 추론의 장점을 유지하기 쉽다. 틱 예산을 넘는 작업은 분할하거나 다음 틱으로 넘기는 규칙도 필요하다.

### 1.11 멀티스레드 게임 서버

멀티스레드 서버는 수신, 패킷 해석, 게임 로직, 저장 같은 작업을 병렬로 처리할 수 있다. 하지만 아무 워커나 모든 객체를 수정하게 하면 잠금 범위가 넓어지고 재현이 어려워진다. 연결이나 룸을 특정 실행자에게 귀속시키는 소유권 모델, 읽기 전용 스냅숏, 메시지 전달 방식으로 공유 쓰기를 제한하는 것이 중요하다.

작업 큐에 넣은 시점과 실행 시점 사이에는 상태가 바뀔 수 있다. 따라서 원본 포인터의 수명, 연결 종료 후 도착한 작업, 같은 플레이어 명령의 순서, 실패한 작업의 재처리를 정의해야 한다. 병렬성은 “스레드 안전한 컨테이너를 사용했다”만으로 완성되지 않으며 게임 규칙 차원의 순서와 원자성이 보장돼야 한다.

```text
I/O 스레드 ── 패킷 해석 ──> 룸 작업 큐 ──> 룸 소유 스레드
                                              │
                                              └─ 게임 상태 변경
```

이 구조에서는 I/O 스레드가 룸 상태를 직접 수정하지 않는다. 룸 상태를 한 스레드가 소유하고 다른 스레드는 명령을 큐에 넣으므로, 공유 쓰기와 잠금 범위를 줄일 수 있다.

### 1.12 스레드 풀링

스레드 풀은 미리 만든 워커들이 큐에서 작업을 가져가므로 요청마다 생성·종료하는 비용을 줄이고 동시 실행량을 제한한다. CPU 중심 작업은 보통 실제 사용 가능한 코어 수 근처에서 출발하고, I/O 대기가 긴 작업은 더 많은 워커가 유리할 수 있다. 하나의 공식으로 고정하지 말고 대기 비율, 작업 길이, 목표 지연을 부하 시험으로 확인한다.

긴 작업과 매우 짧은 작업을 같은 큐에 넣으면 짧은 작업이 뒤에서 기다리는 헤드 오브 라인 블로킹이 생긴다. 우선순위나 별도 풀을 사용할 수 있지만 풀이 너무 많으면 다시 스레드 수와 자원 경쟁이 늘어난다. 큐 길이에 상한을 두고 과부하 시 거절·지연·품질 저하 중 어떤 정책을 적용할지도 정해야 한다. 무제한 큐는 장애를 해결하지 않고 메모리 고갈까지 늦출 뿐이다.

### 1.13 이벤트

이벤트는 특정 조건이 충족될 때까지 스레드를 재웠다가 신호가 오면 깨우는 동기화 도구다. 자동 리셋 이벤트는 보통 대기자 하나를 통과시킨 뒤 비신호 상태로 돌아가고, 수동 리셋 이벤트는 명시적으로 리셋할 때까지 여러 대기자가 통과할 수 있다. “새 작업 하나 도착”과 “서버 종료 시작”처럼 의미가 다른 신호에 알맞은 모드를 선택한다.

신호와 실제 조건을 분리해 생각해야 한다. 깨어났더라도 큐가 비었거나 종료 조건이 바뀌었을 수 있으므로 공유 상태를 다시 검사한다. 모든 스레드를 깨운 직후 곧바로 리셋하면 아직 스케줄되지 않은 대기자가 신호를 놓치는 경쟁도 가능하다. 현대 코드에서는 조건 변수나 고수준 태스크 도구를 우선 검토하되, 어떤 도구든 조건 검사와 상태 변경을 같은 동기화 규칙 안에서 처리한다.

### 1.14 세마포어

세마포어는 내부 카운터로 동시에 자원에 접근할 수 있는 수를 제한한다. 카운터가 양수이면 하나를 줄이고 통과하며, 0이면 반환될 때까지 기다린다. 뮤텍스가 배타적 소유와 임계 영역 보호에 적합하다면 세마포어는 DB 연결 20개, 동시 파일 압축 4개처럼 동일한 자원 슬롯을 관리하는 데 알맞다.

획득과 반환이 모든 종료 경로에서 짝을 이루지 않으면 허용량이 영구히 줄거나 상한을 초과한다. 범위 기반 가드를 사용하고, 기다리는 요청에 타임아웃과 취소를 전달한다. 세마포어로 과부하를 제한해도 대기 큐가 무한하면 문제가 남으므로, 허용 동시성·최대 대기 수·거절 정책을 하나의 용량 계획으로 다룬다.

### 1.15 원자 조작

원자 연산은 다른 스레드가 중간 상태를 관찰할 수 없는 단일 변경을 제공한다. 증가, 교환, 비교 후 교환(CAS)은 카운터, 플래그, 참조 갱신에 쓰인다. 특히 CAS는 현재 값이 예상값과 같을 때만 새 값으로 바꾸므로 잠금 없는 자료구조의 기본 재료가 된다.

원자 변수라고 해서 주변 로직 전체가 원자적이 되는 것은 아니다. 골드 감소와 아이템 추가처럼 두 상태가 함께 바뀌어야 하면 각각을 원자로 바꾸는 것만으로 중간 불일치를 막지 못한다. 메모리 순서도 언어와 플랫폼 규칙을 이해해야 하며, 복잡한 lock-free 코드는 ABA 문제, 회수 시점, 기아를 다뤄야 한다. 단순한 뮤텍스가 충분하다면 정확성과 유지보수성이 더 좋은 선택일 수 있다.

```cpp
#include <atomic>

std::atomic<int> connectedPlayers{0};

void OnConnected() {
    connectedPlayers.fetch_add(1, std::memory_order_relaxed);
}

bool TrySetRunning(std::atomic<bool>& running) {
    bool expected = false;
    return running.compare_exchange_strong(expected, true);
}
```

단순 통계 카운터처럼 다른 데이터와의 순서 관계가 필요 없는 값에는 완화된 메모리 순서를 검토할 수 있다. 반면 여러 필드가 함께 만족해야 하는 게임 규칙은 원자 변수 하나로 표현하려 하지 말고 잠금이나 단일 소유자 모델을 사용한다.

### 1.16 멀티스레드 프로그래밍의 흔한 실수들

자주 발생하는 실수는 쓰기만 잠그고 읽기를 잠그지 않는 것, 경로마다 잠금 순서가 다른 것, 논리 변경의 일부만 보호하는 것, 잠금 안에서 느린 I/O를 하는 것이다. 한 함수가 잠금을 요구하면 그 함수를 호출하는 상위 코드와 전달되는 객체까지 규칙이 퍼지는 “잠금의 전염성”도 생긴다. 객체를 파괴할 때 대기자나 진행 중인 작업이 남아 있으면 잠금 자체의 수명도 문제가 된다.

스레드 안전한 컨테이너도 복합 동작을 자동으로 안전하게 만들지 않는다. “존재 확인 후 삽입”, “앞 원소 확인 후 제거” 사이에 다른 스레드가 끼어들 수 있다. API를 설계할 때 복합 의도를 하나의 원자적 메서드로 제공하고, 보호되는 불변식과 호출 전제조건을 코드 가까이에 기록한다. 테스트에서는 스케줄러의 우연에 기대지 말고 반복 부하, 의도적인 지연, 종료 경합을 넣는다.

### 1.17 심화 내용 및 더 읽을거리

직접 스레드와 잠금을 관리하는 방식 외에도 태스크 기반 병렬성, 퓨처·프로미스, 병렬 컨테이너, 코루틴 같은 고수준 도구가 있다. 이들은 생성과 스케줄링을 추상화하지만 공유 상태와 취소, 예외 전달 문제를 없애지는 않는다. 도구가 보장하는 순서, 실행 컨텍스트, 실패 전파 규칙을 확인해야 한다.

액터 모델은 상태를 액터 내부에 가두고 메시지로만 상호작용하게 해 공유 쓰기를 줄인다. 게임의 룸이나 플레이어 세션을 액터로 표현할 수 있지만 액터 간 메시지는 지연·중복·순서 문제를 가질 수 있고, 한 액터에 일이 몰리면 병목이 된다. 어떤 모델이든 핵심은 상태의 단일 소유자와 경계를 명확히 하고 실제 부하로 처리량과 장애 동작을 검증하는 것이다.

## 공부할 내용

1. 같은 카운터를 여러 스레드가 증가시키는 프로그램으로 경쟁 상태를 재현한다.
2. 뮤텍스와 원자 변수를 각각 적용해 정확성, 처리량, 대기 시간을 비교한다.
3. 두 뮤텍스의 획득 순서를 뒤집어 교착 상태를 만들고 호출 스택으로 원인을 찾는다.
4. CPU 작업과 I/O 대기 작업을 나눠 스레드 풀 크기에 따른 처리량 변화를 측정한다.
