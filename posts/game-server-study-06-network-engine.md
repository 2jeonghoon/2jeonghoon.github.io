소켓 API만으로도 게임 서버를 만들 수 있지만, 제품 수준의 통신에는 연결 상태 관리, 직렬화, 재접속, 암호화, 통계, P2P 연결 같은 반복 작업이 필요하다. 네트워크 엔진은 이 공통 문제를 추상화한다. 중요한 것은 특정 제품의 API를 외우는 것이 아니라 추상화가 감추는 상태와 실패를 이해하는 것이다.

## 엔진을 선택할 때 볼 것

지원 플랫폼과 언어 외에도 전송 프로토콜, 서버 배포 방식, 관측 기능, 라이선스, 장기 지원 여부를 확인해야 한다. 엔진이 연결과 재전송을 대신 처리하더라도 애플리케이션은 메시지의 신뢰성 요구, 권한 검증, 과부하 정책을 직접 결정해야 한다.

연결 객체는 접속 중, 연결됨, 일시 중단, 복구 중, 종료 같은 상태를 가질 수 있다. 모바일에서는 와이파이와 셀룰러가 바뀌거나 앱이 백그라운드로 이동할 수 있다. 자동 복구 기능을 켜더라도 세션이 살아 있는 시간, 중복 로그인, 재전송 가능한 요청, 복구 실패 후 정리 방법을 애플리케이션 규칙으로 정해야 한다.

## 메시지와 원격 호출

전통적인 메시지 API는 바이트 배열과 메시지 종류를 직접 다룬다. 원격 메서드 호출 방식은 송신 측 프록시와 수신 측 스텁을 생성해 함수 호출처럼 보이게 한다. 코드가 읽기 쉬워지는 장점이 있지만 네트워크 호출은 로컬 함수와 다르다. 지연, 유실, 중복, 순서, 버전 불일치, 상대 프로세스 종료를 항상 고려해야 한다.

인터페이스 정의 파일을 사용할 때는 필드 번호와 타입을 안정적으로 유지하고, 새 필드는 선택적으로 추가하며, 구버전 상대가 모르는 메시지를 받았을 때의 정책을 정해야 한다. 요청마다 식별자를 두면 타임아웃 후 재시도와 중복 실행을 구분할 수 있다.

## P2P와 릴레이

P2P는 클라이언트끼리 직접 데이터를 주고받아 서버 대역폭을 줄이고 지연을 낮출 수 있다. 하지만 NAT와 방화벽 때문에 직접 연결이 항상 가능하지 않다. 홀 펀칭이 실패하면 릴레이 서버를 거치는 대체 경로가 필요하다. P2P를 사용해도 신뢰할 수 없는 클라이언트가 최종 게임 판정을 맡아서는 안 된다.

그룹 단위 P2P에서는 참여와 탈퇴, 호스트 변경, 멤버별 연결 품질, 릴레이 전환을 관리한다. 채팅 같은 기능으로 작은 실험을 만든 뒤 연결 실패와 악성 메시지를 시험하는 편이 좋다.

## 스레드 모델

네트워크 콜백이 여러 워커에서 동시에 실행되면 게임 상태에 잠금이 필요하다. 콜백은 I/O 스레드에서 짧게 받아 연결별 또는 월드별 작업 큐로 전달하는 구조가 이해하기 쉽다. 멀티프로세스 방식은 장애 격리와 코어 활용에 유리하지만 프로세스 사이의 상태 전달과 운영 복잡도가 늘어난다.

## 원문별 상세 정리

### 6.1 게임 서버와 네트워크 엔진

네트워크 엔진은 연결 관리, 직렬화, 신뢰 채널, 암호화, NAT 통과, RPC 같은 반복 기능을 추상화한다. 직접 소켓을 다루는 것보다 개발 속도를 높이고 검증된 구현을 활용할 수 있지만 제품의 트래픽 형태와 맞지 않는 추상화가 성능이나 디버깅을 어렵게 만들 수 있다.

선정할 때 최대 연결 수 같은 홍보 수치만 보지 말고 지원 플랫폼, 전송 방식, 스레드 모델, 메모리 할당, 장애 처리, 버전 호환, 라이선스와 유지보수 상태를 확인한다. 작은 부하 시험으로 메시지 크기별 처리량과 지연, 연결 폭주, 패킷 손실, 모바일 네트워크 변경을 재현한다. 엔진을 사용해도 게임 상태의 권한과 보안 검증은 애플리케이션 책임이다.

### 6.2 개발 환경과 기본 모듈

엔진을 도입하면 SDK, 헤더와 라이브러리, 런타임 파일, 빌드 설정을 클라이언트와 서버에 일관되게 구성해야 한다. 디버그와 릴리스, 32·64비트, 정적·동적 링크가 섞이지 않게 하고 배포 머신에 필요한 런타임 의존성을 기록한다. 예제 프로젝트가 실행되는 최소 구성을 먼저 만든 뒤 게임 코드와 통합한다.

초기 모듈은 네트워크 수명 주기, 설정 로드, 로그, 메시지 등록, 이벤트 디스패치 경계를 분리한다. 엔진 타입이 게임 전역으로 퍼지면 교체와 테스트가 어려워지므로 얇은 어댑터와 애플리케이션 인터페이스를 둔다. 시작 실패와 부분 초기화 뒤 자원 정리, 종료 시 콜백 중단과 연결 해제를 역순으로 처리하는 절차도 기본 모듈에 포함한다.

### 6.3 게임 클라이언트-서버 간 통신

클라이언트는 서버 주소와 프로토콜 버전을 가지고 연결을 요청하고 서버는 연결 결과와 인증 단계를 처리한다. 연결 이벤트가 비동기로 전달되는 엔진에서는 UI 스레드와 네트워크 콜백 스레드가 다를 수 있다. 콜백에서 게임 객체를 직접 수정하기보다 스레드 안전한 큐를 통해 주 실행 루프로 넘긴다.

연결 성공, 실패, 타임아웃, 서버 거절, 연결 중단을 서로 다른 상태로 표현한다. 재연결은 지수 백오프와 무작위 지연으로 동시 폭주를 줄이고 사용자가 취소할 수 있어야 한다. 새 연결이 만들어졌을 때 이전 세션의 늦은 콜백이 새 상태를 덮지 않도록 연결 세대 번호나 세션 ID로 구분한다.

### 6.4 메시지 주고받기

엔진이 제공하는 메시지 API는 대상, 신뢰성, 순서 채널, 우선순위 같은 옵션을 가질 수 있다. 로그인 응답과 아이템 변경은 신뢰·순서가 필요하지만 위치 갱신은 오래된 값보다 최신 값이 중요하다. 모든 메시지를 같은 옵션으로 보내면 불필요한 지연이나 트래픽이 생긴다.

직렬화된 데이터의 최대 크기와 필드 버전을 정하고 수신 측에서 범위를 재검증한다. 브로드캐스트는 편리하지만 실제 관심 대상보다 넓게 보내면 접속자 수에 비례해 비용이 급증한다. 메시지별 전송량, 빈도, 큐 대기 시간을 계측하고 디버그 도구에서 메시지 이름과 세션, 추적 ID를 확인할 수 있게 한다.

### 6.5 와이파이·셀룰러 연결 핸드오버

모바일 기기가 Wi-Fi에서 셀룰러로 바뀌면 IP 주소와 NAT 매핑, 사용 가능한 인터페이스가 변한다. 기존 연결은 끊기거나 한동안 응답이 없을 수 있으며 운영체제가 네트워크 변화를 알려도 실제 인터넷 연결 가능성은 별도로 확인해야 한다. 게임은 짧은 단절을 즉시 로그아웃으로 처리하지 않고 재접속 유예를 둘 수 있다.

재접속 시 비밀번호를 다시 보내기보다 만료와 재사용 방지가 있는 세션 자격 증명을 사용한다. 서버는 새 연결을 기존 플레이어 세션과 안전하게 결합하고 이전 연결을 무효화한다. 마지막으로 확인한 서버 틱이나 이벤트 번호를 전달해 누락분을 받거나 전체 스냅숏으로 복구한다. 핸드오버 동안 입력을 얼마나 버퍼링할지와 오래된 입력을 폐기할 기준도 필요하다.

### 6.6 원격 메서드 호출

RPC 또는 RMI는 원격 메시지를 로컬 함수 호출처럼 표현해 보일러플레이트를 줄인다. 그러나 호출은 실제로 직렬화와 네트워크, 원격 큐, 실행, 응답을 거치며 실패 방식도 로컬 함수와 다르다. 상대가 실행했지만 응답만 유실됐는지 구분할 수 없는 경우가 있으므로 타임아웃 뒤 무조건 재호출하면 중복 효과가 발생한다.

인터페이스에 요청 ID, 시간 제한, 오류 모델, 버전을 포함하고 중요한 명령은 멱등하게 만든다. 콜백 스레드에서 다시 동기 RPC를 호출하면 순환 대기나 스레드 고갈이 생길 수 있다. 긴 작업은 비동기 응답과 완료 알림으로 나누고, 분산 추적을 위해 호출 체인 전체에 상관관계 ID를 전달한다.

### 6.7 클라이언트끼리 P2P 통신

P2P는 클라이언트들이 서로 직접 데이터를 보내 서버 대역폭과 경우에 따라 경로 지연을 줄인다. 하지만 NAT와 방화벽 때문에 직접 연결이 항상 가능하지 않고, 참가자의 업로드 품질과 기기 성능이 세션에 영향을 준다. 직접 연결 실패 시 릴레이를 사용하고 경로 전환이 게임 상태를 깨지 않게 해야 한다.

클라이언트를 신뢰할 수 없으므로 승패와 경제 상태의 최종 권한을 P2P 참가자 한 명에게 무조건 맡기기 어렵다. 호스트 권한 구조라면 호스트 이탈과 조작 위험, 새 호스트 선출과 상태 이전을 설계한다. 피어의 실제 IP가 다른 사용자에게 노출되는 개인정보·공격 위험도 평가하고, 필요하면 항상 릴레이를 사용한다.

### 6.8 P2P를 이용한 채팅과 그룹 통신

여러 피어에게 메시지를 보내는 기능은 단순 방송처럼 보여도 참가자 변경과 전달 순서, 중복, 호스트 이탈을 다뤄야 한다. 그룹 멤버십 버전을 두고 메시지가 어느 구성에서 생성됐는지 구분하면 떠난 사용자나 새 사용자의 처리 기준을 세울 수 있다. 큰 그룹에서는 모든 피어가 서로 연결하는 완전 연결 구조의 연결 수가 급증한다.

채팅은 신고, 차단, 보관, 제재가 필요하므로 서버 중계가 운영상 더 적절할 수 있다. P2P 음성이나 상태 전달을 사용하더라도 세션 생성과 권한, 메타데이터는 서버가 관리하는 혼합 구조가 흔하다. 기능마다 P2P로 얻는 대역폭 이득과 보안·운영 비용을 비교한다.

### 6.9 스레드 모델

네트워크 엔진이 콜백을 어느 스레드에서 호출하는지 모르면 데이터 레이스와 프레임 지연이 발생한다. 전용 네트워크 스레드, 내부 워커 풀, 사용자가 직접 폴링하는 모델은 각각 다른 규칙을 가진다. 콜백이 동시에 실행될 수 있는지, 같은 연결의 메시지 순서가 보장되는지, 오래 걸리는 콜백이 다른 연결을 막는지 확인한다.

안전한 기본 패턴은 네트워크 콜백에서 최소한의 검증과 복사만 한 뒤 게임 로직 소유 스레드의 큐로 전달하는 것이다. 반대 방향도 연결별 송신 큐로 직렬화한다. 종료 시 엔진 스레드가 여전히 콜백을 실행하는 동안 게임 객체를 파괴하지 않도록 새 작업 차단, 연결 종료, 워커 합류, 객체 파괴의 순서를 정한다.

### 엔진 콜백과 게임 스레드의 경계

네트워크 엔진이 내부 워커에서 콜백을 실행한다면 게임 객체를 직접 수정하지 않고 명령을 소유 스레드로 전달한다.

```cpp
void NetworkListener::OnMessage(ConnectionId connection,
                                std::span<const std::byte> bytes) {
    auto command = DecodeAndValidate(connection, bytes);
    if (!command) return;

    gameCommandQueue.Push(std::move(*command));
}

void GameLoop::Tick() {
    while (auto command = gameCommandQueue.TryPop()) {
        ApplyCommand(*command); // 게임 상태는 이 스레드에서만 변경
    }
}
```

큐에 넣은 명령은 원본 네트워크 버퍼를 참조하지 않고 필요한 데이터를 소유해야 한다. 연결이 끊겼다가 다시 만들어졌을 때 이전 콜백을 구별하도록 세션 세대 번호도 포함한다.

### 연결과 재접속 상태

```text
Disconnected ── Connect ──> Connecting
      ▲                         │
      │                         ├─ 성공 ──> Authenticating ──> Connected
      │                         │                              │
      └──── 취소/최종 실패 <────┴──── 오류/타임아웃 <─────────┘
                                            │
                                            └─ Backoff 뒤 재시도
```

재시도 간격은 계속 늘리되 작은 무작위 값을 섞어 많은 클라이언트가 동시에 서버를 두드리지 않게 한다. 사용자가 로그아웃했거나 앱을 닫았다면 예약된 재시도를 취소한다.

### RPC가 로컬 호출과 다른 점

```cpp
struct PurchaseRequest {

    ItemId itemId;

// 타임아웃은 '실패'가 아니라 결과를 모른다는 뜻일 수 있다.
auto result = co_await shopClient.Purchase(request, 2s);
if (result.timedOut()) {
    result = co_await shopClient.GetTransaction(request.transactionId);

```

원격 서버가 구매를 처리한 뒤 응답만 유실될 수 있으므로 같은 구매를 새 거래로 재호출하지 않는다. 거래 ID로 기존 결과를 조회하거나 멱등하게 재전송한다.

### P2P 직접 경로와 중계 경로

```text
직접 연결 성공:  클라이언트 A <────────────> 클라이언트 B

직접 연결 실패:  클라이언트 A <──> 릴레이 서버 <──> 클라이언트 B
```

NAT 홀 펀칭에 성공하더라도 상대 주소 노출과 DDoS 위험을 검토한다. 게임 결과의 최종 권한은 별도 권위 서버에 남기고, P2P는 음성이나 지연에 민감한 보조 데이터에 제한할 수 있다.

## 공부할 내용

1. 네트워크 엔진을 쓰지 않은 소켓 서버와 엔진 기반 서버의 책임 목록을 비교한다.
2. 연결 중단 뒤 재접속할 때 재실행해도 되는 요청과 그렇지 않은 요청을 나눈다.
3. 간단한 RMI 인터페이스에 버전이 다른 클라이언트를 연결해 호환 정책을 설계한다.
4. 직접 P2P, 홀 펀칭 실패, 릴레이 전환의 상태도를 그린다.
