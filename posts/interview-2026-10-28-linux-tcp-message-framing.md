## 오늘의 질문

클라이언트가 메시지 두 개를 각각 send()했지만 서버에서는 recv() 한 번에 합쳐서 받거나 여러 번에 나눠 받습니다. 이유를 설명하고, 길이 헤더를 사용하는 수신 처리를 설계해 주세요. 최대 메시지 크기는 1MB입니다.

## 핵심 해설

핵심 원인은 TCP가 애플리케이션 메시지 경계를 보존하지 않는 바이트 스트림이라는 점이다. MTU와 세그먼트 분할만으로 설명하면 부족하며 send 호출, TCP 세그먼트, recv 반환 범위는 일대일 대응하지 않는다. 애플리케이션이 복원하는 단위는 메시지 또는 프레임이라고 표현하는 것이 정확하다.

고정 크기 헤더조차 여러 recv로 나뉠 수 있다. 연결별 버퍼에 누적하고 헤더가 완성되면 바이트 순서를 변환하여 길이를 해석한다. 여기서는 본문 최대 크기를 1MiB로 정의한다. 길이를 검증한 뒤 헤더와 본문이 모두 도착할 때 처리한다. 남은 데이터에서 다음 메시지를 반복 추출하고 미완성 데이터는 유지한다.

과도한 길이, 길이 합산 오버플로, 버퍼 상한과 수신 타임아웃을 검토한다. 스트림에서 recv가 0이면 정상적인 상대 종료로 처리하고 미완성 메시지는 프로토콜 정책에 따라 폐기한다. EINTR과 EAGAIN/EWOULDBLOCK은 영구 오류와 구분한다.

## 바이트 스트림을 쉽게 이해하기

바이트는 데이터를 구성하는 단위이고, 스트림은 그 단위들이 순서대로 이어지는 흐름이다. TCP 연결에서는 송신 애플리케이션이 기록한 바이트를 수신 애플리케이션이 순서대로 읽는다. TCP는 애플리케이션이 의도한 메시지의 시작과 끝을 구분해 주지 않는다.

예를 들어 채팅 프로그램이 HELLO와 WORLD라는 두 메시지를 보낸다고 하자. 아래 예시는 두 send가 요청한 5바이트를 모두 보냈다고 가정하며 문자열 끝의 널 문자는 보내지 않는다.

~~~cpp
send(fd, "HELLO", 5, 0);
send(fd, "WORLD", 5, 0);
~~~

개발자는 다음처럼 메시지를 구분한다.

~~~text
첫 번째 메시지: HELLO
두 번째 메시지: WORLD
~~~

하지만 TCP로 전달되는 애플리케이션 데이터는 다음처럼 이어진 바이트다.

~~~text
H E L L O W O R L D
~~~

HELLO 뒤에 send를 한 번 끝냈다는 구분 표시가 자동으로 붙는 것은 아니다. 처음부터 한 번의 send로 HELLOWORLD를 보냈어도 수신 애플리케이션은 바이트 내용만으로 두 경우를 구분할 수 없다.

## recv는 메시지 한 개를 받는 함수가 아니다

충분한 수신 버퍼를 제공해도 연결 상태와 데이터 도착 시점 등에 따라 다음 결과가 모두 가능하다.

~~~text
경우 A
recv 1 → HELLO
recv 2 → WORLD

경우 B
recv 1 → HELLOWORLD

경우 C
recv 1 → HE
recv 2 → LLOW
recv 3 → ORLD
~~~

경우 C는 수신 경계가 첫 번째 메시지 중간과 두 번째 메시지 중간을 모두 가로지르는 예시다. 어느 경우든 받은 바이트를 순서대로 연결하면 HELLOWORLD다. 메시지 경계가 보존되지 않는다는 말은 바이트 순서가 뒤섞이거나 정상적으로 받은 바이트가 사라진다는 뜻이 아니다.

recv(fd, buffer, 1024, 0)의 1024는 이번 호출에서 받을 수 있는 최대 바이트 수다. 일반적인 recv는 항상 1024바이트를 채우거나 메시지 하나를 완성할 때까지 기다리는 함수가 아니다. 반드시 반환된 바이트 수를 사용해야 한다.

수신 결과만 보고 HELLO와 WORLD인지, HELLOW와 ORLD인지 결정할 수 없다. 따라서 양쪽 애플리케이션이 메시지 구분 규칙인 프로토콜을 약속해야 한다.

## 메시지 경계를 직접 넣는 세 가지 방법

| 방법 | 예시 | 주의할 점 |
| --- | --- | --- |
| 고정 길이 | 매 메시지를 16바이트로 정의 | 남는 공간과 가변 길이 데이터 처리 |
| 구분자 | HELLO 뒤에 줄바꿈을 붙임 | 본문에 구분자가 들어가는 경우 처리 |
| 길이 헤더 | 본문 앞에 본문 길이를 붙임 | 길이 검증과 부분 수신 처리 |

줄바꿈도 TCP가 해석하는 경계는 아니다. 수신 애플리케이션이 버퍼에서 줄바꿈을 찾아 메시지를 나눈다.

## 길이 헤더로 메시지를 복원하는 과정

헤더는 4바이트 부호 없는 정수이고 네트워크 바이트 순서로 본문 길이를 담는다고 약속하자. 본문 길이 5의 헤더는 16진수로 00 00 00 05다. 아래 대괄호와 구분선은 설명용 표시이며 전송하지 않는다.

~~~text
[00 00 00 05][H E L L O][00 00 00 05][W O R L D]
 └ 4바이트 ┘ └ 5바이트 ┘
~~~

헤더를 붙여도 TCP 수신 경계가 고정되지는 않는다. 예를 들어 다음 순서로 나뉘어 도착할 수 있다.

~~~text
첫 수신:  00 00
          → 헤더 4바이트가 부족하므로 보관

둘째 수신: 00 05 H E
          → 누적 데이터에서 길이 5를 확인
          → 본문은 2바이트뿐이므로 더 기다림

셋째 수신: L L O 00 00 00 05 W O R L D
          → HELLO 완성, 처리
          → 남은 데이터에서 다음 헤더와 WORLD도 추출
~~~

연결별 버퍼를 이용한 처리 흐름은 다음과 같다.

~~~text
수신 바이트를 버퍼에 추가

반복:
    헤더 4바이트가 없으면 다음 수신을 기다림
    본문 길이를 읽고 최대 허용 크기를 검증
    헤더 + 본문 전체가 없으면 다음 수신을 기다림
    완성된 메시지를 처리하고 해당 부분을 버퍼에서 소비
    남은 데이터로 다음 메시지 검사
~~~

길이 헤더의 역할은 recv를 메시지 단위로 바꾸는 것이 아니라, 누적한 바이트에서 애플리케이션이 경계를 찾아낼 수 있도록 정보를 제공하는 것이다.

## MTU와 메시지 경계는 어떻게 다른가

MTU는 네트워크 링크에서 운반하는 패킷 크기와 관련된 개념이다. TCP는 MSS와 경로 MTU 등을 고려해 데이터를 세그먼트로 나눌 수 있다. 이것과 애플리케이션 메시지의 구분은 서로 다른 층의 문제다.

메시지가 MTU보다 작거나 같은 컴퓨터 안에서 통신하더라도 send와 recv가 일대일 대응한다고 가정하면 안 된다. TCP가 메시지 경계를 제공하지 않는다는 인터페이스의 성질은 그대로다.

실제 송신 코드에서는 send 역시 요청한 길이보다 적게 보낼 수 있으므로 반환값과 오류를 확인하고 아직 보내지 못한 데이터를 이어서 전송해야 한다. TCP의 신뢰성은 상대 애플리케이션이 메시지를 처리하거나 저장했다는 보장과도 다르다. 필요한 경우 응답이나 확인 절차를 프로토콜에 추가한다.

## 왜 합쳐서 읽히는가: 버퍼와 읽는 시점

송신과 수신은 서로 독립적인 시점에 실행된다. 일반적인 send는 데이터를 운영체제의 송신 버퍼에 넘기고, 수신 측은 도착하여 순서가 맞춰진 데이터를 수신 버퍼에서 recv로 꺼낸다.

~~~text
송신 프로그램 → send → 송신 버퍼
                         ↓ TCP 전송
수신 프로그램 ← recv ← 수신 버퍼
~~~

| 시점 | 일어난 일 | 아직 읽지 않은 수신 데이터 |
| --- | --- | --- |
| 1 | HELLO 도착 | HELLO |
| 2 | 수신 프로그램은 아직 읽지 않음 | HELLO |
| 3 | WORLD 도착 | HELLOWORLD |
| 4 | 충분한 버퍼로 recv 호출 | 한 번에 10바이트를 읽을 수 있음 |

네트워크에서 같은 패킷으로 합쳐져야만 이런 현상이 생기는 것은 아니다. 서로 다른 세그먼트로 도착해도, 수신 버퍼에 쌓인 연속 데이터를 한 번의 recv가 읽을 수 있다. 먼저 읽으면 HELLO와 WORLD를 나누어 받을 수도 있다.

TCP는 시퀀스 번호로 바이트의 위치를 추적한다. 순서를 맞추고 중복과 손실에 대응하지만, 특정 바이트 뒤에서 send 호출이 끝났다는 정보는 제공하지 않는다. 따라서 한 번에 HELLOWORLD를 쓰거나 HELLO와 WORLD로 나누어 써도 바이트 내용만으로 구분할 수 없다.

## 구조체 단위로 읽으면 길이 헤더가 없어도 될까?

모든 메시지를 같은 고정 크기로 약속한다면 길이 헤더를 생략할 수 있다. 예를 들어 모든 메시지의 전송 형식을 8바이트로 정의하면 버퍼에서 8바이트씩 추출한다. 이것도 고정 길이 프레이밍이라는 프로토콜 규칙이다.

구조체를 recv에 넘기는 것 자체가 TCP에 구조체 경계를 알려주지는 않는다.

~~~cpp
struct Message {
    std::uint32_t userId;
    std::uint32_t score;
};

Message message{};
ssize_t n = recv(fd, &message, sizeof(message), 0);
~~~

위 코드는 설명용이다. recv의 크기 인자는 최대 수신 크기이므로 n이 sizeof(message)보다 작을 수 있다. 초기화가 되어 있어도 미수신 필드는 완성된 메시지가 아니다. 모든 바이트를 모으기 전에 message를 처리하면 안 된다.

고정 길이 프로토콜의 누적 예시는 다음과 같다.

~~~text
메시지 크기: 8바이트

첫 수신: 3바이트 → 보관
둘째 수신: 9바이트 → 누적 12바이트
                        8바이트 메시지 처리
                        나머지 4바이트 보관
셋째 수신: 4바이트 → 다음 8바이트 메시지 처리
~~~

같은 구조체 크기를 recv에 지정해 직접 누적하는 방식도 가능하다. 이 경우 매번 아직 부족한 바이트 수만 요청하고, 채워진 위치 다음부터 기록해야 한다. 블로킹 여부에 따라 대기와 EAGAIN 처리가 달라진다. MSG_WAITALL 역시 연결 종료나 오류 등에서 짧게 반환할 수 있어 반환값 확인은 필요하다.

## 메모리 구조체와 전송 형식은 구분한다

C++ 구조체의 메모리를 그대로 전송하면 패딩, 정렬, 정수 바이트 순서와 ABI 차이를 고려해야 한다. std::string, std::vector, 포인터가 든 구조체는 본문 데이터 대신 프로세스 내부 주소나 관리 정보를 담을 수 있으므로 원시 메모리 복사로 전달해서는 안 된다. 패딩에 초기화되지 않은 데이터가 남으면 정보 노출 위험도 있다.

앞의 Message처럼 정수만 있는 구조라도 전송 형식을 명시적으로 정의하는 편이 안전하다.

~~~text
메시지 크기: 8바이트
0~3바이트: userId, 부호 없는 32비트, 네트워크 바이트 순서
4~7바이트: score, 부호 없는 32비트, 네트워크 바이트 순서
~~~

수신 버퍼에서 8바이트가 모이면 각 필드를 해석하여 내부 Message 객체에 넣는다. 네이티브 구조체의 sizeof를 전송 규격으로 암묵적으로 사용하지 않는다.

가변 길이 문자열이나 여러 종류의 메시지를 지원한다면 길이 헤더 또는 종류별 크기 규칙 등이 필요하다. 모든 메시지를 같은 크기로 정의하면 길이 헤더는 없어도 되지만, 고정 크기라는 규칙과 부분 수신 처리는 반드시 남는다.

## 면접용 모범 답변

TCP는 메시지 경계를 보존하지 않는 바이트 스트림이므로 send와 recv는 일대일 대응하지 않습니다. 연결별 버퍼에 데이터를 누적해 헤더가 완성되면 길이를 읽고 상한을 검증하겠습니다. 본문이 모두 도착한 메시지만 처리하고 남은 데이터에서 다음 메시지를 계속 추출하겠습니다. 헤더의 부분 수신, 연결 종료와 타임아웃도 처리하겠습니다.
