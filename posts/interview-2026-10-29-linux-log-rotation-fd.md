## 오늘의 질문

프로세스가 로그 파일을 열어 기록하고 있습니다. 운영자가 파일 이름을 바꾸고 원래 경로에 새 파일을 만들었습니다. 기존 FD를 통한 기록은 어느 파일로 향할까요? 로그 로테이션을 지원하려면 프로그램에 어떤 동작이 필요합니까?

## 핵심 해설

기존 FD는 이름이 바뀐 원래 파일에 계속 기록한다. FD는 매 write마다 경로를 재검색하는 기능이 아니라 열린 파일 기술에 대한 참조다. 경로는 open할 때 대상을 찾는 데 사용한다. rename과 같은 경로 변경이 기존 참조를 새 파일로 바꾸지는 않는다.

~~~text
처음:
app.log → 파일 A
fd 3    → 파일 A

rename 후 새 app.log 생성:
app.log.1 → 파일 A ← fd 3
app.log   → 파일 B

기존 fd 3의 write는 파일 A로 감
~~~

새 로그로 전환하려면 회전된 app.log.1이 아니라 원래 활성 경로 app.log를 다시 열어야 한다.

로그 전용 스레드 또는 동기화된 로거가 재오픈 요청을 처리한다. 새 파일 open과 권한·대상 검증에 성공하면 기존 사용자 공간 버퍼를 적절히 flush하고 쓰기와 FD 교체를 직렬화한 뒤 이전 FD를 닫는다. open 실패 시 기존 FD를 유지하고 오류를 보고하는 정책이 가능하다.

~~~text
회전: app.log → app.log.1
새 app.log 생성
로거에 재오픈 요청
새 app.log 열기 성공
진행 중인 로그 쓰기와 동기화하여 FD 전환
이전 FD 닫기
~~~

SIGHUP 등을 재오픈 신호로 약속할 수 있지만 신호 핸들러에서 복잡한 로거 재설정을 직접 하지 않는다. 안전한 알림 경로를 통해 정상 실행 문맥에서 처리한다. 버퍼 flush가 전원 장애까지의 영속성을 자동 보장하는 것은 아니며 내구성 요구는 별도다.

copytruncate는 파일 복사 후 원본 크기를 줄이는 다른 방식이다. 이번 rename 후 새 파일 생성 방식과 구분하며 복사와 truncate 사이 유실 위험도 검토한다.

## 면접용 모범 답변

기존 FD는 경로가 아니라 열린 파일을 참조하므로 이름이 바뀐 원래 파일에 계속 기록합니다. 새 활성 로그에 쓰려면 원래 경로를 다시 열어야 합니다. 재오픈 성공을 확인하고 로거의 쓰기와 FD 교체를 동기화한 뒤 이전 FD를 닫겠습니다. 재오픈 실패와 사용자 공간 버퍼 처리도 고려하겠습니다.
