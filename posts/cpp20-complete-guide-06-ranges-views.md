## 6.1 범위와 뷰를 예제로 둘러보기

범위 알고리즘은 시작·끝 반복자 쌍 대신 컨테이너 자체를 받을 수 있다.
제약이 필요한 순회·비교·쓰기 능력을 검사하므로 인터페이스의 의도가 선명해진다.
projection은 객체에서 비교할 키를 꺼내는 정책이다.

아래는 독립 실행 예제다.

```cpp
#include <algorithm>
#include <cassert>
#include <ranges>
#include <vector>

struct Task { int priority; int minutes; };

int main() {
    std::vector<Task> tasks{{2, 30}, {1, 10}, {3, 50}};
    std::ranges::sort(tasks, {}, &Task::priority);
    auto short_tasks = tasks
        | std::views::filter([](const Task& t) { return t.minutes <= 30; })
        | std::views::transform([](const Task& t) { return t.priority; });
    int total = 0;
    for (int priority : short_tasks) total += priority;
    assert(total == 3);
}
```

뷰를 만드는 순간에 필터 결과 벡터를 따로 저장하는 것은 아니다.
순회하면서 필요한 원소를 찾고 변환한다.
따라서 결과를 여러 번 사용하면 필터와 변환도 다시 실행될 수 있다.

끝을 나타내는 센티널의 타입은 반복자와 달라도 된다.
개수로 끝을 정하거나, 데이터에 있는 종료 표식을 이용하는 범위도 만들 수 있다.
센티널 비교가 경계에 도달하도록 구성하지 못하면 안전한 범위가 아니다.

`ranges::begin`, `ranges::end`, `range_value_t` 등의 도구로 제네릭 코드를 작성한다.
모든 기존 알고리즘에 범위 버전이 생긴 것은 아니고, 범위 버전은 제약이 더 엄격할 수 있다.
기존 코드가 컴파일된다는 이유만으로 같은 타입이 새 알고리즘에서도 통과한다고 가정하지 않는다.

## 6.2 빌린 반복자와 빌린 범위

일부 범위 알고리즘은 임시 컨테이너를 인수로 받아도 실행 자체는 안전하다.
하지만 반환한 반복자가 식 종료 후 파괴된 컨테이너를 가리키면 위험하다.
`borrowed_iterator_t`와 `dangling`은 이 반환 경계의 위험을 타입으로 드러낸다.

lvalue 범위는 호출 후에도 원본이 존재한다는 전제에서 빌린 범위로 취급된다.
`span`처럼 원소를 소유하지 않는 일부 래퍼는 래퍼가 없어져도 원본이 남을 수 있다.
그렇다고 빌린 범위가 원소 소유자의 파괴나 재할당을 막아 주지는 않는다.

## 6.3 뷰를 사용할 때의 평가와 캐시

뷰는 이동 비용 등에 제약을 둔 범위 추상화이며, 복사 가능성은 구체 타입에 따라 다르다.
반드시 비소유라고 정의되는 것도 아니다.
각 뷰가 원본을 참조하는지, 다른 뷰를 값으로 담는지 구체적으로 봐야 한다.
파이프는 연산을 연결하는 문법이며 데이터의 수명을 자동으로 늘리는 표시는 아니다.

`filter_view`는 첫 일치 원소를 찾는 비용을 줄이려고 일부 상황에서 시작 위치를 캐시한다.
이것은 결과 전체를 캐시한다는 뜻이 아니다.
`transform_view`의 계산 결과를 저장된 원소처럼 여러 번 참조하면 예상보다 호출이 많아질 수 있다.

싼 필터 뒤에 비싼 변환을 놓을지, 변환 결과로 필터해야 할지에 따라 비용이 달라진다.
같은 변환을 반복해야 한다면 결과를 명시적으로 컨테이너에 저장하는 편이 합리적일 수 있다.
C++20에서 컨테이너 수집은 반복과 삽입 등으로 작성하며 C++23의 `ranges::to`와 구분한다.

## 6.4 원본이 없어지거나 바뀌는 경우

지역 벡터를 참조하는 뷰를 반환하면 벡터가 파괴되어 댕글링이 된다.
함수 반환형이 짧다고 소유권이 전달되는 것은 아니다.
콜백 안에서 참조 캡처한 지역 변수의 수명도 별도로 따져야 한다.

쓰기 가능한 뷰는 원본 원소를 바꿀 수 있다.
특히 필터의 조건을 만족하던 원소를 불만족하게 변경하는 동작은 안전한 일반 갱신 패턴이 아니다.
선택 기준과 수정할 필드를 분리하거나 별도 반복으로 처리하는 편이 읽기 쉽다.

원본 컨테이너의 재할당은 뷰가 보관하거나 만든 반복자를 무효화할 수 있다.
컨테이너에 원소를 추가한 뒤 기존 필터 뷰의 캐시가 새 상태를 자동 재탐색한다고 가정하지 않는다.
복사한 뷰도 원본 캐시와 동일한 내부 상태를 그대로 공유한다고 보장되지 않는다.

## 6.5 뷰의 const는 원소의 const와 다르다

`const vector<int>`의 순회는 보통 읽기 전용 원소를 준다.
반면 `const span<int>`는 래퍼를 바꾸지 못할 뿐 원소는 쓸 수 있다.
`ref_view`도 참조 대상의 const 성질을 봐야 한다.

어떤 뷰는 `begin()`에서 내부 캐시를 바꾸므로 const 객체로 순회할 수 없다.
컨테이너와 뷰를 함께 받는 함수에서 무조건 `const R&`를 쓰면 이런 뷰를 거부한다.
필요한 연산과 변경 가능성을 정한 뒤 `R&&` 등 적절한 인터페이스를 선택한다.

C++20에는 C++23의 `views::as_const`가 없다.
읽기 전용 원소가 필요하면 원본을 const 참조로 연결하거나 `span<const T>`를 쓰는 등 경계에서 표현한다.
단순히 뷰 변수에 `const`를 추가하는 것으로 깊은 const가 생기지는 않는다.

## 6.6 컨테이너 관용구를 그대로 적용하지 않기

| 익숙한 기대 | 뷰에서 다시 확인할 것 |
| --- | --- |
| 복사하면 데이터가 독립적이다 | 원본을 계속 공유하는가 |
| const이면 원소도 못 바꾼다 | 참조하는 원소 타입은 무엇인가 |
| begin은 관찰만 한다 | 시작 위치 캐시가 필요한가 |
| 같은 원소 접근은 값이 저장돼 있다 | 변환 함수를 다시 호출하는가 |
| 원본 수정 뒤 다시 순회하면 최신 상태다 | 캐시와 무효화 규칙이 있는가 |
