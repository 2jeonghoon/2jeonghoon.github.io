매일 면접 질문 하나와 정답, 핵심 해설을 정리한다. [지난 글](?post=interview-2026-10-19-character-rubber-banding)에서 다룬 서버 재조정을 숫자로 따라가 본다.

## 오늘의 질문

캐릭터는 1차원 직선 위에서 이동한다. 각 입력은 위치에 이동량을 더하며, 충돌과 가속도는 없다. 입력 번호는 순서대로 증가하고, 이 예제에서는 번호의 순환을 고려하지 않는다.

클라이언트는 100번 입력까지 서버 확인을 받은 뒤 다음 입력을 예측 실행했다.

| 입력 번호 | 이동량 |
| --- | ---: |
| 101 | +2 |
| 102 | +2 |
| 103 | −1 |
| 104 | +2 |

현재 클라이언트 위치는 **15**다. 이때 서버에서 **“102번 입력까지 처리한 위치는 11”**이라는 보정 메시지가 도착했다. 이 확인은 102번까지의 모든 입력이 처리됐다는 의미다.

1. 미확인 입력을 재실행한 뒤 현재 위치는 얼마인가? 어떤 입력 기록을 삭제하고 유지해야 하는가?
2. 재실행 없이 현재 위치를 서버 위치 11로 매 프레임 Lerp하면 어떤 문제가 생기는가?
3. 이후 늦게 도착한 “101번 입력까지 처리한 위치는 9”라는 보정 메시지는 어떻게 처리해야 하는가?

## 핵심 해설

### 1. 서버 위치 11은 현재가 아니라 102번까지의 상태다

서버 응답이 도착했을 때 클라이언트는 이미 104번까지 실행했다. 따라서 서버 위치를 현재 위치에 그대로 적용하면 이후 입력의 결과가 빠진다.

서버가 확인한 상태를 기준으로 미확인 입력을 순서대로 다시 적용한다.

$$
\begin{aligned}
x_{102}^{\mathrm{server}}&=11,\\
x_{103}^{\mathrm{replay}}&=11+(-1)=10,\\
x_{104}^{\mathrm{replay}}&=10+2=12.
\end{aligned}
$$

이 예제처럼 입력이 단순한 이동량 $\Delta x_i$를 더하는 경우에는,
서버 확인 번호 $k$ 이후 현재 번호 $n$까지의 재실행을 다음처럼 적을 수 있다.

$$
x_{\mathrm{corrected}}=x_k^{\mathrm{server}}+
\sum_{i=k+1}^{n}\Delta x_i
=11+(-1)+2=12.
$$

충돌이나 가속도가 있는 실제 시뮬레이션에서는 단순 합 대신 각 입력에 대한 상태 전이를 순서대로 재실행한다.

보정된 현재 위치는 **12**다. 기존 예측 위치 15와의 차이는 3이다. 입력을 현재 위치 15에 다시 더하는 것이 아니라, 서버 상태 11에서 시작한다는 점이 중요하다.

| 입력 기록 | 처리 | 이유 |
| --- | --- | --- |
| 102번까지 | 대기 입력 목록에서 삭제 | 서버가 누적 처리를 확인했다 |
| 103·104번 | 재실행 후에도 유지 | 서버가 아직 확인하지 않았다 |

클라이언트에서 재실행했다는 사실은 서버가 확인했다는 의미가 아니다. 다음 보정이 도착하면 아직 확인되지 않은 입력이 다시 필요할 수 있다.

### 2. Lerp는 올바른 현재 상태를 계산하지 못한다

11로 Lerp하면 이동이 부드러워 보일 수 있지만, 103·104번 입력의 결과가 누락된 과거 상태를 따라간다. 이 예제에서 현재 시점에 맞는 보정 목표는 **12**다.

처리 순서는 다음과 같다.

1. 서버가 확인한 시점의 상태를 적용한다.
2. 이후 미확인 입력을 순서대로 재실행해 현재 시뮬레이션 상태를 구한다.
3. 화면에 보이는 위치 차이는 필요한 시각적 스무딩으로 완화한다.

시뮬레이션 상태의 정확성과 화면에 보이는 움직임의 부드러움은 서로 다른 문제다. Lerp는 시각적 스무딩에 활용할 수 있지만 입력 재실행을 대신하지 못한다.

실제 게임에서는 위치뿐 아니라 속도와 이동 모드 등 재실행에 필요한 상태도 복원해야 한다. 입력 역시 이동량만이 아니라 방향과 실행 시간 등을 포함할 수 있다.

### 3. 뒤늦게 온 101번 보정은 무시한다

이미 102번까지의 보정을 수용했다. 이후 도착한 101번 보정은 더 오래된 상태이므로 적용하지 않는다.

이 예제에서는 마지막으로 수용한 확인 번호를 102로 저장하고, 그보다 작은 번호의 보정은 버린다. 실제 프로토콜에서는 번호 순환, 세션 변경, 동일 확인 번호에 대한 상태 갱신 여부도 설계에 맞게 처리해야 한다.

## Unreal과 연결하기

이 문제의 입력 번호는 원리를 설명하기 위한 단순한 모델이다. Unreal CharacterMovementComponent는 타임스탬프와 저장된 이동 정보 등을 이용하므로 이 숫자 예제를 엔진의 메시지 형식과 동일하게 보면 안 된다.

Epic 공식 문서는 클라이언트가 이동을 SavedMoves에 저장하고, 서버 확인에 따라 기록을 정리하며, 서버 보정 후 남은 이동을 재실행하는 흐름을 설명한다.
