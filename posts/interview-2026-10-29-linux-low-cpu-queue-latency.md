## 오늘의 질문

부하가 증가하자 응답 지연이 커졌지만 CPU 사용률은 낮습니다. 작업 큐 길이는 계속 늘고 있습니다. 원인 후보를 제시하고, 스레드 상태·락 대기·네트워크·디스크를 어떤 순서와 증거로 확인하겠습니까?

## 핵심 해설

wait/sleep은 CPU 낭비를 피하는 정상 동작일 수 있다. 대기 자체가 원인이라고 단정하지 말고 무엇을 왜 기다리는지 확인한다.

큐 증가가 지속되면 일정 구간에서 입력률이 완료율보다 높다는 뜻이다. 요청 유입률, 완료율, 큐 길이와 가장 오래된 요청의 나이, 큐 대기와 작업 실행 시간을 같은 시간대에 측정한다. 서버 전체 평균 CPU가 낮아도 단일 코어 포화나 CPU 할당 제한이 있을 수 있다.

작업이 있는데 소비자가 조건 변수에서 계속 기다린다면 알림 누락, 조건식과 큐 불일치, 잘못된 mutex 사용, 작업자 종료를 의심한다. 모든 작업자가 실행 중이면 긴 외부 I/O, 락이나 DB 연결 풀 대기, 디스크 fsync, 고정 sleep 재시도 등을 확인한다.

스레드별 CPU와 문맥 교환, 스레드 스택과 대기 위치를 수집한다. 예를 들어 pidstat -t로 스레드별 활동을 보고 짧은 strace로 시스템 호출과 소요 시간을 확인할 수 있다. tracing의 부하와 민감 정보 노출도 고려한다. futex 대기만으로 mutex 경합이라고 단정하지 않는다. 조건 변수 등도 futex를 사용하므로 스택과 잠금 계측을 함께 본다.

| 관찰 | 다음 확인 |
| --- | --- |
| 작업이 있는데 소비자가 조건 변수 대기 | 알림·조건식·큐 연결과 소비자 생존 |
| 여러 스레드가 같은 락에서 대기 | 소유 스레드, 임계 구역의 I/O와 보유 시간 |
| 네트워크 호출 대기 | 상대 지연, 타임아웃, 연결 풀, 송수신 큐 |
| 쓰기·fsync 지연 | 디스크 지연, 큐 깊이와 커밋 패턴 |
| nanosleep 반복 | 고정 sleep 폴링·재시도 정책 |
| 일부 코어만 포화 | 단일 스레드 직렬 구간과 할당 제한 |

네트워크 다음 디스크처럼 고정 순서를 따르기보다는 스택과 요청 추적이 가리키는 경로를 조사한다. 스레드 수 증가는 락·DB·외부 서버 부하를 악화시킬 수 있다. 수정 후 같은 부하에서 처리량, p95/p99 지연, 큐 적체와 오류를 비교한다.

## 면접용 모범 답변

낮은 CPU만으로 자원이 충분하다고 판단하지 않겠습니다. 유입률과 완료율, 큐 대기와 작업 시간을 측정하고 스레드별 상태와 스택으로 대기 지점을 찾겠습니다. 작업이 있는데 소비자가 잠들어 있으면 알림과 조건식을 확인하고, 작업자가 락이나 외부 I/O에서 막혀 있으면 해당 대기와 의존 서비스 지연을 검증하겠습니다. 변경 후 동일 부하에서 지연과 적체가 개선됐는지 확인하겠습니다.
