소켓 API는 네트워크를 파일과 비슷한 읽기·쓰기 인터페이스로 다루게 해준다. 그러나 호출이 언제 기다리고, 운영체제 버퍼가 언제 가득 차며, 완료 통지가 어떤 스레드로 전달되는지를 이해하지 못하면 서버는 적은 연결에서도 쉽게 멈춘다.

## 블로킹 소켓의 동작

블로킹 호출은 지금 작업을 마칠 수 없을 때 호출한 스레드를 대기 상태로 전환한다. 이때 해당 스레드는 CPU를 계속 소비하지 않지만 다른 일을 수행할 수도 없다. 단순한 구조에서는 이해하기 쉽지만 연결마다 대기 스레드를 두면 스택 메모리와 스케줄링 비용이 커진다.

TCP 송신은 상대 애플리케이션이 데이터를 읽었다는 뜻이 아니라 로컬 송신 버퍼에 데이터를 받아들였다는 뜻에 가깝다. 수신도 한 번의 호출로 논리 메시지 전체가 온다고 보장되지 않는다. 수신 버퍼가 차면 TCP는 흐름 제어를 통해 송신 속도를 낮추지만, UDP 데이터그램은 공간이 없을 때 버려질 수 있다.

## 논블로킹과 이벤트 기반 I/O

논블로킹 소켓은 즉시 처리할 수 없는 작업에 대기 상태를 반환한다. 애플리케이션이 모든 소켓을 반복 검사하면 CPU를 낭비하므로 운영체제의 이벤트 통지 기능과 결합한다.

Linux의 `epoll`은 관심 소켓을 등록하고 준비된 이벤트를 얻는다. 레벨 트리거는 처리할 데이터가 남아 있는 동안 계속 알리고, 엣지 트리거는 상태가 변하는 순간을 중심으로 알린다. 엣지 트리거에서는 더 읽을 수 없다는 결과가 나올 때까지 반복 처리하지 않으면 남은 데이터를 놓칠 수 있다.

Windows의 IOCP는 I/O 완료를 큐로 전달하고 제한된 워커 스레드가 완료 이벤트를 처리하는 모델이다. `epoll`의 준비 통지와 IOCP의 완료 통지는 관점이 다르지만, 둘 다 많은 연결을 적은 스레드로 다루려는 목적을 가진다. 플랫폼 API의 차이보다 중요한 것은 연결 상태, 버퍼 수명, 취소와 종료 순서를 명확히 관리하는 것이다.

## 서버 루프에서 지킬 원칙

- 부분 송신과 부분 수신을 정상 상황으로 취급한다.
- 연결별 입력 버퍼에서 완성된 메시지만 파싱한다.
- 느린 클라이언트의 송신 큐에 상한을 두어 메모리 증가를 막는다.
- 연결 종료와 진행 중인 비동기 작업 사이의 수명 규칙을 정한다.
- I/O 스레드에서 오래 걸리는 게임 로직을 실행하지 않고 작업 큐로 넘긴다.

## 원문별 상세 정리

### 3. 소켓 프로그래밍

소켓은 애플리케이션이 운영체제의 네트워크 스택을 사용하는 통신 종단점이다. 서버는 일반적으로 소켓 생성, 주소 바인드, 수신 대기, 연결 수락의 순서로 준비하고 클라이언트는 대상 주소로 연결한다. 연결 뒤에는 송수신과 종료를 수행한다. 각 단계는 실패할 수 있으므로 오류 코드와 재시도 가능 여부를 구분해야 한다.

소켓 핸들은 커널 자원이므로 모든 종료 경로에서 닫아야 하며, 연결 종료는 정상 종료·타임아웃·프로토콜 오류·프로세스 장애처럼 원인이 다양하다. TCP와 UDP의 API 모양이 비슷해도 연결 상태와 전달 보장은 다르다. 네트워크 코드는 성공 경로보다 부분 처리, 상대 종료, 지연, 취소, 재연결 같은 경계 조건을 중심으로 설계한다.

### 3.1 블로킹 소켓

블로킹 소켓 호출은 즉시 완료할 수 없으면 호출 스레드를 대기시킨다. 코드는 위에서 아래로 읽히므로 연결 수가 적은 도구나 학습용 서버에는 이해하기 쉽다. 대기 중인 스레드는 보통 CPU를 사용하지 않지만 그 스레드의 스택과 관리 비용은 남고, 같은 스레드에 맡긴 다른 작업도 진행할 수 없다.

연결마다 스레드를 하나씩 두면 구현은 단순해도 수천 연결에서 메모리와 스케줄링 비용이 커진다. 블로킹 모델을 쓸 때도 제한된 워커 풀, 타임아웃, 취소 가능한 종료를 고려한다. 어떤 호출이 어느 조건에서 기다리는지와 서버 종료 시 대기를 어떻게 깨울지를 문서화하지 않으면 정상 종료가 교착처럼 멈출 수 있다.

### 3.2 네트워크 연결 및 송신

클라이언트의 `connect`는 이름 해석, 경로 선택, TCP 핸드셰이크를 거쳐 연결을 수립한다. 주소가 여러 개면 순차 또는 병렬 시도 정책이 필요하고, 연결 제한 시간과 취소를 지원해야 UI나 게임 루프가 멈추지 않는다. 연결 성공 후에도 인증과 프로토콜 버전 협상은 별개의 애플리케이션 단계다.

`send`는 요청한 바이트 전부보다 적게 보낼 수 있으므로 반환된 길이만큼 진행하고 남은 구간을 다시 보내야 한다. 0 또는 오류 반환, 인터럽트, 일시적 대기 상태를 구분한다. 여러 스레드가 같은 TCP 스트림에 동시에 쓰면 메시지 경계를 관리하기 어려우므로 연결별 송신 큐와 단일 직렬화 지점을 두는 편이 안전하다.

### 3.3 블로킹과 소켓 버퍼

송신 호출은 데이터를 운영체제 송신 버퍼에 복사한 뒤 반환될 수 있다. 상대가 느리거나 네트워크가 막혀 버퍼 여유가 사라지면 블로킹 송신은 공간이 생길 때까지 기다린다. 즉, 평소에는 즉시 반환되던 코드도 특정 클라이언트 상태에서 서버 스레드를 오래 묶을 수 있다.

버퍼 크기를 키우면 짧은 폭주는 흡수하지만 지속적인 생산·소비 속도 차이는 해결하지 못한다. 오히려 오래된 게임 상태가 큐에 쌓여 지연을 키울 수 있다. 최신 상태로 대체 가능한 메시지는 합치거나 버리고, 반드시 전달할 메시지는 상한과 타임아웃을 둔다. 애플리케이션 큐와 커널 버퍼를 모두 관찰해야 실제 백프레셔를 이해할 수 있다.

### 3.4 네트워크 연결받기 및 수신

서버는 수신 대기 소켓에 `listen`을 설정하고 `accept`로 연결된 새 소켓을 얻는다. 대기 큐가 가득 차거나 서버가 느리면 새 연결 수립이 지연되거나 실패할 수 있다. 수락 직후 원격 주소만 믿어 사용자를 인증하지 말고 애플리케이션 인증과 속도 제한을 거친다.

`recv`는 현재 도착한 만큼만 반환하므로 고정 헤더조차 여러 번에 나뉠 수 있다. 연결별 입력 버퍼에 데이터를 누적하고 헤더에서 검증된 길이를 얻은 뒤 완성된 메시지만 파서로 넘긴다. 0바이트 반환은 TCP 상대의 정상 송신 종료를 뜻할 수 있고, 오류와 구별해 정리 절차를 시작한다. 길이 값은 버퍼 할당 전에 상한을 검사한다.

### 3.5 수신 버퍼가 가득 차면 발생하는 현상

TCP 수신 애플리케이션이 데이터를 읽지 않으면 수신 창이 줄고 결국 송신 측에 더 보내지 말라는 흐름 제어가 전달된다. 송신 측 커널 버퍼와 애플리케이션 큐도 차오르면 송신 호출이 막히거나 대기 상태가 된다. 이 과정은 손실을 줄이지만 느린 소비자가 시스템 전체의 메모리와 작업을 붙잡는 문제를 만들 수 있다.

UDP는 연결별 흐름 제어와 재전송이 없으므로 수신 버퍼에 공간이 없으면 데이터그램이 버려질 수 있다. 애플리케이션은 드롭 수와 처리 시간을 관찰하고 패킷당 작업을 줄이거나 수신을 분산해야 한다. 어느 프로토콜이든 입력 속도가 처리 능력을 지속적으로 넘으면 버퍼 확대가 아니라 부하 제한과 메시지 우선순위가 필요하다.

### 3.6 논블록 소켓

논블로킹 모드에서는 지금 완료할 수 없는 호출이 즉시 “다시 시도” 상태를 반환한다. 호출이 실패한 것이 아니라 준비가 안 된 정상 상황이므로 오류와 분리해 처리한다. 단순 반복 호출로 준비 여부를 확인하면 CPU를 낭비하므로 `select`, `poll`, `epoll` 같은 준비 통지와 결합한다.

연결마다 읽기·쓰기 관심 상태와 버퍼 오프셋을 저장해야 하므로 제어 흐름이 상태 기계로 바뀐다. 송신 큐가 비었을 때 쓰기 이벤트를 계속 구독하면 항상 준비 상태라 바쁜 루프가 생길 수 있다. 데이터가 생길 때만 쓰기 관심을 켜고 모두 보낸 뒤 끈다. 연결 종료와 오류 이벤트가 읽기·쓰기 이벤트와 함께 올 수 있다는 점도 처리한다.

### 3.7 Overlapped I/O와 비동기 I/O

비동기 I/O는 작업을 제출한 호출이 완료를 기다리지 않고 반환하며, 나중에 콜백·이벤트·완료 큐 등으로 결과를 받는다. Windows의 Overlapped I/O에서는 작업별 상태 구조체와 버퍼가 완료 시점까지 살아 있어야 한다. 함수가 반환됐다고 스택 버퍼나 연결 객체를 파괴하면 사용 후 해제 오류가 된다.

동시에 여러 수신이나 송신을 제출할 때 완료 순서와 메시지 순서를 구분한다. 취소 요청도 이미 완료와 경쟁할 수 있으므로 “취소 호출 성공 = 완료 통지가 절대 오지 않음”이라고 가정하면 안 된다. 연결 객체에 진행 중 작업 수나 참조 수를 두고 모든 완료가 회수된 뒤 파괴하는 규칙을 만든다.

### 3.8 epoll

Linux의 `epoll`은 관심 파일 디스크립터를 커널에 등록하고 준비된 이벤트 집합을 가져온다. 많은 비활성 연결을 매번 전체 순회하지 않아도 된다는 장점이 있다. 레벨 트리거는 처리할 상태가 남아 있으면 다시 알려 주어 구현이 비교적 관대하고, 엣지 트리거는 상태 변화 중심으로 알려 호출 횟수를 줄일 수 있지만 완전히 비울 때까지 읽거나 쓸 책임이 커진다.

엣지 트리거에서는 `EAGAIN`이 나올 때까지 반복하지 않으면 남은 데이터에 대해 새 변화가 없어 다시 알림을 못 받을 수 있다. 이벤트 배열 크기, 한 연결이 한 루프를 독점하지 않게 하는 작업 예산, 파일 디스크립터 재사용 문제도 고려한다. 이벤트 루프에서 무거운 게임 로직을 직접 실행하지 말고 작업 큐로 넘겨 네트워크 진행을 보호한다.

### 3.9 IOCP

IOCP는 Windows에서 완료된 비동기 I/O 결과를 완료 포트 큐로 모으고 워커가 꺼내 처리하는 모델이다. 준비됐다는 알림 뒤 실제 I/O를 수행하는 `epoll`과 달리 제출한 작업의 완료 결과를 받는 관점이다. 제한된 워커로 많은 연결을 처리하고 동시 실행 스레드 수를 제어할 수 있다.

완료 패킷에는 연결 문맥, 작업 종류, 전송 바이트 수를 연결할 정보가 필요하다. 0바이트 완료, 부분 송신, 연결 끊김, 실패 완료를 각각 처리하고 작업 구조체를 정확히 한 번 회수한다. 서버 종료 시 새 작업 제출을 막고 소켓을 취소·종료한 뒤 남은 완료를 모두 배출하는 순서를 갖춰야 메모리 누수와 사용 후 해제를 피할 수 있다.

## 코드와 그림으로 확인하기

### TCP 서버의 기본 호출 순서

```text
서버: socket → bind → listen → accept → recv/send → close
클라이언트: socket → connect ────────────> send/recv → close
```

다음 코드는 POSIX 소켓의 흐름을 보여 주는 축약 예제다. 실제 서버에서는 모든 반환값, 인터럽트, 타임아웃과 종료 경로를 처리해야 한다.

```cpp
int listenSocket = socket(AF_INET, SOCK_STREAM, 0);
bind(listenSocket, reinterpret_cast<sockaddr*>(&address), sizeof(address));
listen(listenSocket, SOMAXCONN);

int clientSocket = accept(listenSocket, nullptr, nullptr);
std::array<char, 4096> buffer{};
const ssize_t received = recv(clientSocket, buffer.data(), buffer.size(), 0);

if (received > 0) {
    // received만큼 연결별 입력 버퍼에 추가한다.
} else if (received == 0) {
    // 상대가 정상적으로 송신 방향을 닫았다.
}
```

### 부분 송신 처리

`send`가 요청한 전체 길이를 처리한다고 가정하면 안 된다.

```cpp
bool SendAll(int socket, std::span<const std::byte> data) {
    std::size_t offset = 0;
    while (offset < data.size()) {
        const auto sent = send(
            socket,
            data.data() + offset,
            data.size() - offset,
            0);
        if (sent <= 0) return false;
        offset += static_cast<std::size_t>(sent);
    }
    return true;
}
```

블로킹 예제에서는 이해하기 쉽지만, 운영 서버에서는 느린 클라이언트 때문에 이 루프가 오래 멈출 수 있다. 논블로킹 방식은 남은 범위를 연결의 송신 큐에 저장하고 쓰기 가능 이벤트에서 이어서 보낸다.

### 논블로킹 `epoll` 읽기

```cpp
for (;;) {
    const auto received = recv(fd, buffer, sizeof(buffer), 0);
    if (received > 0) {
        AppendAndParse(fd, buffer, received);
        continue;
    }
    if (received == 0) {
        CloseConnection(fd);
        break;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        break; // 현재 읽을 데이터를 모두 소비했다.
    }
    CloseConnection(fd);
    break;
}
```

엣지 트리거에서는 `EAGAIN`이 나올 때까지 읽어야 다음 상태 변화 알림을 놓치지 않는다. 한 연결이 루프를 너무 오래 독점하지 않도록 바이트나 메시지 처리 예산도 둘 수 있다.

### 완료 기반 I/O 객체 수명

```text
I/O 요청 제출
   │
   ├─ 연결 객체와 버퍼의 참조 유지
   ▼
IOCP 완료 큐 ──> 워커가 결과 처리 ──> 진행 중 작업 수 감소
                                         │
연결 종료 요청 ── 새 요청 차단 ─────────┘
                                         ▼
                              완료가 모두 회수된 뒤 파괴
```

종료 요청과 완료 통지는 경쟁할 수 있으므로, 소켓을 닫았다는 이유만으로 비동기 작업 구조체를 즉시 삭제해서는 안 된다.
