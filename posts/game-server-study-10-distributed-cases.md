분산 시스템의 원칙은 실제 기능에 적용할 때 구체적인 선택이 된다. 어떤 상태를 공유하는지, 요청이 몰리는 지점이 어디인지, 실패 후 복구할 수 있는지를 기능별로 살펴봐야 한다. 이번 단원은 여러 사례를 통해 분산 경계를 판단하는 연습에 초점을 둔다.

## 로그온과 라우팅

로그온 서버는 인증 정보를 확인하고 사용자가 접속할 게임 서버를 선택한다. 인증 처리가 무상태에 가까우면 여러 인스턴스로 수평 확장하기 쉽다. 앞단 로드 밸런서는 연결을 분배하지만 그 자체의 장애와 확장도 고려해야 한다. 인증 후에는 짧은 수명의 자격 증명을 발급해 대상 서버가 다시 비밀번호를 다루지 않고 사용자를 확인하게 할 수 있다.

## 데이터베이스 샤딩

사용자 ID를 샤드 수로 나누는 단순 해시는 샤드 수가 변할 때 많은 레코드의 위치를 바꾼다. 일관된 해싱은 이동 범위를 줄일 수 있고, 별도 매핑 저장소는 사용자와 샤드의 관계를 직접 관리할 수 있다. 일관된 해싱은 계산 규칙과 재배치가 중요하고, 매핑 방식은 조회 의존성과 매핑 저장소의 가용성이 중요하다.

샤드 선택 정보는 로그인 과정에서 결정해 세션에 포함할 수 있다. 이후 요청이 항상 올바른 데이터 소유자에게 가도록 라우팅하고, 샤드 이동 중에는 구주소와 신주소가 동시에 쓰이지 않도록 전환 절차를 마련해야 한다.

## 로비, 배틀과 매치메이킹

대전 게임은 로비와 배틀 서버를 나누기 좋다. 로비는 파티와 매치 대기열을 관리하고, 배틀 서버는 한 경기의 실시간 상태를 담당한다. 경기가 끝나면 결과를 영속 저장소나 결과 처리 서비스에 기록한다. 로비 인스턴스가 여러 개라면 대기열을 어디에 둘지, 파티원이 다른 인스턴스에 있을 때 어떻게 만날지 정해야 한다.

매치 생성은 중복되면 안 되므로 매치 ID와 상태 전이를 멱등하게 관리한다. 배틀 서버 할당에 실패하거나 참가자가 접속하지 않을 때 예약을 해제하는 시간 제한도 필요하다.

## 월드 로직, NPC와 상호작용

NPC 전체를 별도 서버로 옮기면 이동과 전투 판단마다 월드 서버와 통신해야 해 응집도가 깨질 수 있다. 계산량이 큰 길찾기처럼 입력과 출력 경계가 분명한 작업만 분리하는 편이 나을 수 있다. 플레이어 간 거래나 전투도 같은 소유 서버 안에서는 단순하지만 서버 경계를 넘으면 조정과 실패 복구가 필요하다.

MMORPG는 지역 또는 채널 단위, 심리스 월드는 공간 분할과 경계 복제, FPS와 MOBA는 로비-배틀 인스턴스, 소셜 게임은 요청 처리 계층과 캐시·DB 계층 중심으로 분산하는 경우가 많다. 장르 이름만으로 구조를 고르지 말고 상호작용 범위와 세션 수명을 기준으로 판단해야 한다.

## 로그와 통계

게임 서버가 분석 DB에 직접 무거운 질의를 보내면 플레이 지연에 영향을 줄 수 있다. 서버는 구조화된 이벤트를 빠르게 기록하고, 별도 수집·큐·처리 계층이 저장과 집계를 담당하게 할 수 있다. 큐가 가득 찼을 때 버릴 수 있는 로그와 반드시 보존해야 하는 감사 로그를 구분한다.

## 원문별 상세 정리

### 10.1 로그온 처리의 분산

로그온은 연결 수립, 자격 증명 검증, 중복 로그인 확인, 사용자 데이터 위치 조회, 접속할 게임 서버 선택, 짧은 수명의 접속 자격 발급으로 나눌 수 있다. 인증 요청을 처리한 서버가 장기 세션 상태를 적게 가지면 로드 밸런서 뒤에 인스턴스를 늘리기 쉽다. 비밀번호는 전송 암호화와 안전한 해시 검증을 거치고 이후 서버 간 이동에는 재사용하지 않는다.

로드 밸런서도 용량과 장애 지점을 가지므로 상태 점검과 다중화가 필요하다. 로그인 폭주에서는 DB와 외부 인증 공급자가 먼저 한계에 닿을 수 있어 대기열, 속도 제한, 지수 백오프를 사용한다. 인증 성공 뒤 발급한 자격에는 사용자, 대상 서버, 만료, 일회성 값과 서명을 포함하고 대상 서버가 검증한 뒤 재사용을 막는다.

### 10.2 데이터베이스의 수평 확장

사용자 ID를 단순히 샤드 수로 나눈 방식은 빠르지만 샤드 수가 바뀌면 대부분의 매핑이 달라져 대량 이동이 발생한다. 일관된 해시는 노드를 링에 배치해 증설·축소 때 이동 범위를 줄이며 가상 노드로 분포를 조정한다. 그래도 인기 사용자의 핫키와 범위 질의, 실제 데이터 이동 절차는 별도로 해결해야 한다.

매핑 DB 방식은 사용자와 샤드의 관계를 명시적으로 저장해 일부 사용자만 옮기기 쉽다. 대신 매핑 조회의 지연과 가용성, 캐시 갱신이 새 문제가 된다. 로그인 단계에서 데이터 샤드를 결정하고 게임 서버에 서명된 자격으로 전달할 수 있다. 이동 중에는 쓰기를 잠시 막거나 변경 로그를 따라잡은 뒤 원자적으로 라우팅을 전환해 이중 쓰기와 손실을 방지한다.

### 10.3 매치메이킹의 분산 처리

로비는 파티, 대기열, 방 목록을 관리하고 배틀 서버는 하나의 경기를 권위 있게 실행한다. 배틀 인스턴스는 경기 단위로 독립적이어서 여러 서버에 분배하기 쉽다. 매치메이커는 지역과 실력, 파티 크기, 모드, 대기 시간을 고려해 그룹을 만들고 사용 가능한 배틀 서버를 예약한다.

로비를 여러 대로 늘리면 서로 다른 인스턴스의 대기자를 한 매치에 넣기 위한 공유 큐나 파티션 규칙이 필요하다. 같은 사용자가 두 로비에서 중복 대기하지 않게 상태 전이를 원자적으로 관리한다. 배틀 할당 뒤 참가자 접속 실패와 서버 시작 실패를 위한 예약 만료가 필요하며, 매치 ID를 멱등 키로 사용해 중복 경기가 생성되지 않게 한다.

### 10.4 몬스터 NPC 처리의 분산

몬스터 AI는 주변 플레이어 감지, 대상 선택, 이동, 길찾기, 공격과 피해 판정처럼 월드 상태와 자주 상호작용한다. 전체 AI를 별도 서버로 옮기면 매 판단마다 위치와 전투 상태를 동기화해야 하며 오래된 복제 데이터로 잘못된 결정을 내릴 수 있다. 응집도가 높은 로직을 분리해 네트워크 비용이 계산 이득보다 커지는 대표 사례다.

길찾기처럼 입력 지형과 시작·목표가 명확하고 결과 경로를 돌려주는 무거운 계산은 분리하기 쉽다. 요청에 월드 버전을 넣고 결과가 돌아왔을 때 장애물이나 목표가 바뀌었는지 검증한다. 시간 제한 뒤 간단한 로컬 이동이나 이전 경로를 사용하는 대체 동작을 둔다. 인기 지역의 요청 폭주를 위해 우선순위와 취소도 지원한다.

### 10.5 플레이어 간 상호작용 분산 처리

전투, 거래, 파티처럼 두 플레이어가 함께 상태를 바꾸는 기능은 같은 서버가 둘을 소유할 때 단순하다. 서로 다른 서버에 있으면 최신 상태 조회, 명령 순서, 부분 실패를 조정해야 한다. 그래서 상호작용이 잦은 플레이어를 같은 방·지역·파티 소유 서버에 배치하는 것이 중요한 분산 원칙이다.

경계를 넘는 거래가 꼭 필요하면 한 서비스가 거래 상태 기계를 소유하고 양쪽 자원을 예약한 뒤 확정하거나 취소한다. 메시지 중복과 지연에도 각 단계가 멱등해야 하며 만료 후 예약을 해제한다. 실시간 전투는 원격 왕복을 매 프레임 요구하지 않도록 세션 시작 때 참가자의 권한 있는 상태를 한 배틀 서버로 모으는 편이 일반적이다.

### 10.6 로그 및 통계 분석의 분산 처리

접속, 경기 시작·종료, 사망, 구매, 오류, 성능 지표를 운영 DB에 직접 무거운 형태로 쓰면 플레이 요청과 자원을 경쟁한다. 게임 서버는 구조화된 이벤트를 빠르게 수집 계층이나 큐로 보내고 별도 소비자가 저장·가공·집계를 수행하도록 분리할 수 있다. 이벤트에는 종류, 발생 시각, 서버와 세션, 스키마 버전, 추적 ID를 넣는다.

큐가 느려질 때 모든 로그를 같은 방식으로 취급하지 않는다. 디버그 통계는 샘플링하거나 버릴 수 있지만 결제·관리자 행동 감사 기록은 내구성 있게 보존해야 한다. 중복 전달을 예상해 이벤트 ID로 제거하거나 집계를 멱등하게 만든다. 이벤트 시간과 처리 시간을 구분하고 늦게 도착한 로그를 처리할 창을 둔다. 개인정보는 수집 목적과 보존 기간에 맞게 최소화한다.

### 10.7 게임 장르별 분산 서버 형태

MMORPG는 지역별로 월드를 나누고 경계 근처 객체를 복제하거나 이동 시 소유권을 넘길 수 있다. 채널 방식은 복제된 독립 월드로 나눠 단순하지만 채널 간 상호작용이 제한된다. 심리스 월드는 하나처럼 보이는 공간을 여러 서버가 처리해 경계 이동과 광역 이벤트, 인기 지역의 동적 부하 이동이 어렵다. NPC 로직 분리는 응집도를 해치지 않는 계산부터 제한적으로 적용한다.

FPS와 MOBA는 로비·매치메이킹과 독립된 배틀 인스턴스를 나누어 경기 단위로 수평 확장하기 좋다. 소셜 게임은 짧은 요청과 영속 데이터 비중이 높아 무상태 API 계층, 캐시, 샤딩 DB 구조가 잘 맞을 수 있다. 장르 이름만으로 설계를 복제하지 말고 세션 수명, 한 상태를 공유하는 최대 인원, 상호작용 빈도, 지연 예산, 장애 시 보존할 상태를 기준으로 경계를 선택한다.

    ├───────────>│────────────>│ 자격 확인  │            │            │

    │            │             │<──────────┤            │            │
    │            │             │ 샤드/서버 조회           │            │
    │            │             ├───────────────────────>│            │
    │ 주소+토큰   │             │<───────────────────────┤            │

로그온 서버는 비밀번호를 게임 서버에 전달하지 않는다. 대상 서버와 사용자, 만료, 일회성 값을 담아 서명한 자격을 발급하고 게임 서버가 이를 검증한다.

### 단순 해시와 일관된 해시

```cpp
std::size_t SimpleShard(PlayerId player, std::size_t shardCount) {
    return Hash(player) % shardCount;
}
```

이 방식은 샤드 수가 4에서 5로 바뀌면 많은 사용자의 결과가 달라진다. 일관된 해시는 해시 공간의 링에서 사용자 키 다음에 위치한 노드를 선택한다.

```text
                 [Shard A]
              /             \
        key 17                 key 63
          │                       │
      [Shard D]  ←── 해시 링 ──> [Shard B]
              \             /
                 [Shard C]
```

노드를 추가하면 링에서 새 노드가 담당하게 된 인접 범위만 이동한다. 실제 구현은 노드마다 여러 가상 노드를 두어 분포를 고르게 하고, 이동 중 읽기·쓰기 전환 절차를 별도로 마련한다.

### 명시적 매핑 DB

```sql
SELECT shard_id, mapping_version
FROM player_shard_mapping
WHERE player_id = :player_id;
```

매핑은 원하는 사용자만 옮기기 쉽지만 조회 경로가 하나 더 생긴다. 게임 서버는 매핑 버전을 세션에 저장하고, 이전 버전 요청이 들어오면 새 샤드로 재안내하거나 안전하게 실패시킨다.

### 매치메이킹 상태 기계

```text
Queued ── 조건 충족 ──> Reserving ── 배틀 서버 확보 ──> Ready
  ▲                         │                              │
  │                         ├─ 실패/만료 ──> Queued       ├─ 모두 접속 ─> Running
  │                         │                              └─ 접속 만료 ─> Cancelled
  └──────── 재등록 <────────┴───────────────────────────────────────────┘
```

상태 전이는 매치 ID와 버전을 조건으로 갱신해 두 로비가 같은 대기자를 동시에 확정하지 못하게 한다. 예약과 접속에는 만료 시간을 두어 실패한 배틀 서버가 자원을 영구히 점유하지 않게 한다.

### 길찾기 계산 분리

```cpp
struct PathRequest {
    RequestId requestId;
    WorldVersion worldVersion;
    Vec3 start;
    Vec3 destination;
};

void OnPathResult(const PathResult& result) {
    if (result.worldVersion != world.CurrentVersion())
        return; // 장애물이나 지형 상태가 바뀐 오래된 결과
    npc.SetPath(result.points);
}
```

NPC 전체 상태를 원격 서버에 나누기보다 입력과 출력이 명확한 비싼 길찾기 계산만 분리한다. 결과가 늦거나 실패하면 이전 경로 유지, 짧은 로컬 회피 같은 대체 동작을 사용할 수 있다.
