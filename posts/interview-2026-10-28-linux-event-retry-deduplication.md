## 오늘의 질문

에이전트가 서버에 이벤트를 전송한 직후 연결이 끊겨 응답을 받지 못했습니다. 서버가 저장했는지는 알 수 없습니다. 에이전트 재시작도 고려해 재시도, 중복 처리, 로컬 저장과 삭제 시점을 설계해 주세요.

## 핵심 해설

서버가 저장하지 못한 경우와 저장 후 응답만 사라진 경우를 클라이언트는 타임아웃만으로 구분할 수 없다. 재시도를 생략하면 유실될 수 있고 재시도하면 중복될 수 있다.

각 이벤트에 재시작 후에도 동일하게 유지할 ID를 부여한다. 장치 ID와 영속 시퀀스 또는 UUID 등 충돌 방지 규칙을 정한다. 재시도 시 ID를 새로 만들지 않는다. 같은 ID에 다른 내용이 오면 충돌 오류로 처리한다.

수집 → ID와 본문을 로컬 DB에 내구성 있게 커밋 → 전송 → 서버 커밋 확인 응답 → 로컬 삭제 순서로 처리한다. 로컬 커밋 전의 장애까지 유실을 막으려면 수집 원천의 재생 또는 확인 절차가 추가로 필요하다.

서버는 인증된 장치와 이벤트 ID에 유일 제약을 두고 중복 요청이 와도 같은 이벤트를 다시 기록하지 않게 한다. 중복 제거 기록과 이벤트 저장은 하나의 트랜잭션으로 묶는다. 서버는 커밋 후 이벤트별 성공 또는 이미 저장됨을 응답한다. 단순한 TCP 송신 성공을 저장 확인으로 사용하지 않는다.

응답을 잃으면 로컬 기록이 남아 재시작 후 같은 ID로 재전송한다. 서버는 기존 저장을 확인하고 다시 성공 응답을 준다. 응답 후 로컬 삭제 전 에이전트가 죽어도 같은 방식으로 복구한다.

적어도 한 번 전달 시도와 서버 멱등 처리의 조합이다. 외부 알림 등 별도 부수 효과에는 해당 처리도 멱등하게 하거나 transactional outbox 같은 연계 설계가 필요하다. 모든 시스템에 걸친 exactly-once를 자동 보장하지 않는다.

지수 백오프와 지터, 배치 내 이벤트별 확인, 재시도 가능한 오류 분류, 디스크 상한과 적체 정책을 설계한다. 중복 제거 ID 보관 기간은 재전송 가능 기간과 맞춘다. 영구 네트워크 단절이나 디스크 파괴까지 무조건 무유실을 보장할 수는 없으므로 장애 가정을 명시한다.

## 장애 테스트

전송 전, 서버 커밋 직전과 직후, 응답 직후와 로컬 삭제 직전에 프로세스를 종료한다. 재시작 후 이벤트 유실 여부와 ID별 서버 저장 건수, 적체 복구 시간을 확인한다.

## 면접용 모범 답변

서버 저장 후 응답만 유실될 수 있으므로 같은 ID로 재시도하고 서버에서 멱등하게 처리하겠습니다. 전송 전에 이벤트를 로컬 DB에 커밋하고 서버의 저장 완료 응답 후 삭제하겠습니다. 서버는 ID 유일 제약과 트랜잭션으로 중복 저장을 방지합니다. 재시작 시 미확인 이벤트를 재전송하고 장애 주입으로 유실과 중복을 검증하겠습니다.
