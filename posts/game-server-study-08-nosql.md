NoSQL은 관계형 데이터베이스를 무조건 대체하는 기술이 아니다. 데이터 구조, 조회 패턴, 일관성 요구, 확장 방식에 따라 다른 선택지를 제공한다. 게임 서버에서는 계정과 결제처럼 강한 일관성이 필요한 데이터와 로그·세션처럼 대량 확장이 중요한 데이터를 구분하는 것이 출발점이다.

## 관계형 모델과 문서 모델

관계형 DB는 명확한 스키마와 조인, 트랜잭션에 강점이 있다. 문서 DB는 관련 데이터를 하나의 문서에 모아 애플리케이션 객체와 비슷하게 다룰 수 있고 스키마 변화가 비교적 유연하다. 하지만 같은 정보를 여러 문서에 중복하면 갱신 시점과 일관성 규칙을 직접 관리해야 한다.

MongoDB의 데이터는 데이터베이스, 컬렉션, BSON 문서로 구성된다. JSON과 비슷하지만 추가 타입을 지원한다. 문서를 설계할 때는 정규화 여부보다 **함께 읽고 함께 바뀌는 데이터인가**를 먼저 본다. 배열이 무제한으로 커지거나 한 문서가 여러 서비스의 동시 갱신 지점이 되지 않도록 경계를 정해야 한다.

## CRUD와 성능 확인

생성, 조회, 수정, 삭제 연산에는 대상 조건과 결과 행 수를 명확히 둔다. 필요한 필드만 조회하면 네트워크와 역직렬화 비용을 줄일 수 있다. 인덱스는 조건과 정렬에 맞게 설계하고 설명 기능으로 전체 스캔 여부와 처리 문서 수를 확인한다. 인덱스를 많이 만들면 모든 쓰기가 여러 자료구조를 갱신해야 하므로 실제 질의를 기준으로 선택한다.

## 고가용성과 수평 확장

복제 세트는 여러 노드에 데이터를 복제해 일부 장애에서도 서비스를 이어갈 수 있게 한다. 장애 전환이 있어도 애플리케이션은 일시 오류와 재시도를 처리해야 한다. 읽기와 쓰기 우려 수준을 조정하면 지연, 내구성, 일관성 사이의 균형이 달라진다.

샤딩은 데이터를 여러 샤드에 분산한다. 샤드 키는 데이터 분포와 주요 질의를 함께 결정한다. 값이 한쪽으로 몰리거나 계속 증가하는 키는 특정 샤드에 쓰기를 집중시킬 수 있다. 라우터와 설정 서버도 운영상 중요한 구성 요소이므로 모니터링과 이중화 대상에 포함한다.

ACID와 BASE는 단순한 제품 분류가 아니라 요구 사항의 차이를 생각하는 도구다. 모든 데이터에 같은 일관성 수준을 적용하기보다 잃을 수 없는 상태, 잠시 늦게 맞아도 되는 상태, 다시 계산할 수 있는 상태를 나눈다.

## 원문별 상세 정리

### 8.1 관계형 데이터베이스와 NoSQL

NoSQL은 “SQL을 쓰지 않는 하나의 제품군”이 아니라 키값, 문서, 와이드 컬럼, 그래프 등 서로 다른 데이터 모델을 묶어 부르는 말이다. 관계형 DB는 명시적 스키마, 조인, 제약과 트랜잭션에 강하고, 문서 DB는 관련 데이터를 한 문서에 모아 애플리케이션 객체와 비슷하게 다루며 구조 변경을 유연하게 할 수 있다.

제품 선택은 유행보다 읽기·쓰기 패턴, 데이터 크기, 관계, 일관성, 운영 능력으로 결정한다. 계정과 결제는 강한 제약과 거래가 중요하고, 세션 캐시나 대량 이벤트는 다른 속성을 요구할 수 있다. 한 서비스에서 여러 저장소를 사용할 수 있지만 백업, 모니터링, 장애 대응, 개발 지식이 각각 필요해 운영 복잡성이 증가한다.

### 8.2 관계형 데이터베이스의 확장성

먼저 더 강한 CPU·메모리·스토리지로 수직 확장하고 질의와 인덱스를 최적화할 수 있다. 읽기 복제본은 조회 부하를 나누지만 복제 지연 때문에 최신 쓰기가 바로 보이지 않을 수 있다. 쓰기 부하가 한 노드 한계를 넘으면 사용자나 월드 기준으로 데이터를 나누는 샤딩을 검토한다.

샤딩은 각 샤드의 처리량을 늘리지만 샤드 간 조인과 트랜잭션, 유일 제약, 집계, 재분배를 어렵게 한다. 분할 키가 고르게 분포하고 주요 질의가 한 샤드에서 끝나는지 확인한다. 샤드 수 변경과 핫키 처리, 잘못된 라우팅 복구를 미리 설계하지 않으면 확장을 위해 도입한 구조가 운영 병목이 된다.

### 8.3 관계형 데이터베이스의 고가용성

고가용성은 복제본을 두는 것뿐 아니라 장애를 감지하고 새 주 노드를 선택하며 애플리케이션 연결을 복구하는 전체 과정이다. 동기 복제는 커밋 내구성을 높이지만 느린 복제본이 쓰기 지연에 영향을 줄 수 있고, 비동기 복제는 성능이 좋은 대신 장애 순간 아직 전달되지 않은 변경을 잃을 수 있다.

ACID는 트랜잭션의 원자성·일관성·격리성·지속성을 설명하고, BASE는 분산 환경에서 가용성과 최종 일관성을 우선하는 접근을 설명할 때 쓰인다. 실제 시스템은 둘 중 하나만 선택하기보다 데이터별 요구를 정한다. 재화는 강한 확정이 필요하지만 접속 상태나 추천 결과는 잠시 늦게 맞아도 될 수 있다. RPO와 RTO를 수치로 정하고 장애 전환을 연습한다.

### 8.4 MongoDB를 위한 JSON 이해

JSON은 객체, 배열, 문자열, 숫자, 불리언, null로 중첩 구조를 표현한다. MongoDB는 이를 확장한 BSON으로 날짜, ObjectId, 바이너리 등 추가 타입을 저장한다. 겉으로 JSON처럼 보여도 숫자 타입과 날짜 표현이 다를 수 있으므로 드라이버의 타입 변환을 확인한다.

문서 모델은 함께 읽고 바뀌는 데이터를 한 경계에 포함하는 것이 기본이다. 작은 장비 목록은 캐릭터 문서에 넣을 수 있지만 끝없이 커지는 전투 로그 배열은 별도 컬렉션이 낫다. 같은 값을 여러 문서에 중복하면 읽기는 쉬워져도 갱신과 복구 책임이 생긴다. 최대 문서 크기와 깊이, 필드 이름 검증도 입력 제한에 포함한다.

### 8.5 MongoDB 시작

개발 환경에서는 MongoDB 서버와 셸 또는 GUI 도구를 설치하고 로컬 인스턴스에 연결해 데이터베이스와 컬렉션을 만든다. 설치 자체보다 버전, 인증 활성화, 바인드 주소와 방화벽이 중요하다. 기본 설정 그대로 공용 네트워크에 노출하지 말고 최소 권한 계정을 사용한다.

운영은 단일 개발 인스턴스와 다르다. 복제 세트, 백업, 디스크 용량과 IOPS, 로그 순환, 인증서, 버전 업그레이드 절차를 준비한다. GUI 도구는 편리하지만 운영 데이터 수정 권한을 넓게 주지 않으며 변경을 감사한다. 설정과 초기 컬렉션·인덱스는 코드화해 환경마다 같은 방식으로 배포한다.

### 8.6 MongoDB 데이터 액세스

삽입은 문서를 만들고 컬렉션에 추가하며, 조회는 필터와 정렬, 투영으로 원하는 문서와 필드만 가져온다. `$gt`, `$or` 같은 연산자를 조합할 수 있지만 사용자 입력으로 임의 쿼리 구조를 만들지 않는다. 페이지 조회는 안정적인 정렬 키를 사용하고 반환 개수에 상한을 둔다.

수정에서는 `$set`, `$inc`, 배열 연산처럼 필요한 필드만 원자적으로 바꾸고 대상 조건에 현재 버전이나 잔액 조건을 포함할 수 있다. 삭제는 조건과 삭제 건수를 확인한다. `find` 후 별도 `update` 사이에는 다른 요청이 끼어들 수 있으므로 조건부 단일 연산이나 트랜잭션을 활용한다. 드라이버 결과의 매칭 수와 실제 변경 수를 구분해 검사한다.

### 8.7 성능 분석 기능

실행 계획 설명 기능으로 컬렉션 전체 스캔인지 인덱스 탐색인지, 몇 문서를 조사해 몇 개를 반환했는지 확인한다. 느린 쿼리 프로파일러는 실제 운영 패턴을 찾는 데 도움이 되지만 기록 자체의 부하와 민감 정보 노출을 관리해야 한다. 평균 시간보다 상위 지연과 빈도를 함께 봐야 총 비용이 큰 질의를 찾을 수 있다.

복합 인덱스는 필터와 정렬 순서에 맞춰 만들고 사용하지 않는 인덱스는 쓰기와 메모리 비용을 위해 제거한다. 인덱스 생성도 큰 컬렉션에서는 자원과 시간이 들므로 배포 계획이 필요하다. 데이터 분포가 바뀌면 과거에 좋았던 인덱스가 더 이상 유효하지 않을 수 있어 실행 계획과 캐시 적중, 작업 세트를 지속적으로 관찰한다.

### 8.8 MongoDB 수평 확장

샤딩된 MongoDB는 샤드에 데이터를 나누고 라우터가 질의를 적절한 샤드로 전달하며 설정 메타데이터가 분포 정보를 관리한다. 샤드 키가 질의에 포함되면 대상을 좁힐 수 있지만 없으면 여러 샤드에 질의를 뿌려 결과를 합쳐야 한다. 높은 카디널리티와 고른 분포, 주요 접근 패턴을 함께 고려한다.

계속 증가하는 시간이나 ID를 단순 범위 키로 쓰면 최신 쓰기가 한 샤드에 몰릴 수 있다. 해시 키는 분산에는 유리하지만 범위 조회가 여러 샤드로 퍼질 수 있다. 청크 이동과 밸런싱은 네트워크와 디스크를 사용하므로 피크 시간 영향도 본다. 샤딩은 인덱스와 스키마 설계를 대신하지 않는다.

### 8.9 게임 서버에서 MongoDB 명령 실행

애플리케이션은 드라이버 클라이언트를 만들고 데이터베이스와 컬렉션 핸들을 얻어 BSON 문서를 삽입·조회한다. 클라이언트는 내부 연결 풀을 관리하는 경우가 많으므로 요청마다 새로 만들지 않고 수명과 스레드 안전성 지침에 따라 재사용한다. 연결 문자열과 인증 정보는 설정과 비밀 저장소에서 주입한다.

네트워크 타임아웃, 서버 선택 타임아웃, 쓰기 우려 수준과 읽기 선호도를 명시한다. 게임 로직 스레드가 DB 완료를 기다리지 않게 비동기 API를 사용하고, 콜백에서 객체 수명을 보호한다. 삽입 성공 여부가 불확실할 때 같은 문서를 다시 넣어 중복되지 않도록 고유 거래 키나 결정적인 ID를 사용할 수 있다.

### 8.10 요약 및 더 알아보기

MongoDB를 배웠다고 모든 데이터를 문서로 옮길 필요는 없다. 관계와 강한 제약이 많은 데이터, 전체 문서로 함께 읽고 쓰는 데이터, 대량 로그처럼 추가 중심인 데이터를 구분해 저장소를 선택한다. 팀이 두 종류 DB를 운영할 능력과 장애 시 데이터 흐름을 추적할 도구도 기술 선택에 포함한다.

다음 단계로 복제 세트 장애 전환, 읽기·쓰기 우려 수준, 트랜잭션 범위, 백업과 시점 복구를 실습해야 한다. CAP를 단순 슬로건으로 외우기보다 실제 네트워크 분할에서 요청을 거부할지 오래된 값을 반환할지 기능별로 결정한다. 성능 시험은 현실적인 문서 크기와 인덱스, 동시성을 사용하고 장애 복구 시간까지 기록한다.

### 플레이어 문서 예시

```json
{
  "_id": "player-42",
  "profile": {
    "name": "Knight",
    "level": 18
  },
  "equipment": [
    { "slot": "weapon", "itemType": 1201, "enhance": 3 },
    { "slot": "armor", "itemType": 2304, "enhance": 1 }
  ],
  "version": 7
}
```

프로필과 소수의 장비는 함께 읽는 경계라 한 문서에 둘 수 있다. 반대로 전투 로그나 우편처럼 계속 증가하는 배열은 문서가 끝없이 커지므로 별도 컬렉션에 두는 편이 낫다.

### CRUD와 조건부 갱신

```javascript
db.players.find(
  { "profile.level": { $gte: 10 } },
  { "profile.name": 1, "profile.level": 1 }
).limit(100)

db.players.updateOne(
  { _id: "player-42", version: 7 },
  {
    $inc: { "profile.level": 1, version: 1 },
    $set: { lastLevelUpAt: new Date() }
  }
)
```

두 번째 갱신은 현재 버전이 7일 때만 적용된다. 매칭된 문서가 0개라면 다른 요청이 먼저 변경했을 수 있으므로 최신 상태를 읽고 충돌 정책을 적용한다.

### 실행 계획과 인덱스

```javascript
db.players.createIndex({ "profile.level": 1, "profile.name": 1 })

db.players.find({ "profile.level": { $gte: 10 } })
          .sort({ "profile.name": 1 })
          .explain("executionStats")
```

`totalDocsExamined`, `totalKeysExamined`, 반환 문서 수를 비교한다. 모든 질의에 인덱스를 추가하지 말고 빈도와 쓰기 비용, 메모리 사용을 함께 본다.

```text
                                      ├─> 샤드 A 복제 세트
                                      ├─> 샤드 B 복제 세트
                                      └─> 샤드 C 복제 세트
```

샤드 키가 없는 질의는 모든 샤드로 퍼질 수 있다. 계속 증가하는 값은 최신 쓰기를 한쪽에 몰 수 있고 해시 키는 범위 조회를 어렵게 하므로 실제 읽기·쓰기 패턴으로 선택한다.

### 드라이버 수명

```cpp
MongoClient client{connectionString}; // 애플리케이션 수명 동안 재사용
auto players = client.Database("game").Collection("players");

Document player;
player.Set("_id", playerId);
player.Set("version", 1);
co_await players.InsertOneAsync(player);
```

위 코드는 특정 드라이버 API를 복제한 것이 아니라 수명 구조를 나타내는 의사 코드다. 요청마다 클라이언트를 새로 만들지 말고 드라이버의 연결 풀을 재사용하며, 실제 API의 BSON 타입과 오류 모델을 따른다.

## 공부할 내용

1. 같은 플레이어 데이터를 관계형 테이블과 MongoDB 문서로 각각 모델링한다.
2. 대표 조회 세 가지를 정하고 인덱스 적용 전후의 실행 계획을 비교한다.
3. 복제 노드 하나를 중지해 장애 전환 동안 클라이언트가 보는 오류를 기록한다.
4. 여러 샤드 키 후보의 분포, 범위 조회, 재샤딩 비용을 표로 비교한다.
