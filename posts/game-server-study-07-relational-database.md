게임 서버의 메모리 상태는 빠르지만 프로세스가 종료되면 사라진다. 계정, 캐릭터, 재화, 아이템처럼 다음 접속에도 남아야 하는 데이터는 영속 저장소가 필요하다. 관계형 데이터베이스는 스키마, 제약 조건, 트랜잭션을 통해 데이터의 의미와 일관성을 표현한다.

## 데이터 모델링

플레이어 한 명에게 여러 캐릭터가 있고 캐릭터마다 여러 아이템이 있다면 계정, 캐릭터, 아이템을 별도 테이블로 나누고 키로 관계를 연결할 수 있다. 기본 키는 각 행을 유일하게 식별하고 외래 키는 테이블 사이의 참조 규칙을 표현한다. 정규화는 중복과 갱신 오류를 줄이지만, 읽기 경로가 복잡해질 수 있어 실제 조회 패턴과 함께 판단해야 한다.

문서 전체를 JSON이나 XML 한 필드에 저장하면 구조를 그대로 보존하기 쉽지만 일부 값만 검색하거나 제약을 적용하기 어렵다. 반대로 세분화된 테이블은 질의와 일관성 관리에 유리하지만 스키마 변경과 조인이 필요하다. 데이터의 변경 단위와 검색 요구를 기준으로 선택한다.

## SQL과 인덱스

CRUD는 생성, 조회, 수정, 삭제의 기본 연산이다. 조건 없는 수정이나 삭제는 큰 사고로 이어질 수 있으므로 트랜잭션, 영향 행 수 확인, 운영 권한 분리가 필요하다. 인덱스는 조회할 위치를 빠르게 찾게 하지만 저장 공간과 쓰기 비용을 추가한다. 자주 조회되는 조건과 정렬 순서를 기준으로 만들고 실행 계획으로 실제 사용 여부를 확인해야 한다.

## 트랜잭션과 동시성

아이템 구매처럼 재화 차감과 아이템 지급이 함께 성공해야 하는 작업은 하나의 트랜잭션으로 묶는다. 격리 수준이 높을수록 다른 트랜잭션의 중간 상태를 보기 어렵지만 대기와 충돌 가능성이 커질 수 있다. 서로 다른 순서로 행을 잠그면 데이터베이스에서도 데드락이 생길 수 있으므로 잠금 순서를 통일하고 트랜잭션을 짧게 유지한다.

게임 루프에서 동기 DB 호출을 기다리면 틱이 멈출 수 있다. 비동기 작업 큐로 분리하더라도 성공 전에 클라이언트에 확정 결과를 보여줄지, 실패 시 어떻게 보상할지 정해야 한다. 저장 프로시저나 서버 코드 중 어디에 로직을 둘지도 배포와 테스트 전략에 맞춰 결정한다.

## 보안과 오류 처리

사용자 입력을 문자열 연결로 SQL에 넣으면 인젝션 공격에 노출된다. 매개변수화된 질의를 사용하고 DB 계정에 필요한 최소 권한만 부여해야 한다. 비밀번호와 비밀 키를 소스 코드나 로그에 남기지 않고 별도 비밀 저장소에서 관리한다.

## 원문별 상세 정리

### 7.1 플레이어의 정보 저장

플레이어 정보는 계정, 캐릭터 능력치, 인벤토리, 퀘스트, 재화처럼 서비스가 재시작돼도 남아야 하는 영속 상태와 현재 위치, 전투 중 버프처럼 짧게 유지되는 세션 상태로 나눌 수 있다. 모든 값을 같은 주기와 방식으로 저장하면 중요 데이터의 내구성이 부족하거나 임시 데이터 때문에 DB 부하가 과도해진다.

데이터마다 진실의 원본, 허용 가능한 손실 범위, 저장 시점, 복구 방법을 정한다. 재화 거래는 즉시 트랜잭션으로 확정하고 감사 기록을 남기며, 재생성 가능한 값은 체크포인트나 주기 저장을 사용할 수 있다. 클라이언트 저장 파일은 표현 설정에는 적합하지만 경쟁과 경제에 영향을 주는 상태의 권위 있는 원본으로 삼지 않는다.

### 7.3 데이터베이스 사용

데이터베이스는 단순 파일 저장보다 동시 접근, 질의, 인덱스, 트랜잭션, 백업과 복구 기능을 제공한다. 관계형 DB는 테이블과 제약으로 구조와 관계를 명시하고 SQL로 다양한 조건을 조회한다. 문서·키값·그래프 DB는 다른 접근 패턴과 확장 특성을 제공하므로 이름보다 데이터와 질의의 요구를 먼저 본다.

게임 서버가 DB를 사용할 때는 연결 수, 질의 지연, 실패와 재시도, 스키마 버전을 관리해야 한다. 연결 풀은 생성 비용을 줄이지만 무제한 요청을 처리하지는 못한다. DB가 느려지면 풀 대기와 게임 서버 큐가 함께 증가하므로 상한과 타임아웃을 둔다. 백업이 존재하는 것뿐 아니라 실제 복원 시험이 성공해야 복구 전략이 완성된다.

### 7.4 데이터베이스 시작

관계형 DB를 시작할 때 인스턴스, 데이터베이스, 스키마, 테이블, 행과 열의 관계를 이해한다. 열에는 타입과 NULL 허용 여부, 기본값을 정의하고 테이블에는 기본 키와 제약을 둔다. 문자열 길이와 숫자 범위를 넉넉하게만 잡기보다 도메인 의미에 맞춰 정해야 잘못된 데이터가 저장되는 것을 줄일 수 있다.

개발 환경에서도 운영과 비슷한 문자 집합, 정렬 규칙, 시간대 설정을 사용한다. 날짜와 시간은 기준 시간대와 정밀도를 명확히 하고, 사용자에게 보여 줄 지역 시간과 저장 시간을 분리한다. 스키마 변경은 수동으로 기억하지 말고 버전 관리되는 마이그레이션으로 적용하며, 이전 애플리케이션 버전과 함께 동작할 전환 순서를 계획한다.

### 7.5 SQL 질의 구문

CRUD는 `INSERT`, `SELECT`, `UPDATE`, `DELETE`로 표현되며 실제 서비스에서는 조건과 영향 범위가 핵심이다. 조회는 필요한 열과 행만 요청하고, 정렬과 페이지 방식도 인덱스와 함께 설계한다. 운영 데이터에서 조건 없는 수정·삭제는 치명적이므로 트랜잭션 안에서 예상 행 수를 확인하고 권한과 도구로 방지한다.

여러 테이블을 조인할 때 논리적으로 맞는 결과뿐 아니라 데이터가 커졌을 때 실행 비용을 본다. 오프셋 기반 페이지는 뒤로 갈수록 많은 행을 건너뛸 수 있어 안정적인 키 기준 페이지가 유리할 수 있다. 애플리케이션은 “행이 없음”, “중복 키”, “제약 위반”, “일시 오류”를 구분해 사용자 결과와 재시도 정책을 결정한다.

### 7.6 인덱스와 키

기본 키는 행을 유일하게 식별하고, 외래 키는 테이블 사이 참조 무결성을 지킨다. 일반 인덱스는 검색과 정렬을 빠르게 하지만 유일성을 의미하지 않을 수 있다. 복합 인덱스는 열 순서가 중요하며 대표 질의의 조건, 범위, 정렬 방식에 맞춰 설계한다.

인덱스가 많으면 디스크와 메모리를 사용하고 삽입·수정·삭제마다 갱신 비용이 든다. 추측으로 추가하지 말고 실제 느린 질의와 실행 계획에서 스캔 행 수, 선택도, 정렬 비용을 확인한다. 낮은 선택도의 단일 열 인덱스가 도움이 되지 않을 수 있고, 함수나 암시적 타입 변환 때문에 인덱스를 못 쓰는 경우도 있다. 추가 후 쓰기 부하까지 비교한다.

### 7.7 플레이어 정보를 저장하는 방법 1

플레이어 객체를 JSON이나 XML 같은 하나의 문서로 직렬화해 열에 저장하면 애플리케이션 구조를 빠르게 보존하고 한 번에 읽고 쓰기 쉽다. 스키마 초기 개발과 전체 캐릭터 단위 로드에는 편리하지만 내부 필드별 검색, 제약, 부분 갱신과 인덱싱이 어려워진다. 작은 변경도 큰 문서를 다시 쓸 수 있다.

문서 버전과 마이그레이션 규칙이 없으면 클래스 구조 변경 뒤 오래된 데이터를 읽지 못한다. 동시에 두 서버가 같은 문서를 수정하면 서로의 필드를 덮어쓸 수 있어 버전 기반 갱신이 필요하다. 이 방식은 “항상 함께 읽고 쓰는 작은 덩어리”에 제한하고 거래·랭킹처럼 검색과 일관성이 중요한 값은 별도 구조로 두는 혼합 모델을 고려한다.

### 7.8 플레이어 정보를 저장하는 방법 2

정규화된 테이블 방식에서는 계정, 캐릭터, 아이템, 퀘스트 등을 관계에 맞춰 나눈다. 중복을 줄이고 외래 키와 유일 제약으로 규칙을 DB가 지킬 수 있으며 특정 아이템이나 조건을 효율적으로 조회할 수 있다. 대신 캐릭터 전체를 읽을 때 여러 질의나 조인이 필요하고 스키마 변경 절차가 늘어난다.

정규화 수준은 이론적 최대치보다 실제 변경 단위와 질의 패턴에 맞춘다. 읽기 성능을 위해 일부 값을 중복할 수 있지만 어느 값이 원본인지와 갱신 실패 시 복구 방법을 명시한다. 인벤토리 슬롯 같은 관계에는 `(character_id, slot)` 유일 제약을 두어 애플리케이션 버그가 중복 상태를 만들지 못하게 하는 식으로 도메인 규칙을 스키마에 반영한다.

### 7.9 질의 구문 실행

질의가 제출되면 DB는 구문을 분석하고 실행 계획을 선택해 인덱스 탐색, 테이블 스캔, 조인과 정렬을 수행한다. 같은 SQL도 통계와 매개변수, 데이터 분포에 따라 다른 계획을 사용할 수 있다. 느린 질의는 문장 길이가 아니라 읽은 행 수, 잠금 대기, 디스크 I/O, 반환 데이터량으로 분석한다.

트랜잭션은 여러 변경을 하나의 원자적 단위로 묶는다. 격리 수준은 다른 트랜잭션의 미완료 또는 변경된 데이터를 얼마나 볼 수 있는지를 결정하며, 높은 격리는 충돌과 대기를 늘릴 수 있다. 두 거래가 서로 다른 순서로 행을 잠그면 데드락이 발생할 수 있으므로 접근 순서를 통일하고 트랜잭션 안의 외부 호출과 사용자 대기를 피한다.

### 7.10 게임 서버에서 질의 구문 실행

게임 서버는 DB 드라이버와 연결 풀을 통해 매개변수화된 질의를 실행한다. 게임 틱이나 네트워크 콜백 스레드에서 동기 질의를 기다리면 한 사용자의 DB 지연이 다른 사용자에게 전파될 수 있다. 비동기 작업으로 분리하고 완료 결과를 원래 상태 소유자에게 메시지로 돌려보낸다.

비동기화하면 요청 시점과 완료 시점의 게임 상태가 다를 수 있다. 작업에 사용자와 세션의 세대, 기대 버전, 거래 ID를 담고 늦은 결과가 새 세션을 덮지 않게 한다. 일시적인 연결 오류는 제한적으로 재시도할 수 있지만 이미 커밋됐는지 불명확한 변경은 멱등 키로 확인한다. 연결 풀 고갈과 질의 타임아웃을 지표로 노출한다.

### 7.11 보안을 위한 주의 사항

사용자 입력을 문자열로 연결해 SQL을 만들면 인젝션 공격이 가능하다. 값은 항상 매개변수로 전달하고, 테이블명이나 정렬 열처럼 매개변수화할 수 없는 구조 요소는 허용 목록에서 선택한다. 입력 검증은 사용자 경험과 도메인 보호에 필요하지만 매개변수화의 대체물이 아니다.

게임 서버 DB 계정에는 필요한 테이블과 작업만 허용하고 관리 권한을 주지 않는다. 비밀번호와 연결 문자열은 비밀 저장소에서 주입하고 로그와 오류 응답에 노출하지 않는다. 전송 암호화, 저장 데이터 암호화, 백업 접근 제어를 적용하며 개인정보 보존·삭제 정책을 지킨다. 감사 로그에는 누가 언제 어떤 중요 변경을 했는지 남기되 민감한 원문 값은 최소화한다.

## 코드와 그림으로 확인하기

### 계정·캐릭터·아이템 관계

```sql
CREATE TABLE characters (
    character_id BIGINT PRIMARY KEY,
    account_id   BIGINT NOT NULL,
    name         VARCHAR(32) NOT NULL UNIQUE,
    gold         BIGINT NOT NULL CHECK (gold >= 0)
);

CREATE TABLE inventory_items (
    item_instance_id BIGINT PRIMARY KEY,
    character_id     BIGINT NOT NULL,
    slot              INT NOT NULL,
    item_type_id      INT NOT NULL,
    quantity          INT NOT NULL CHECK (quantity > 0),
    UNIQUE (character_id, slot),
    FOREIGN KEY (character_id) REFERENCES characters(character_id)
);
```

기본 키는 행을 식별하고 외래 키는 존재하지 않는 캐릭터의 아이템이 생기는 것을 막는다. 슬롯 유일 제약은 애플리케이션 버그가 같은 슬롯에 두 아이템을 저장하지 못하게 한다.

### 재화 차감과 아이템 지급 트랜잭션

```sql
UPDATE characters
SET gold = gold - :price
WHERE character_id = :character_id
  AND gold >= :price;

INSERT INTO inventory_items
    (item_instance_id, character_id, slot, item_type_id, quantity)
VALUES
    (:instance_id, :character_id, :slot, :item_type_id, 1);

COMMIT;
```

골드가 부족해 UPDATE된 행이 없다면 INSERT하지 않고 롤백한다. 실제 구현은 거래 ID의 유일 제약도 두어 응답 유실 뒤 같은 요청이 다시 와도 중복 지급되지 않게 한다.

### 실행 계획으로 인덱스 확인

```sql
CREATE INDEX idx_inventory_character_type
ON inventory_items (character_id, item_type_id);

EXPLAIN
SELECT item_instance_id, quantity
FROM inventory_items
WHERE character_id = :character_id
  AND item_type_id = :item_type_id;
```

인덱스를 만들었다는 사실보다 실행 계획에서 조사 행 수가 실제로 줄었는지 확인하는 것이 중요하다. 대표 데이터량과 분포로 읽기 성능뿐 아니라 아이템 추가·변경의 쓰기 비용도 함께 측정한다.

### 매개변수화된 질의

```cpp
auto statement = connection.Prepare(
    "SELECT character_id, gold "
    "FROM characters WHERE name = ?");
statement.Bind(1, requestedName);
auto rows = statement.ExecuteQuery();
```

`requestedName`을 SQL 문자열에 이어 붙이지 않는다. 값은 매개변수로 보내고, 정렬 열이나 테이블처럼 구조를 동적으로 선택해야 한다면 서버가 정의한 허용 목록을 사용한다.

### 게임 스레드와 DB 작업 큐

```text
게임 스레드 ── SaveCommand(version=42) ──> DB 워커
     ▲                                         │
     └── SaveResult(version=42, success) <─────┘
```

완료 결과가 돌아왔을 때 현재 캐릭터 버전과 세션 세대를 확인한다. 오래된 저장 결과가 새로운 상태를 확정한 것처럼 처리되지 않게 해야 한다.

## 공부할 내용

1. 계정-캐릭터-아이템 관계를 ER 다이어그램으로 그리고 키와 제약을 정의한다.
2. 캐릭터 생성과 아이템 거래를 트랜잭션으로 구현해 중간 실패를 시험한다.
3. 조회 전후의 실행 계획을 비교해 인덱스의 효과와 쓰기 비용을 측정한다.
4. 매개변수화된 질의와 문자열 연결 질의의 보안 차이를 작은 예제로 확인한다.
