매일 면접 질문 하나와 정답, 핵심 해설을 정리한다. [지난 글](?post=interview-2026-10-20-input-replay-reconciliation)에서 배운 입력 재실행을 복습하고, 입력 기록의 삭제 기준을 확인한다.

## 오늘의 질문

캐릭터가 직선 위를 이동한다. 각 입력은 위치에 이동량을 더하며, 충돌과 가속도는 없다.

| 입력 번호 | 이동량 |
| --- | ---: |
| 201 | +3 |
| 202 | +2 |
| 203 | −1 |

클라이언트가 모두 예측 실행한 뒤, 서버에서 **“201번까지 처리한 위치는 20”**이라는 보정이 도착했다. 이 확인은 201번까지의 입력이 모두 처리됐다는 의미다. 202·203번은 아직 확인되지 않았다.

1. 어떤 입력을 다시 적용해야 하며, 보정된 현재 위치는 얼마인가?
2. 재실행한 202·203번 기록을 바로 삭제해도 되는가?
3. 입력 재실행과 시각적 스무딩은 각각 무엇을 해결하는가?

## 핵심 해설

### 1. 보정된 현재 위치는 21이다

서버가 확인한 위치 20에서 미확인 입력 202·203번을 순서대로 재실행한다.

```text
201번까지 처리한 서버 위치:     20
202번 재실행:          20 + 2 = 22
203번 재실행:          22 − 1 = 21
```

201번은 서버 상태 20에 이미 반영됐으므로 다시 적용하지 않는다. 재실행은 기존 클라이언트 위치가 아니라 서버가 확인한 상태에서 시작한다.

### 2. 입력 기록은 서버 확인 후 삭제한다

202·203번 기록은 재실행 후에도 보관한다. **클라이언트에서 실행했다는 사실과 서버가 처리를 확인했다는 사실은 다르다.**

다음 서버 보정에서도 미확인 입력을 재실행해야 할 수 있다. 손실 복구를 위해 미확인 입력을 재전송하는 프로토콜이라면 그 기록도 필요하다. 입력 순서를 확인하기 위해서만 남기는 것이 아니라, 아직 확인되지 않은 입력을 다시 사용할 수 있어야 하기 때문에 보관한다.

| 서버가 누적 확인한 입력 | 대기 목록에서 삭제 | 계속 보관 |
| --- | --- | --- |
| 201번까지 | 201번까지 | 202·203번 |
| 202번까지 | 202번까지 | 203번 |
| 203번까지 | 203번까지 | 이후 미확인 입력이 있다면 해당 입력 |

별도 디버깅 기록은 보관할 수 있지만, 여기서 말하는 삭제는 재전송·재실행을 위한 대기 입력 목록에서 제거한다는 의미다.

### 3. 상태 재조정과 시각적 스무딩은 역할이 다르다

입력 재실행은 **서버가 확인한 과거 상태를 기준으로 현재 시뮬레이션 상태를 다시 계산**한다. 이 예제의 결과는 21이다.

시각적 스무딩은 그 보정 결과로 생기는 **화면상의 갑작스러운 위치 변화를 완화**한다. 올바른 현재 상태를 계산하는 과정과 그 상태를 부드럽게 보여주는 과정을 구분해야 한다.

단순히 과거 서버 위치 20으로 Lerp하면 202·203번의 결과가 빠진다. 따라서 스무딩만으로 입력 재실행을 대체할 수 없다.

실제 이동에서는 위치뿐 아니라 속도, 이동 모드 등 재실행에 필요한 상태도 복원해야 한다. 이 문제는 이동량만 더하는 단순한 모델이며, Unreal의 실제 메시지 형식과 동일하지 않다.
