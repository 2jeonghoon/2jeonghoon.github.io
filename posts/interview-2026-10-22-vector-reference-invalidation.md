매일 면접 질문 하나와 정답, 핵심 해설을 정리한다. 오늘은 vector에 저장한 게임 객체의 주소를 오래 보관할 때 생기는 문제를 다룬다.

## 오늘의 질문

```cpp
struct Player {
    int id;
    int hp;
};

std::vector<Player> players;
players.reserve(2);
players.push_back({1, 100});
players.push_back({2, 100});

Player* target = &players[0];
players.reserve(players.capacity() + 1);
target->hp -= 10;
```

1. 마지막 줄은 안전한가? reserve 호출 전후에 어떤 일이 일어나는가?
2. 처음부터 reserve(1000)을 호출하면 해결되는가?
3. 추가·삭제가 잦고 다른 시스템에서도 특정 플레이어를 계속 참조해야 한다면 어떤 방식을 선택할 수 있는가?

## 핵심 해설

### 1. 재할당 후 기존 주소는 사용할 수 없다

두 번째 reserve는 현재 capacity보다 큰 값을 요청하므로 정상적으로 완료되면 재할당이 발생한다. 원소가 새 저장 공간으로 옮겨지고 기존 저장 공간은 해제된다. size는 그대로다.

기존 원소의 포인터·참조·반복자는 무효화된다. target은 이전 주소를 보관한 댕글링 포인터이므로 이를 역참조하는 마지막 줄은 정의되지 않은 동작이다. 크래시 없이 실행되는 것처럼 보여도 안전하지 않다.

이 예제에서는 재할당 후 target을 &players[0]으로 다시 얻을 수 있다. 다만 이후 삽입·삭제에서도 유효성을 다시 고려해야 한다.

### 2. reserve는 수명을 보장하지 않는다

포인터를 얻기 전에 충분한 용량을 확보하면 끝에 원소를 추가할 때 발생하는 재할당을 줄일 수 있다. 하지만 capacity를 넘으면 다시 재할당된다.

중간 삽입·삭제는 전체 재할당이 없어도 원소를 옮긴다. 따라서 재할당 여부와 함께 변경 위치도 확인해야 한다.

| 연산 | 기존 원소에 대한 참조의 보장 |
| --- | --- |
| 재할당 발생 | 모든 원소의 포인터·참조·반복자 무효화 |
| 재할당 없는 중간 삽입 | 삽입 위치 앞은 유지, 해당 위치부터 뒤는 무효화 |
| 중간 삭제 | 삭제 위치 앞은 유지, 해당 위치부터 뒤의 참조·반복자 무효화 |
| 재할당 없는 끝 추가 | 기존 원소의 포인터·참조·반복자 유지, 기존 end 반복자는 무효화 |

### 3. 왜 중간에서 삭제하면 뒤쪽이 영향을 받을까?

vector는 원소를 연속으로 저장한다. 중간 원소를 삭제하면 빈자리를 메우기 위해 뒤쪽 원소를 앞으로 당긴다.

아래 숫자는 실제 Player의 크기와 무관한 설명용 주소다.

```text
주소       100   104   108   112
삭제 전     A     B     C     D
B 삭제 후   A     C     D    [끝]
```

기존 C를 가리키던 포인터는 주소 108을 저장한다. 포인터는 C의 새 위치 104를 자동으로 따라가지 않는다. 일반적인 이동 대입 구현에서는 108의 살아 있는 객체가 이제 D의 값을 가질 수 있고, 마지막 112 위치의 객체는 파괴된다.

여기서 두 문제를 구분해야 한다. 재할당처럼 메모리가 해제된 경우에는 댕글링 포인터가 된다. 반면 중간 삭제에서는 같은 주소에 살아 있는 객체가 남아 있어도, 원래 플레이어를 가리킨다는 의미가 깨질 수 있다. 무효화된 참조를 이용해 기존 원소를 계속 추적해서는 안 된다.

중간 삽입도 빈자리를 만들기 위해 뒤쪽 원소를 오른쪽으로 밀기 때문에 비슷한 문제가 생긴다. 변경 위치 앞의 원소는 재할당이 없으면 영향을 받지 않는다.

### 4. 외부 참조에는 슬롯과 세대 번호를 가진 핸들을 고려한다

```cpp
struct PlayerHandle {
    uint32_t slot;
    uint32_t generation;
};
```

다른 시스템은 주소 대신 핸들을 보관한다. 저장소는 조회 시 슬롯의 사용 여부와 세대 번호를 검사한다. 플레이어 삭제 시 세대 번호를 바꾸면 같은 슬롯에 새 플레이어가 들어와도 오래된 핸들을 거부할 수 있다.

객체가 이동한다면 슬롯에서 실제 위치로 연결하는 정보도 갱신해야 한다. 조회한 원시 포인터를 장기간 보관하면 다시 같은 문제가 생긴다. 실제 구현에서는 검증 비용, 세대 번호 순환과 동시 접근 정책도 고려한다.
