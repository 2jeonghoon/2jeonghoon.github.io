## 오늘의 질문

서버 권한 기반 게임에서 클라이언트 예측, 서버 보정, 보간은 어떤 역할을 할까?

Unreal 기반 대전 게임에서 클라이언트는 입력 즉시 자신의 캐릭터를 움직이고 서버에 이동 입력을 전송한다. 서버는 이동의 최종 권한을 가진다.

왕복 지연 120ms, 패킷 손실 2% 환경에서 자신의 캐릭터가 간헐적으로 뒤로 튕기고, 다른 플레이어의 이동도 끊겨 보인다.

1. 자신의 캐릭터가 뒤로 튕기는 이유는 무엇인가?
2. 자신과 다른 플레이어의 이동을 각각 어떻게 부드럽게 만들 수 있는가?
3. 모든 이동 메시지를 Reliable로 보내면 해결될까? 어떤 지표로 진단해야 할까?

## 핵심 해설

### 1. 서버 보정은 같은 시점의 상태를 기준으로 한다

클라이언트는 서버 응답을 기다리지 않고 입력을 예측 실행한다. 서버는 전달받은 입력을 처리하고, 클라이언트와 상태가 어긋나면 보정 정보를 보낸다.

서버 응답은 과거 입력을 처리한 결과이므로 클라이언트의 현재 위치에 그대로 덮어쓰면 안 된다. 서버가 확인한 입력 시점의 상태로 보정하고, **그 이후 아직 서버가 확인하지 않은 입력을 순서대로 재실행**해야 한다. 이것이 서버 재조정(reconciliation)의 핵심이다.

지연 자체가 반드시 예측 오차를 만드는 것은 아니다. 이동 속도, 충돌 판정, 이동 모드, 입력 처리의 차이도 원인이 될 수 있다. 보정이 올바르더라도 오차가 크거나 시각적 처리가 부족하면 뒤로 튕기는 현상이 보일 수 있다.

### 2. 자기 캐릭터와 다른 플레이어는 처리 방식이 다르다

자기 캐릭터는 입력 반응성이 중요하므로 **예측 → 서버 보정 → 미확인 입력 재실행** 흐름을 사용한다. 충돌 등 게임 판정에 사용하는 상태를 맞추면서 화면에 보이는 메시와 카메라에는 필요한 스무딩을 적용할 수 있다.

다른 플레이어는 일반적인 스냅샷 방식에서 수신 상태를 잠시 버퍼에 저장하고, 약간 과거 시점을 보간해 표시할 수 있다. 표시 지연을 조금 늘려 불규칙한 수신 간격을 흡수하는 방식이다. 버퍼가 비면 제한적인 외삽이나 대기 정책이 필요하다.

Unreal CharacterMovementComponent의 원격 캐릭터는 복제된 이동 상태와 네트워크 스무딩을 활용한다. 일반적인 스냅샷 보간 설계를 엔진의 기본 구현과 동일한 것으로 단정하지 말고, 현재 프로젝트의 이동 경로와 설정을 확인해야 한다.

따라서 “모든 위치를 Lerp하면 해결된다”는 답은 부족하다. 시뮬레이션 상태의 일치와 화면에 보이는 움직임의 부드러움을 구분해야 한다.

### 3. Reliable은 이동 지연을 키울 수 있다

Reliable 전송은 재전송과 순서 보장에 비용이 든다. 같은 순서 보장 범위에서 손실된 메시지를 기다리느라 뒤의 최신 메시지 처리가 밀릴 수 있다. 모든 네트워크 트래픽이 일괄적으로 멈춘다는 의미는 아니다.

이동 입력을 Unreliable로 보낼 때도 손실 대책은 필요하다. 입력 순번, 확인 응답, 미확인 입력의 중복 전송과 중복 처리 방지 등을 활용할 수 있다. 최신 위치 스냅샷은 오래된 것을 버릴 수 있지만, 이동 입력은 누락에 대한 별도의 복구가 필요하다.

[Epic의 CharacterMovementComponent 설명](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine?lang=en-US)에 따르면 저장된 이동을 기록하고 확인되지 않은 이동을 다시 보내며, 서버 보정 후 남은 이동을 재실행한다. 이동 RPC는 Unreliable을 사용한다. 빈번한 이동을 Reliable로 보내면 Reliable 버퍼가 넘칠 위험도 있다.

## 진단할 지표

| 지표 | 확인할 내용 |
| --- | --- |
| RTT·지터·패킷 손실률 | 평균뿐 아니라 튕김이 발생한 순간의 지연 변화와 연속 손실 |
| 서버 보정 횟수·보정 거리 | 특정 이동 모드, 충돌, 속도 변경에서 오차가 반복되는지 |
| 이동 업데이트 수신 간격 | 전송 주기 대비 긴 공백과 수신 간격의 변동 |
| 서버 틱 시간·처리 지연 | 서버 부하와 보정·수신 공백이 함께 증가하는지 |
| 보간 버퍼 부족 횟수 | 끊김이 버퍼 고갈과 겹치는지 |

지표는 동일한 타임라인에 기록해 증상과 비교한다. 지연·손실이 없는 환경에서도 재현되는지 먼저 확인한 뒤 지연, 지터, 손실 조건을 나누어 재현하면 원인을 좁히기 쉽다.

[Unreal Networking Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-insights-in-unreal-engine)에서는 패킷 타이밍·크기와 RPC 내용을 분석할 수 있다. 보정 거리와 입력 번호 등 프로젝트 고유 정보는 별도 로그나 추적으로 함께 남긴다.
