멀티플레이 게임에서 서버의 핵심 역할은 여러 클라이언트가 공유하는 세계에 대해 신뢰할 수 있는 판정을 내리는 것이다. 모든 연산을 서버로 옮기면 안전하지만 지연과 비용이 커지고, 모든 연산을 클라이언트에 맡기면 조작과 불일치에 취약해진다. 현실적인 설계는 권한과 표현을 분리한다.

## 서버 권한과 클라이언트 표현

클라이언트는 입력을 받고 화면과 소리를 즉시 표현한다. 서버는 이동 가능 여부, 피해량, 아이템 소유권처럼 게임 결과에 영향을 주는 상태를 검증한다. 클라이언트가 예측한 결과와 서버 판정이 다르면 보정한다. 이 구조에서는 무엇이 최종 권한을 가지는지 메시지마다 명확해야 한다.

클라이언트와 서버의 상호작용은 연결, 요청과 응답, 서버의 능동 통보, 연결 종료로 나눠 볼 수 있다. 요청 식별자와 오류 규칙을 정하면 재시도와 중복 처리가 쉬워진다. 서버 알림은 상대가 이미 연결을 잃었거나 이전 상태를 보고 있을 가능성까지 고려해야 한다.

## 좋은 게임 서버의 품질

- 안정성: 일부 입력이나 컴포넌트 실패가 전체 프로세스 장애로 번지지 않아야 한다.
- 확장성: 사용자와 콘텐츠가 늘 때 병목을 찾아 자원을 늘리거나 역할을 분리할 수 있어야 한다.
- 성능: 평균값뿐 아니라 상위 지연 시간과 프레임별 처리 예산을 함께 관찰해야 한다.
- 운영성: 로그, 지표, 설정 변경, 배포, 복구 절차가 서비스 중에도 동작해야 한다.

플레이어의 영구 상태는 일반적으로 서버 측 데이터베이스에 둔다. 트랜잭션은 함께 성공하거나 실패해야 하는 변경을 묶고, 인덱스는 조회 속도를 높이며, 백업과 복제는 장애 후 복구 가능성을 높인다. 클라이언트에는 UI 설정처럼 조작돼도 게임 경제에 영향을 주지 않는 값만 맡기는 편이 안전하다.

## 구동 환경 선택

온프레미스는 하드웨어와 네트워크를 세밀하게 통제할 수 있지만 구매와 운영 부담이 크다. 클라우드는 빠른 증설과 관리형 서비스를 제공하지만 비용 구조와 제공자 의존성을 고려해야 한다. IaaS, PaaS, SaaS로 갈수록 관리 범위는 줄고 제어 범위도 작아진다. 게임의 트래픽 변화, 지역, 규제, 팀 역량을 기준으로 선택해야 한다.

## 원문별 상세 정리

### 4.1 패키지 게임에서 게임 서버

패키지 게임은 실행 파일과 주요 로직이 사용자의 기기에 설치되며, 전통적으로 혼자 실행하거나 한 기기가 호스트 역할을 맡는 경우가 많았다. 모든 상태가 로컬에 있으면 네트워크 지연 없이 동작하고 서버 운영비가 들지 않지만, 저장 파일과 실행 코드를 사용자가 통제하므로 기록 조작을 막기 어렵다. 호스트 기반 멀티플레이는 호스트의 성능과 네트워크 품질에 좌우되고 호스트 종료가 세션 종료로 이어질 수 있다.

현대 패키지 게임도 계정, 라이선스, 랭킹, 매치메이킹, 저장 동기화 같은 온라인 기능을 사용한다. 핵심 플레이가 오프라인에서 가능한지, 서비스 종료 뒤 어떤 기능을 유지할지, 치트가 다른 사용자에게 미치는 범위가 어디까지인지에 따라 서버 권한의 범위를 정해야 한다. “패키지”와 “온라인”은 완전히 배타적인 분류가 아니라 기능마다 다른 운영 모델을 선택하는 문제다.

### 4.2 온라인 게임에서 게임 서버

온라인 게임은 여러 사용자가 같은 규칙과 세계 상태를 공유하도록 서버가 중재한다. 서버는 접속과 세션을 관리하고, 클라이언트가 보낸 입력을 검증하며, 결과를 관련 사용자에게 전파한다. 영구적인 계정·캐릭터 데이터도 중앙에서 관리해 기기가 바뀌어도 이어서 플레이할 수 있게 한다.

서버가 필수가 되면 점검, 장애, 비용, 지역별 지연이 제품 경험의 일부가 된다. 동시 접속자 수뿐 아니라 로그인 폭주, 업데이트 직후 트래픽, 한 지역 장애 같은 시나리오를 계획한다. 클라이언트 버전과 서버 프로토콜의 호환 범위를 관리하고, 오래된 클라이언트가 위험한 요청을 보내지 못하도록 최소 지원 버전을 통제해야 한다.

### 4.3 서버의 역할

서버의 가장 중요한 역할은 여러 클라이언트가 동의할 수 있는 권위 있는 상태를 만드는 것이다. 이동 가능 여부, 공격 적중, 아이템 획득과 소비, 거래 결과처럼 경쟁이나 경제에 영향을 주는 값은 서버가 최종 판정한다. 클라이언트는 사용자의 입력을 표현하고 결과를 예측할 수 있지만 임의의 결과를 사실로 제출해서는 안 된다.

모든 세부를 서버가 계산하면 보안은 강화되지만 CPU·대역폭·지연 비용이 커진다. 카메라, 이펙트, UI처럼 다른 사용자나 경제에 영향을 주지 않는 표현은 클라이언트에 맡긴다. 기능마다 입력, 검증 규칙, 최종 소유자, 복구 원본을 표로 정리하면 경계가 분명해진다. 서버는 단순 데이터 중계기가 아니라 규칙 집행자이자 공유 상태의 소유자다.

### 4.4 게임 클라이언트와 서버의 상호 작용

상호작용은 연결 수립, 인증, 요청·응답, 서버 알림, 연결 종료로 나눌 수 있다. 요청에는 종류와 식별자, 필요한 입력이 포함되고 응답은 성공 결과나 구체적인 실패 원인을 돌려준다. 서버 알림은 주변 플레이어 입장, 채팅, 상태 갱신처럼 클라이언트 요청 없이 발생할 수 있으므로 클라이언트는 언제든 받을 준비가 되어야 한다.

네트워크 재시도 때문에 같은 요청이 여러 번 도착할 수 있다. 구매나 보상 수령은 요청 ID와 처리 기록으로 멱등하게 만들고, 응답 유실 뒤 재요청해도 중복 반영되지 않게 한다. 연결이 끊겼을 때 세션을 즉시 제거할지 짧은 재접속 유예를 둘지, 재접속 후 전체 스냅숏과 누락 이벤트 중 무엇으로 복구할지도 정한다.

### 4.5 게임 서버가 하는 일

게임 서버는 네트워크 연결 관리, 메시지 해석, 플레이어 세션, 게임 규칙 실행, 관심 대상에게 상태 전파, 영속 데이터 읽기·쓰기, 로그와 지표 수집을 수행한다. 실시간 루프는 일정 틱 안에 입력을 모으고 시뮬레이션한 뒤 결과를 보내며, 계정이나 상점 기능은 요청·응답 중심으로 동작할 수 있다.

각 기능의 시간 요구가 다르므로 한 실행 경로에 모두 넣지 않는다. 로그 쓰기나 DB 저장이 게임 틱을 막지 않게 비동기로 분리하되, 저장 성공 전 클라이언트에게 확정 결과를 줄 경우 실패 보상 규칙을 마련한다. 운영 명령과 상태 점검, 안전한 종료도 서버의 일이다. 새 연결을 막고 진행 중 요청을 마치며 상태를 저장한 뒤 종료하는 순서를 자동화해야 한다.

### 4.6 게임 서버의 품질

품질은 처리 속도 하나로 설명되지 않는다. 정확성은 규칙과 데이터 불변식을 지키는지, 안정성은 잘못된 입력과 부분 장애에서도 서비스를 보호하는지, 확장성은 부하 증가에 대응할 수 있는지, 보안은 신뢰 경계를 지키는지를 뜻한다. 운영성은 문제를 발견하고 배포·롤백·복구할 수 있는 능력이다.

평균 응답 시간과 평균 CPU만으로는 소수 사용자의 긴 지연과 순간 폭주를 놓친다. p95·p99 지연, 틱 초과 비율, 오류율, 큐 길이, 연결 수, DB 대기, 메모리 증가를 함께 본다. 서비스 수준 목표를 수치로 정하고, 장애 주입과 부하 시험으로 실제 한계를 확인한다. 복구 시간 목표와 허용 데이터 손실 범위 역시 품질 요구다.

### 4.7 플레이어 정보의 저장

계정, 캐릭터, 재화, 인벤토리처럼 세션을 넘어 유지돼야 하는 정보는 서버 측 영속 저장소에 둔다. 게임 서버 메모리는 빠른 작업 복사본일 수 있지만 프로세스가 종료되면 사라진다. 무엇이 진실의 원본인지 정하고, 메모리와 DB가 어긋났을 때 어느 방향으로 복구할지 결정한다.

모든 행동마다 동기 저장하면 안전하지만 지연과 DB 부하가 크고, 일정 주기로만 저장하면 장애 시 최근 변경을 잃을 수 있다. 중요한 거래는 트랜잭션과 기록으로 즉시 확정하고, 재생성 가능한 위치나 임시 상태는 지연 저장하는 식으로 등급을 나눈다. 버전 번호나 낙관적 동시성으로 오래된 저장이 최신 상태를 덮지 못하게 한다.

### 4.8 서버 구동 환경

온프레미스는 하드웨어와 네트워크를 직접 통제하며 장기적으로 일정한 부하에서 비용 예측이 쉬울 수 있지만 구매, 증설, 장애 교체를 팀이 담당한다. 클라우드는 필요한 자원을 빠르게 만들고 여러 지역과 관리형 서비스를 사용할 수 있으나 지속 비용, 송신 비용, 제공자 제약과 장애 범위를 이해해야 한다.

IaaS는 가상 머신과 네트워크 위에서 운영체제부터 관리하고, PaaS나 관리형 서비스는 관리 범위를 줄이는 대신 설정과 이동 자유도가 낮아질 수 있다. 컨테이너는 배포 단위를 표준화하지만 상태, 네트워크, 관측, 오케스트레이션 문제를 자동으로 해결하지 않는다. 목표 지역, 동시 접속 변동, 규제, 팀의 운영 역량을 기준으로 환경을 선택한다.

### 4.9 게임 서버 개발 지침

개발 초기에 프로토콜과 상태 소유권, 오류 처리 원칙을 정하고 서버는 모든 외부 입력을 검증해야 한다. 길이와 범위, 권한, 현재 상태에서 가능한 행동인지를 확인하며 잘못된 요청 하나가 프로세스를 종료시키지 않게 한다. 시간과 난수처럼 재현에 영향을 주는 의존성을 분리하면 테스트와 장애 재현이 쉬워진다.

운영을 고려해 구조화 로그, 추적 ID, 핵심 지표, 설정 버전을 넣고 비밀 정보는 로그에서 제외한다. 작은 단위 테스트 외에도 여러 클라이언트의 순서 경쟁, 연결 끊김, 재시도, DB 실패, 과부하를 통합 시험한다. 성능 최적화는 측정 뒤에 하고, 배포에는 점진 전환과 빠른 롤백 경로를 둔다.

### 클라이언트 입력과 서버 판정

```cpp
MoveResult HandleMove(Player& player, const MoveRequest& request) {
    if (request.sequence <= player.lastInputSequence)
        return MoveResult::Duplicate;
    if (!IsFinite(request.direction) || Length(request.direction) > 1.0f)
        return MoveResult::Invalid;
    if (!CanMove(player.state))
        return MoveResult::Rejected;

    player.lastInputSequence = request.sequence;
    player.position = SimulateMove(player, request.direction);
    return MoveResult::Accepted;
}
```

클라이언트는 방향이라는 입력을 보내고 서버가 위치를 계산한다. 서버는 순서, 값 범위, 현재 상태를 검사한다. 클라이언트 화면은 먼저 예측해 표시할 수 있지만 서버의 결과가 최종 상태다.

```text
    │                 │                               │
    │                 └─ 버전 번호 포함               └─ 성공/실패 결과
    └─ 거래 ID로 중복 실행 방지 <─────────────────────────┘
```

재화 차감과 아이템 지급처럼 중요한 작업은 하나의 트랜잭션 또는 복구 가능한 상태 기계로 처리한다. 위치처럼 재생성 가능한 상태는 더 느슨한 저장 정책을 사용할 수 있다.

## 공부할 내용

1. 로그인, 이동, 공격, 아이템 구매를 표로 만들고 최종 판정 주체를 표시한다.
2. 요청·응답·알림·연결 종료가 포함된 간단한 프로토콜 상태도를 그린다.
3. 서버 품질 지표로 동시 접속자, 틱 지연, 오류율, 큐 길이, DB 지연을 선정한다.
4. 온프레미스와 클라우드 배포의 비용 및 장애 대응 차이를 비교한다.

## 복습 질문

- 클라이언트 예측과 서버 권한은 어떻게 함께 사용할 수 있는가?
- 성능과 확장성은 왜 같은 의미가 아닌가?
- 플레이어 데이터를 클라이언트에만 저장하면 어떤 문제가 생기는가?
- 운영 중인 서버에서 관리 편의성이 기능 완성도만큼 중요한 이유는 무엇인가?
