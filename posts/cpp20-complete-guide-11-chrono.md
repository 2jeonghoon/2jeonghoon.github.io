## 11.1 달력 일정으로 전체 구조 보기

매월 5일 일정은 고정된 초 수를 반복해서 더하는 문제와 다르다.
매월 마지막 날은 다음 달의 날짜 수에 따라 달라진다.
첫째 월요일 일정은 연·월·요일 순번이라는 달력 규칙으로 표현하는 편이 정확하다.

아래는 독립 실행 예제다.

```cpp
#include <cassert>
#include <chrono>

int main() {
    using namespace std::chrono;
    year_month month = 2026y / October;
    year_month_day fifth{month / 5};
    year_month_day last_day{month / last};
    year_month_weekday first_monday{month / Monday[1]};

    assert(fifth.ok());
    assert(last_day.day() == day{31});
    year_month_day converted{sys_days{first_monday}};
    assert(converted.day() == day{5});
}
```

같은 회의의 현지 시각을 여러 지역에 보여 주려면 시간대 규칙을 적용한다.
전 세계 어디서나 같은 순간을 뜻하는 시점과 특정 지역의 시계 표시를 분리한다.
그 지역에서 앞으로 열릴 반복 일정은 지역 달력 규칙도 함께 저장할 필요가 있다.

## 11.2 기본 용어부터 분리하기

`duration`은 두 시점 사이의 길이이며 개수와 단위를 가진다.
`time_point`는 특정 시계의 기준점에 대한 기간이다.
`clock`은 그 기준과 현재 시점 취득 방법을 정의한다.
달력 날짜는 연·월·일 조합이며 시간대가 없으면 전 지구적 순간을 뜻하지 않는다.

UTC 오프셋은 어느 순간에서의 차이고 시간대는 시간에 따라 달라지는 규칙의 묶음이다.
`+09:00`과 `Asia/Seoul`은 저장하는 정보의 종류가 다르다.
사용자의 위치가 바뀌어도 어떤 정보를 유지해야 하는지 제품 요구부터 정한다.

## 11.3 C++20의 기본 chrono 확장

`days`, `weeks`, `months`, `years`와 달력 관련 타입이 추가되었다.
`months`와 `years`는 기간 타입으로 평균 길이를 나타내며 모든 달의 실제 길이가 같다는 뜻이 아니다.
달력 타입에 월을 더하는 연산과 기간을 초로 변환하는 연산을 구분해야 한다.

`sys_time<Duration>`은 시스템 시계 계열 시점을 표현하는 별칭이다.
`sys_days`는 일 단위 정밀도를 사용하므로 날짜 사이의 일수 계산에 편리하다.
`local_time`은 지역 달력·시계 표시를 표현하지만 시간대가 정해지기 전에는 모호할 수 있다.

`year`, `month`, `day`, `weekday`를 조합해 달력 타입을 만든다.
`year_month_day_last`와 `year_month_weekday`는 마지막 날과 요일 기반 일정을 표현한다.
서로 다른 표현 사이의 변환이 어떤 날짜 규칙을 적용하는지 명확히 읽는다.

`hh_mm_ss`는 기간을 시·분·초와 소수 초 등으로 분해해 표시하기 좋다.
음수 여부와 24시간을 넘는 기간은 시각 표시와 구분한다.
`is_am`, `is_pm`, `make12`, `make24`는 12시간·24시간 표현 변환을 돕는다.

## 11.4 입출력과 형식화

chrono 타입의 스트림 출력과 format 지원은 타입에 맞는 기본 표현을 제공한다.
사용자가 읽는 날짜 순서는 로캘에 따라 다르므로 저장 형식과 화면 출력을 분리한다.
형식 지정은 날짜·시간 전용 변환 문자를 사용한다.

입력은 `from_stream`이나 `parse` 계열로 명시적인 패턴에 맞춰 읽을 수 있다.
입력 실패 상태를 확인하고 실패한 값을 일정 계산에 계속 사용하지 않는다.
시간대 약어와 오프셋을 함께 읽는 경우 그것이 시간대 규칙 전체를 식별하는지 따져야 한다.

파싱 성공과 비즈니스적으로 허용하는 일정인지는 별개다.
예를 들어 영업일만 허용하는 정책은 달력 날짜 파싱 이상의 검증이 필요하다.
모호한 날짜 형식을 자동 추측하는 방식보다 입력 계약을 명확히 하는 편이 안전하다.

## 11.5 실제 달력 계산의 함정

달력 타입은 잘못된 조합을 표현할 수 있으므로 `ok()`를 확인한다.
2월 31일 같은 날짜가 객체로 만들어졌다고 실제 날짜로 유효하다는 뜻은 아니다.
유효하지 않은 날짜를 시점으로 변환해 자동 검증을 대신하려 하지 않는다.

1월 31일에 한 달을 더하면 존재하지 않는 2월 31일 조합이 될 수 있다.
말일로 맞출지, 다음 달로 넘길지, 입력을 거부할지 정책을 정한다.
매월 말일 일정은 처음부터 `last`를 포함한 달력 규칙으로 저장하면 의도가 분명하다.

경과 시간 24시간과 다음 날 같은 현지 시각은 일광 절약 시간 전환에서 다를 수 있다.
기간 계산과 달력 일정 계산을 같은 함수에 섞지 않는다.
시점이나 기간을 파싱한 뒤에도 단위와 정밀도 손실을 확인한다.

## 11.6 시간대 규칙 적용하기

시간대 데이터베이스는 지역 식별자와 시간에 따른 오프셋·전환 규칙을 제공한다.
`locate_zone`으로 지역을 찾고 `zoned_time`으로 지역 규칙과 시점을 연결한다.
라이브러리의 시간대 지원과 데이터베이스 설치 여부는 환경에 따라 확인해야 한다.

다음은 시간대 데이터가 있는 환경을 전제로 한 독립 실행 예제다.

```cpp
#include <cassert>
#include <chrono>

int main() {
    using namespace std::chrono;
    auto instant = sys_days{2026y / October / 19} + hours{3};
    zoned_time<seconds> utc{"Etc/UTC", instant};
    zoned_time<seconds> seoul{"Asia/Seoul", instant};
    assert(utc.get_sys_time() == seoul.get_sys_time());
}
```

약어는 지역을 유일하게 식별하지 못할 수 있다.
사용자가 선택한 IANA 지역 이름과 실제 순간을 용도에 맞게 저장한다.
정치적 결정으로 미래 규칙이 바뀔 수 있으므로 장기 반복 일정에는 재해석 정책도 필요하다.

지역 시각에서 시스템 시점으로 변환할 때 존재하지 않거나 두 번 존재하는 시각이 있다.
이는 오류로 처리하거나 허용되는 모호성에 대해 `choose` 정책을 명시한다.
사용자 정의 시간대는 필요한 변환 인터페이스를 제공해야 하며 단순한 오프셋 숫자와 구분된다.

## 11.7 시계를 자세히 구분하기

`system_clock`, `utc_clock`, `tai_clock`, `gps_clock`은 기준과 윤초 취급이 다르다.
`steady_clock`은 경과 시간 측정에 적합하며 달력 날짜 출력용 기준과는 목적이 다르다.
`local_t`는 지역 시각 타입을 구분하는 표식이며 직접 현재 시각을 읽는 시계가 아니다.

윤초를 취급하는 시점과 일반 시스템 시간을 단순 숫자 복사로 변환하지 않는다.
지원되는 `clock_cast`나 해당 시계의 변환 함수를 사용하고 변환 경로의 의미를 확인한다.
파일 시계는 구현의 기준을 고려해 변환해야 하며 시스템 시계와 같은 epoch라고 가정하지 않는다.

## 11.8 그 밖의 새 기능

달력 값의 산술, 비교, chrono 리터럴과 입출력 지원을 함께 익히면 수동 정수 계산이 줄어든다.
그러나 일정을 나타내는 자료형 하나가 정책과 유효성까지 전부 대신하지는 않는다.
저장에는 순간, 지역 규칙, 반복 규칙 중 어떤 정보가 필요한지 먼저 결정한다.
