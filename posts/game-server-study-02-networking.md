게임 서버의 메시지는 여러 네트워크 장비와 계층을 지나 클라이언트에 도달한다. 지연, 유실, 중복, 순서 변경은 예외적인 사건이 아니라 설계가 다뤄야 할 조건이다. 이번 단원에서는 전송 방식의 특성을 이해하고 메시지마다 적절한 선택을 내리는 기준을 정리한다.

## 네트워크를 구성하는 요소

스위치는 같은 네트워크 안에서 프레임을 전달하고, 라우터는 서로 다른 네트워크 사이에서 패킷의 경로를 선택한다. 방화벽은 규칙에 따라 트래픽을 허용하거나 차단한다. 인터넷에서는 여러 중간 장비를 지나므로 서버가 보는 연결 품질은 거리뿐 아니라 경로 혼잡과 각 구간의 처리 상태에도 영향을 받는다.

IP 주소는 호스트를, 포트는 한 호스트 안의 통신 종단점을 식별한다. IP와 포트를 합친 소켓 주소가 실제 통신 상대를 나타낸다. 도메인 이름은 DNS를 통해 IP 주소로 해석된다. 사설 네트워크에서는 NAT 장비가 내부 주소와 외부 주소의 매핑을 관리하므로, 외부에서 내부 클라이언트로 직접 연결하려면 별도 전략이 필요할 수 있다.

## 스트림, 메시지, 패킷

TCP는 애플리케이션에 연속된 바이트 스트림을 제공한다. 한 번의 `send`가 상대의 한 번의 `recv`와 같은 경계를 가진다고 가정하면 안 된다. 따라서 길이 헤더, 구분자 또는 고정 길이 규칙으로 메시지 프레이밍을 구현해야 한다.

UDP는 데이터그램 경계를 보존하지만 도착, 순서, 중복 제거를 보장하지 않는다. IP 계층의 패킷 크기와 경로 MTU도 고려해야 한다. 큰 메시지의 단편화는 일부 조각만 유실돼도 전체 데이터그램을 사용할 수 없게 만들 수 있어 실시간 트래픽에는 작은 메시지가 유리하다.

## TCP와 UDP 선택

TCP는 신뢰성과 순서를 제공하므로 로그인, 결제, 채팅처럼 빠짐없이 순서대로 처리해야 하는 데이터에 잘 맞는다. 하지만 유실된 앞부분이 재전송될 때 뒤의 데이터도 기다리는 지연이 생길 수 있다. UDP는 최신 위치나 조준 방향처럼 오래된 데이터의 재전송 가치가 낮은 경우에 유리하다. 중요한 점은 프로토콜 이름보다 메시지가 요구하는 **신뢰성, 순서, 최신성, 지연 허용치**를 먼저 정의하는 것이다.

메시지 형식은 사람이 읽기 쉬운 텍스트와 크기가 작고 처리 효율이 높은 바이너리 사이에서 선택한다. 어느 형식이든 버전 필드, 메시지 종류, 길이, 선택 필드 처리 규칙을 두어 이전 클라이언트와의 호환성을 계획해야 한다.

## 원문별 상세 정리

### 2.1 컴퓨터 네트워크를 구성하는 기기

호스트의 네트워크 인터페이스는 프레임을 송수신하고, 스위치는 같은 링크 영역에서 MAC 주소를 바탕으로 전달한다. 라우터는 서로 다른 IP 네트워크 사이의 다음 경로를 결정하며, 방화벽과 로드 밸런서, NAT 장비는 규칙에 따라 연결을 필터링하거나 목적지를 바꾼다. 애플리케이션이 보는 한 번의 연결 뒤에는 여러 장비와 큐가 존재한다.

장애를 분석할 때 “네트워크가 느리다”로 끝내지 말고 DNS 해석, 연결 수립, 각 홉의 지연, 패킷 손실, 서버 큐 대기 중 어디에서 시간이 소모됐는지 나눈다. 서버를 여러 지역에 둘 때는 물리 거리뿐 아니라 피어링과 라우팅 경로도 영향을 준다. 장비 하나가 모든 트래픽의 단일 통과점인지, 이중화 시 세션이 유지되는지도 구조도에 표시해야 한다.

### 2.2 인터넷

인터넷은 하나의 중앙 네트워크가 아니라 자율적으로 운영되는 수많은 네트워크가 공통 프로토콜로 연결된 구조다. 패킷은 목적지까지 여러 라우터를 거치며 경로는 고정되어 있지 않다. 한 방향과 반대 방향이 서로 다른 경로를 사용할 수도 있고, 혼잡이나 장애로 경로가 바뀌면 지연 특성이 달라진다.

게임 서버는 이 변동을 전제로 설계해야 한다. 평균 왕복 시간만 보지 말고 지터, 손실률, 재전송, 시간대별 변화를 관찰한다. 인터넷 구간에 완전한 전달 시간을 약속할 수 없으므로 타임아웃과 재연결 정책이 필요하며, 지역 선택이나 엣지 중계로 긴 경로를 줄일 수 있다. 단, 중계 지점을 늘리면 운영해야 할 장애 지점과 비용도 늘어난다.

### 2.3 컴퓨터 네트워크 데이터

애플리케이션은 논리적인 메시지를 다루지만 전송 계층과 네트워크 계층에서는 바이트 스트림, 세그먼트, 데이터그램, 패킷처럼 다른 단위로 처리된다. TCP의 `send` 호출 경계는 수신 측에서 유지되지 않으므로 하나의 메시지가 여러 번에 나뉘거나 여러 메시지가 한 번에 도착할 수 있다. 길이 접두부나 명확한 프레이밍 규칙이 반드시 필요하다.

UDP는 한 데이터그램의 경계를 보존하지만 크기가 경로 MTU를 넘으면 IP 단편화 위험이 커진다. 조각 하나만 잃어도 전체 데이터그램이 쓸모없어질 수 있다. 게임 프로토콜은 메시지 헤더, 종류, 버전, 길이, 시퀀스 번호를 정의하고 최대 크기를 검증해야 한다. 압축이나 암호화 후 크기가 어떻게 변하는지도 패킷 예산에 포함한다.

### 2.4 컴퓨터 네트워크 식별자

MAC 주소는 주로 로컬 링크에서 인터페이스를 식별하고, IP 주소는 네트워크 간 라우팅 가능한 호스트 위치를 나타낸다. 포트 번호는 한 호스트 안에서 통신 종단점을 구분한다. IP 주소와 포트, 전송 프로토콜을 함께 봐야 실제 연결을 특정할 수 있으며 서버는 일반적으로 잘 알려진 포트에 바인드하고 클라이언트는 임시 포트를 사용한다.

도메인 이름은 DNS를 통해 하나 이상의 주소로 해석될 수 있고 결과는 TTL 동안 캐시된다. 서버 주소가 바뀌어도 모든 클라이언트가 즉시 새 값을 보는 것은 아니다. IPv4와 IPv6, 공인·사설 주소, 바인드 주소와 외부에서 보이는 주소를 구분해야 한다. 로그에는 개인정보 노출 정책을 지키면서 연결 식별자와 주소 변환 정보를 남겨야 문제를 추적할 수 있다.

### 2.5 컴퓨터 네트워크의 품질과 특성

대역폭은 단위 시간에 보낼 수 있는 데이터량이고, 지연은 데이터가 상대에게 도달하고 처리되는 데 걸리는 시간이다. 처리량이 충분해도 지연이 크면 실시간 조작감은 나쁠 수 있다. 지터는 지연의 변동이고, 손실과 중복, 순서 변경 역시 사용자 경험에 직접 영향을 준다.

측정할 때 평균만 보면 짧은 장애가 숨는다. p95·p99 지연, 연속 손실 길이, 송수신 큐 크기, 지역과 통신사별 분포를 본다. 클라이언트 보간 버퍼를 늘리면 지터는 가릴 수 있지만 기본 지연이 늘어난다. 더 자주 보내면 최신성은 좋아질 수 있으나 대역폭과 혼잡 가능성이 커진다. 품질 목표는 메시지 종류별 허용 지연과 유실 정책으로 구체화해야 한다.

### 2.6 컴퓨터 네트워크에서 데이터 보내기와 받기

송신 데이터는 애플리케이션에서 소켓 송신 버퍼로 들어간 뒤 전송 계층과 IP 계층, 링크 계층의 헤더를 거쳐 네트워크로 나간다. 수신 측에서는 역순으로 처리되어 소켓 수신 버퍼에 쌓이고 애플리케이션이 읽는다. `send` 성공은 대개 로컬 운영체제가 데이터를 받아들였다는 뜻이지 상대 게임 로직이 처리했다는 확인이 아니다.

신뢰가 필요한 애플리케이션 동작에는 별도 응답이나 상태 확인이 필요하다. 부분 송신과 부분 수신을 처리하고, 바이트 순서와 정수 크기, 문자열 인코딩을 프로토콜에 고정한다. 운영체제 버퍼가 일시적인 속도 차이를 흡수하지만 무한하지 않으므로 느린 상대를 위해 송신 큐 상한과 연결 종료 정책을 둔다.

### 2.7 패킷 유실 시 UDP와 TCP에서 나타나는 현상

UDP는 손실된 데이터그램을 전송 계층에서 복구하지 않는다. 애플리케이션은 위치 스냅숏처럼 다음 값으로 대체할지, 중요한 이벤트만 자체 확인·재전송할지 결정한다. 재전송을 추가할 경우 시퀀스 번호, 중복 제거, 만료 시간, 순서 정책을 함께 구현해야 하며 결국 요구에 맞춘 신뢰 계층을 만드는 셈이다.

TCP는 손실을 감지해 재전송하고 순서대로 바이트를 전달한다. 앞 세그먼트가 사라지면 뒤 데이터가 도착했어도 애플리케이션 전달이 지연되는 헤드 오브 라인 블로킹이 생긴다. 그래서 로그인과 거래에는 유리하지만 오래된 위치 값까지 반드시 순서대로 기다리는 것은 불리할 수 있다. TCP와 UDP는 우열이 아니라 데이터의 의미에 따라 선택한다.

### 2.8 주로 사용하는 메시지 형식

텍스트 형식은 사람이 읽고 도구로 확인하기 쉬우며 필드 이름이 있어 개발 초기와 운영 진단에 편하다. 대신 필드 이름과 숫자 표현 때문에 크기가 커지고 파싱 비용과 타입 모호성이 생길 수 있다. 바이너리 형식은 작고 빠르게 만들 수 있지만 스키마와 디버깅 도구가 필요하며 잘못된 길이 값이 큰 보안 문제로 이어질 수 있다.

형식 선택과 별개로 메시지 ID, 스키마 버전, 필수·선택 필드, 알 수 없는 필드 처리, 최대 배열 길이를 정의한다. 클라이언트와 서버를 동시에 배포할 수 없는 온라인 서비스에서는 이전 버전 호환성이 중요하다. 새 필드를 추가할 때 기본값을 두고, 의미를 바꾸기보다 새 필드나 새 메시지를 도입하며, 퍼징과 경계값 테스트로 디코더를 검증한다.

### 2.9 네트워크 주소 변환

NAT는 사설 주소와 포트를 외부에서 사용할 공인 주소와 포트로 매핑한다. 여러 내부 기기가 하나의 공인 IPv4 주소를 공유할 수 있지만, 외부 상대는 내부 주소를 직접 사용할 수 없다. 매핑은 보통 내부에서 먼저 트래픽을 보낼 때 만들어지고 일정 시간 통신이 없으면 사라질 수 있다.

클라이언트-서버 방식에서는 클라이언트가 공인 서버로 연결하므로 비교적 단순하지만 P2P에서는 NAT 유형과 방화벽 규칙이 문제가 된다. 홀 펀칭을 시도하더라도 모든 환경에서 성공하지 않으므로 릴레이 서버라는 대체 경로가 필요하다. 모바일 네트워크 변경이나 공유기 재부팅으로 외부 주소가 바뀔 수 있어 주소를 사용자 신원으로 간주해서는 안 된다.

### TCP 메시지 프레이밍

TCP는 메시지 경계를 보존하지 않으므로 헤더에 본문 길이를 넣을 수 있다. 네트워크에서 사용하는 정수의 바이트 순서를 통일해야 한다.

```cpp
struct PacketHeader {
    std::uint16_t type;
    std::uint32_t bodySize;
};

void WriteHeader(Buffer& out, std::uint16_t type, std::uint32_t bodySize) {
    out.WriteUInt16NetworkOrder(type);
    out.WriteUInt32NetworkOrder(bodySize);
}
```

수신 측은 먼저 고정 크기 헤더가 모였는지 확인하고, `bodySize`가 서버의 최대 패킷 크기 이하인지 검증한 뒤 본문이 모두 들어올 때까지 기다린다.

```text
TCP 수신 조각 1: [헤더 일부]
TCP 수신 조각 2: [헤더 나머지][본문 일부]
TCP 수신 조각 3: [본문 나머지][다음 메시지 헤더]
                         │
                         └─ 연결별 버퍼가 메시지 경계를 복원한다.
```

### 메시지 성격에 따른 전송 선택

| 메시지 | 중요한 성질 | 일반적인 선택 |
| --- | --- | --- |
| 로그인 결과 | 손실되면 안 됨, 순서 중요 | 신뢰·순서 채널 |
| 아이템 구매 | 중복 반영 금지, 결과 확인 필요 | 신뢰 채널 + 거래 ID |
| 위치 스냅숏 | 오래된 값보다 최신 값이 중요 | 비신뢰 최신 상태 채널 |
| 채팅 | 전달과 순서가 중요 | 신뢰·순서 채널 |

UDP에 시퀀스 번호를 붙이면 늦게 도착한 이전 상태를 버릴 수 있다.

```cpp
if (packet.sequence <= player.lastSequence) {
    return; // 중복되었거나 더 오래된 위치 갱신
}
player.lastSequence = packet.sequence;
ApplySnapshot(packet);
```

### NAT를 통과하는 경로

```text
내부 클라이언트 192.168.0.10:53000
        │
        │ 사설 주소와 포트를 외부 매핑으로 변환
        ▼
NAT 공유기 203.0.113.7:62001
        │
        ▼
공인 게임 서버 198.51.100.20:7777
```

서버에는 공유기의 공인 주소와 변환된 포트가 보인다. P2P에서 직접 연결이 실패하면 중계 서버를 사용해야 하며, 외부 주소는 네트워크가 바뀌면 달라질 수 있으므로 계정 식별자로 사용하지 않는다.

## 공부할 내용

1. TCP로 길이 헤더 기반 메시지 프레이밍을 구현하고 메시지가 나뉘어 수신되는 상황을 시험한다.
2. UDP 패킷의 일부를 의도적으로 버려 위치 갱신과 확정 이벤트가 어떻게 달라야 하는지 관찰한다.
3. JSON과 바이너리 직렬화의 크기와 인코딩 시간을 같은 데이터로 비교한다.
4. 공유기 뒤의 두 클라이언트가 외부 서버에서 어떤 주소로 보이는지 확인한다.
