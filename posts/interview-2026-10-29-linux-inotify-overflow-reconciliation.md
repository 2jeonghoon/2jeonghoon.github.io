## 오늘의 질문

파일 감시 에이전트가 inotify를 사용합니다. 대량의 파일 변경 후 큐 오버플로 이벤트를 확인했습니다. 이후 수신되는 이벤트만 계속 처리하면 충분할까요? 현재 파일 상태와 에이전트의 기록을 다시 맞추는 복구 절차를 설명해 주세요.

## inotify란

Linux 커널이 감시하는 파일·디렉터리의 생성, 변경, 삭제, 이동 등을 애플리케이션에 알려주는 인터페이스다. 반복적인 전체 조회를 줄일 수 있지만 신뢰할 수 있는 영구 감사 로그는 아니다.

inotify_init1로 이벤트를 읽을 FD를 만들고 inotify_add_watch로 대상과 관심 이벤트를 등록한다. read는 하나 이상의 inotify_event를 반환할 수 있으며 epoll과 결합할 수 있다. 일반적으로 하위 디렉터리까지 자동 재귀 감시하지 않으므로 각 디렉터리와 새 디렉터리에 대한 등록 관리가 필요하다.

~~~text
감시 폴더에 a.txt 생성
    → 커널 이벤트 큐에 IN_CREATE
    → 에이전트가 read로 수신
    → 파일 목록 기록 갱신
~~~

## 큐 오버플로의 의미

유한한 커널 큐가 넘치면 이벤트 일부가 버려지고 IN_Q_OVERFLOW로 이를 알린다. 이벤트에 wd=-1이 올 수 있어 특정 감시 하나의 문제로만 다루면 안 된다.

실제로 a.txt가 삭제됐지만 삭제 이벤트를 놓쳤다면 기록에는 계속 존재한다. 이후 b.txt의 새 이벤트만 처리해도 a.txt의 오류는 해결되지 않는다.

인스턴스가 담당한 상태를 불확실하게 표시하고, 이벤트 소비를 계속하면서 감시 목록과 현재 파일 상태를 다시 스캔하여 기록과 비교한다. 추가·변경·삭제를 조정하고 재스캔 중 발생한 변경도 반영한다. 필요하면 감시를 재구성한다. 디렉터리 감시를 먼저 등록한 뒤 스캔하고 경합을 재검증하는 등 공백을 줄인다. 다시 overflow가 발생하면 재조정을 반복하고 부하 대책을 수행한다.

스캔은 원자적 스냅샷이 아니므로 조용한 시점의 최종 재검증이나 별도의 일관성 전략이 필요하다. 재스캔으로 현재 상태를 복구할 수 있어도 유실 구간에 생성됐다 삭제된 파일의 전체 이력은 복원하지 못한다.

이벤트 읽기와 느린 해시·DB 작업을 분리하고 유실 감지, 큐 상태, 재조정 성공을 모니터링한다. 큐 크기 증가만으로 영구적인 과부하를 해결하지는 못한다.

## 면접용 모범 답변

inotify는 파일시스템 변경을 커널 이벤트로 받는 기능입니다. 오버플로가 나면 일부 이벤트를 놓쳤으므로 내부 기록을 신뢰하지 않고 현재 파일 상태와 재조정하겠습니다. 재스캔 중 변경과 감시 등록 누락도 처리하고, 현재 상태 복구와 과거 이벤트 이력 복구는 구분하겠습니다.
