분산은 서버를 여러 대 두는 행위가 아니라 상태와 책임을 여러 실패 영역으로 나누는 설계다. 처리량과 가용성을 높일 수 있지만 네트워크 실패, 부분 성공, 데이터 불일치, 운영 복잡성을 새로 만든다. 따라서 단일 서버의 병목을 측정하고 최적화한 뒤 필요한 지점만 분산하는 것이 기본 원칙이다.

## 확장 방식

수직 확장은 한 서버의 CPU, 메모리, 스토리지를 더 강하게 만든다. 구조 변경이 적지만 하드웨어 한계와 단일 장애 지점이 남는다. 수평 확장은 같은 역할의 서버를 늘려 부하를 나눈다. 무상태 요청에는 비교적 쉽지만 메모리에 사용자 상태를 가진 서버는 라우팅, 이전, 복구 전략이 필요하다.

고전적인 게임 구조에서는 인증 서버와 여러 채널 또는 월드 서버를 분리할 수 있다. 사용자를 독립된 채널에 나누면 확장이 단순하지만 서로 다른 채널의 사용자가 상호작용하기 어렵다. 논리적으로 하나의 세계를 유지하려면 지역, 객체, 기능 중 어떤 경계를 기준으로 나눌지 결정해야 한다.

## 데이터 분산과 기능 분산

데이터 분산은 같은 기능이 서로 다른 사용자나 월드 조각을 담당하게 한다. 기능 분산은 로그인, 채팅, 경매장처럼 서로 다른 책임을 별도 서비스에 둔다. 데이터 응집도가 높은 상태를 서로 다른 서버로 찢으면 작은 행동마다 원격 호출이 필요해져 오히려 느리고 불안정해질 수 있다.

분산된 로직을 처리하는 대표 방식은 다음과 같다.

- 동기 호출: 결과를 기다려 다음 작업을 진행한다. 이해하기 쉽지만 지연과 연쇄 장애에 민감하다.
- 비동기 메시지: 요청을 큐에 넣고 나중에 처리한다. 결합을 줄이지만 완료 확인과 중복 처리가 필요하다.
- 데이터 복제 후 로컬 판정: 읽기는 빠르지만 복제 지연과 충돌 규칙을 관리해야 한다.

원격 작업에는 타임아웃, 재시도, 멱등성, 추적 ID가 필요하다. 재시도는 성공 여부를 모르는 요청을 중복 실행할 수 있으므로 거래 ID나 상태 전이를 이용해 한 번만 반영되게 해야 한다.

## 가용성과 데이터베이스

서버를 여러 대 두는 것만으로 가용성이 생기지 않는다. 로드 밸런서, 서비스 발견, 데이터베이스, 메시지 브로커가 새로운 단일 장애 지점이 될 수 있다. 장애를 감지하고 우회하는 시간, 손실 가능한 데이터 범위, 복구 절차를 수치로 정의해야 한다.

DB는 행 또는 사용자 기준의 수평 파티셔닝, 테이블 또는 기능 기준의 수직 파티셔닝, 복제를 조합할 수 있다. 분할 키를 바꾸거나 샤드를 늘릴 때 데이터 이동 비용과 서비스 중단 가능성을 함께 계획한다.

## 원문별 상세 정리

### [9.1 수직 확장과 수평 확장](https://softhamzzi.github.io/gameserver/game_server_9_1/)

수직 확장은 한 서버의 CPU, 메모리, 디스크 성능을 높이는 방식이라 애플리케이션 구조 변경이 적고 빠르게 적용할 수 있다. 다만 가장 큰 장비의 한계와 비용 곡선이 있고 단일 장애 영역이 남는다. 수평 확장은 인스턴스를 늘려 부하를 나누지만 요청 라우팅과 상태 분배, 장애 복구가 필요하다.

무상태 HTTP 요청은 수평 확장이 비교적 쉽지만 메모리에 월드 상태를 가진 게임 서버는 아무 인스턴스로 요청을 보낼 수 없다. 방이나 사용자, 지역 같은 분할 단위를 정해야 한다. 먼저 프로파일링과 단일 노드 최적화로 실제 병목을 찾고, 목표 부하와 장애 요구가 수직 확장의 범위를 넘을 때 필요한 부분부터 수평화한다.

### [9.2 서버 분산이 없다면?](https://softhamzzi.github.io/gameserver/game_server_9_2/)

클라이언트, 게임 서버 하나, 데이터베이스 하나로 구성된 구조는 데이터 흐름이 단순하고 디버깅하기 쉽다. 초기 서비스나 작은 동시 접속에서는 이런 단순성이 큰 장점이며, 네트워크 호출과 중복 상태가 적어 개발 속도도 빠르다. 분산을 미리 도입한다고 반드시 더 좋은 구조가 되는 것은 아니다.

사용자가 늘면 게임 서버 CPU·메모리·네트워크와 DB 연결·질의 중 어느 곳이 먼저 한계에 닿는지 측정한다. 단일 프로세스 장애가 전체 접속을 끊는 위험과 점검 중단도 고려한다. 단일 구조에서 모듈 경계와 상태 소유권, 관측성을 잘 만들어 두면 이후 병목 기능을 분리하기 쉽다. 한계를 숫자로 알기 전 분산하면 복잡성만 먼저 지불할 수 있다.

### [9.3 고전적인 서버 분산 방법](https://softhamzzi.github.io/gameserver/game_server_9_3/)

고전적인 MMORPG 구조는 인증 서버 뒤에 여러 월드나 채널 서버를 두고 사용자가 하나를 선택하게 한다. 각 채널은 독립된 게임 상태와 사용자 집합을 처리하므로 부하가 자연스럽게 나뉘고 한 채널 장애의 범위를 제한할 수 있다. 인증과 캐릭터 선택 뒤 대상 서버 주소와 일회성 접속 자격을 전달한다.

대신 서로 다른 채널 사용자는 같은 공간에서 직접 만나기 어렵고 친구·채팅·거래 같은 전역 기능은 별도 서비스가 필요해진다. 인기 채널에만 사용자가 몰릴 수 있어 인원 제한과 이동 정책을 둔다. 채널 이동 때 상태 저장과 세션 인계가 정확히 한 번 일어나도록 전환 상태와 타임아웃을 설계한다.

### [9.4 논리적 단일 서버 분산](https://softhamzzi.github.io/gameserver/game_server_9_4/)

사용자에게는 하나의 세계처럼 보이지만 내부적으로 여러 서버가 역할이나 데이터를 나누는 구조다. 먼저 단일 서버에서 CPU 샘플, 큐 대기, 잠금, DB와 네트워크 시간을 측정해 과부하 지점을 찾는다. 병목이 아닌 기능을 분리하면 원격 통신만 늘고 전체 처리량은 그대로일 수 있다.

분산 뒤에도 객체 ID와 라우팅 규칙, 상태 소유자는 단 하나로 결정되어야 한다. 서버 경계를 넘는 이동에는 출발 서버 중지, 상태 전달, 대상 서버 수락, 라우팅 전환을 조정하는 프로토콜이 필요하다. 중간 실패 뒤 두 서버가 동시에 소유하거나 아무도 소유하지 않는 상태를 막기 위해 전환 ID와 복구 가능한 단계를 둔다.

### [9.5 데이터 분산과 기능적 분산](https://softhamzzi.github.io/gameserver/game_server_9_5/)

데이터 분산은 같은 코드가 서로 다른 사용자·방·지역 데이터를 담당하게 하는 수평 분할이다. 기능적 분산은 로그인, 채팅, 길드, 경매장처럼 서로 다른 책임을 별도 서비스로 나누는 수직 분할이다. 데이터 분산은 반복 가능한 처리량 확장에 유리하고, 기능 분산은 독립 배포와 자원 특화에 유리하다.

어느 방식이든 경계를 넘는 작업은 네트워크 실패와 부분 성공을 가진다. 자주 함께 읽고 바뀌는 데이터를 다른 서비스로 나누면 원격 호출이 폭증하고 일관성 유지가 어려워진다. 데이터베이스도 행 기준 샤딩과 테이블·도메인 기준 분리를 같은 관점으로 볼 수 있다. 경계는 조직 편의보다 데이터 응집도와 요청 패턴을 우선한다.

### [9.6 로직 처리의 분산 방식](https://softhamzzi.github.io/gameserver/game_server_9_6/)

동기식 명령 방식은 소유 서버에 작업을 요청하고 결과를 기다려 흐름이 명확하지만 상대 지연과 장애가 호출자를 막는다. 동기식 데이터 변경은 필요한 상태를 원격에서 읽거나 쓰며, 여러 왕복과 경쟁이 생길 수 있다. 타임아웃 뒤 실제 실행 여부가 불명확하므로 요청 ID와 상태 조회가 필요하다.

비동기 방식은 큐나 메시지로 일을 전달해 호출 경로를 분리하고 폭주를 완충하지만 완료 시점과 실패 통지가 늦어진다. 적어도 한 번 전달에서는 중복 처리를, 많아야 한 번 전달에서는 손실 가능성을 다룬다. 데이터를 복제해 로컬에서 처리하면 읽기는 빠르지만 복제 지연과 충돌이 생긴다. 기능마다 즉시 정확한 답이 필요한지, 잠시 오래된 값이 허용되는지로 방식을 선택한다.

### [9.7 데이터 응집도](https://softhamzzi.github.io/gameserver/game_server_9_7/)

응집도는 함께 사용되고 함께 바뀌는 데이터가 얼마나 가까이 모여 있는지를 뜻한다. 같은 전투 안의 플레이어와 몬스터, 충돌 지형은 상호작용 빈도가 높으므로 같은 소유 서버에 둘수록 원격 호출이 줄어든다. 반면 계정 프로필과 실시간 위치처럼 결합이 약한 데이터는 별도 기능으로 나누기 쉽다.

극단적으로 객체 하나씩 다른 서버에 두면 단순 이동조차 여러 네트워크 왕복과 잠금 조정이 필요하다. 분산 후보를 평가할 때 호출 횟수, 전달 데이터량, 함께 트랜잭션해야 하는 불변식, 장애가 전파되는 방향을 그린다. 응집도가 높은 덩어리는 유지하고 입력과 출력 경계가 명확한 계산이나 독립 수명 기능부터 분리한다.

### [9.8 기능적 분산 처리](https://softhamzzi.github.io/gameserver/game_server_9_8/)

사용자나 방 기준으로 더 나누기 어려운 기능도 특정 계산이나 데이터 도메인을 별도 서비스로 옮길 수 있다. 경매장은 목록 검색, 입찰, 정산이라는 독립 규칙과 저장소를 가지고 있어 월드 서버와 분리할 후보가 된다. 월드 서버는 경매장 내부 테이블을 직접 수정하지 않고 정의된 명령과 결과를 사용한다.

분리하면 팀과 배포, 자원 확장이 독립적이지만 서비스 호출 실패가 사용자 흐름에 추가된다. 입찰 성공 후 재화 차감 실패처럼 여러 서비스 변경이 걸린 작업에는 예약, 상태 기계, 보상 작업이 필요하다. 분산 트랜잭션을 피하려면 한 서비스가 중요 불변식을 소유하도록 경계를 다시 조정하는 방법도 검토한다.

### [9.9 분산 처리를 엄선해야 하는 이유](https://softhamzzi.github.io/gameserver/game_server_9_9/)

분산은 프로세스 내부 호출을 지연과 실패가 있는 네트워크 호출로 바꾸고, 하나의 상태를 여러 관점에서 보게 만든다. 배포 버전 호환, 서비스 발견, 타임아웃, 재시도, 중복, 관측, 보안 인증까지 새 책임이 생긴다. 작은 기능을 많이 나눈 구조는 개발 환경과 장애 재현도 어려워진다.

분리 전에는 실제 병목과 목표 확장량, 독립 장애의 이익을 수치로 제시한다. 모듈화된 단일 프로세스와 비동기 작업 큐로도 해결되는지 먼저 확인한다. 분산이 필요하다면 한 경계를 작게 도입하고 부하·장애 시험으로 효과를 검증한다. 되돌릴 수 있는 인터페이스와 데이터 마이그레이션 경로를 남겨야 한다.

### [9.10 분산 처리 전략](https://softhamzzi.github.io/gameserver/game_server_9_10/)

전략의 출발점은 측정 가능한 요구다. 최대 동시 접속, 지역, 지연 목표, 허용 중단 시간과 데이터 손실을 정하고 단일 노드 한계를 측정한다. 다음으로 상태 소유권과 응집도를 기준으로 방·월드·사용자 데이터 분산 또는 기능 분산을 선택한다.

모든 원격 요청에는 시간 제한을 두고 무제한 재시도를 피한다. 재시도 가능한 명령은 멱등 키를 가지며, 연쇄 장애를 막기 위해 회로 차단, 격리된 큐, 부하 차단을 적용할 수 있다. 로그와 지표에는 서비스·요청·사용자 흐름을 잇는 추적 ID를 넣는다. 단계적 전환, 이중 쓰기 검증, 되돌리기와 데이터 정합성 확인 절차를 배포 계획에 포함한다.

### [9.11 분산 서버의 또 다른 장점](https://softhamzzi.github.io/gameserver/game_server_9_11/)

분산은 처리량 외에도 장애 격리와 독립 배포, 서로 다른 자원 특성에 맞춘 확장을 가능하게 한다. 채팅 장애가 전투 진행을 중단시키지 않거나 경로 탐색 서버만 CPU 중심 장비로 늘리는 식이다. 지역별 배치로 사용자의 네트워크 지연을 낮추고 규제상 데이터 위치를 분리할 수도 있다.

하지만 분리했다는 사실만으로 격리가 생기지는 않는다. 공용 DB, 메시지 브로커, 인증 서비스가 모두의 단일 장애 지점이면 실패가 그대로 전파된다. 호출자가 타임아웃 없이 기다리거나 자동 재시도로 다운된 서비스를 압박해도 격리가 무너진다. 의존성별 실패 모드와 대체 동작을 시험해야 이점이 현실이 된다.

### [9.12 고가용성](https://softhamzzi.github.io/gameserver/game_server_9_12/)

액티브-패시브는 한 인스턴스가 처리하고 대기 인스턴스가 상태를 따라가다 장애 시 승계한다. 구조가 비교적 단순하지만 장애 감지와 승계 시간, 최신 상태 전달이 중요하다. 액티브-액티브는 여러 인스턴스가 동시에 처리해 자원을 활용하지만 동일 사용자 요청의 라우팅과 동시 쓰기 충돌을 해결해야 한다.

메모리 상태 서버를 이중화할 때 복제 지연 때문에 승계 노드의 데이터가 오래됐을 수 있다. 세션 상태를 외부 저장소에 두거나 이벤트 로그로 재구성할 수 있지만 외부 저장소 자체의 가용성이 새 요구가 된다. 잘못된 장애 감지로 두 주 노드가 생기는 스플릿 브레인을 막기 위해 리스·쿼럼·펜싱 토큰을 사용한다. 장애 전환뿐 아니라 원래 노드 복귀 절차도 연습한다.

### [9.13 데이터베이스의 분산](https://softhamzzi.github.io/gameserver/game_server_9_13/)

수평 파티셔닝은 행을 사용자 ID나 지역 같은 키로 나누고, 수직 파티셔닝은 테이블이나 열·기능을 다른 DB로 나눈다. 수평 분할은 같은 형태의 부하를 여러 노드로 나누지만 샤드 간 거래와 재분배가 어렵다. 수직 분할은 도메인 경계를 명확히 할 수 있지만 서로 자주 조인하는 데이터에는 원격 통신을 만든다.

복제는 가용성과 읽기 확장에 사용되며 분할과 목적이 다르다. 비동기 복제본에서 읽으면 방금 쓴 값이 보이지 않을 수 있어 읽기 일관성 정책이 필요하다. 분할 키, 라우팅 메타데이터, 백업, 복원과 장애 전환을 함께 설계한다. 특정 샤드만 복구하거나 전체 시점 일관 백업을 만드는 방법도 실제로 시험해야 한다.

## 코드와 그림으로 확인하기

### 수직 확장과 수평 확장

```text
수직 확장(Scale up)
┌──────────────┐       ┌────────────────────┐
│ 4 CPU / 16GB │  ──>  │ 16 CPU / 64GB      │
└──────────────┘       └────────────────────┘

수평 확장(Scale out)
                         ┌──────────────┐
클라이언트 ── 라우터 ────┼─ 서버 A      │
                         ├─ 서버 B      │
                         └─ 서버 C      │
```

수평 확장에서는 “어느 서버가 이 사용자의 상태를 소유하는가”가 추가된다. 무작위 분배가 가능한 무상태 요청과 달리 월드 요청은 소유 서버로 라우팅해야 한다.

### 데이터 분산과 기능 분산

```text
데이터 분산
  월드 서버 A: 방 1~100       월드 서버 B: 방 101~200
  같은 기능, 서로 다른 상태

기능 분산
  로그인 서비스 ── 채팅 서비스 ── 경매장 서비스 ── 월드 서비스
  서로 다른 책임과 데이터 소유권
```

한 플레이어의 전투 상태를 여러 기능 서비스가 각각 수정하게 만들면 일관성을 유지하기 어렵다. 경계를 정할 때 호출 빈도와 함께 바뀌는 데이터의 응집도를 먼저 본다.

### 동기·비동기·복제 기반 처리

```text
동기 호출:       A ── 요청 ──> B ── 실행 ──> 응답 ──> A가 계속 진행

비동기 메시지:   A ── 큐에 기록 ──> 즉시 계속 진행
                              └─> B가 나중에 처리 ──> 완료 이벤트

복제 기반 읽기:  소유 서버 ── 변경 로그 ──> 읽기 복제본
                                      └─ 로컬에서 빠르게 조회
```

동기 방식은 결과를 즉시 알 수 있지만 지연과 장애가 호출 경로로 전파된다. 비동기 방식은 결합을 줄이는 대신 중복·완료 확인·보상 처리가 필요하다. 복제본은 빠르지만 최신 상태가 아닐 수 있다.

### 멱등한 명령 처리

```cpp
CommandResult HandlePurchase(const PurchaseCommand& command) {
    if (auto previous = transactionStore.Find(command.transactionId)) {
        return previous->result;
    }

    return transactionStore.RunAtomically([&] {
        auto result = ApplyPurchase(command.playerId, command.itemId);
        transactionStore.Save(command.transactionId, result);
        return result;
    });
}
```

호출자가 타임아웃 후 같은 거래 ID로 재시도하면 기존 결과를 돌려준다. “정확히 한 번 전송”을 기대하기보다 중복 도착해도 효과가 한 번만 반영되도록 만든다.

### 액티브-패시브와 액티브-액티브

```text
액티브-패시브
요청 ──> Active ── 상태 복제 ──> Standby
            X 장애                 │
                                   └─ 승격 후 요청 처리

액티브-액티브
               ┌─> Active A ─┐
요청 ── 라우터 ─┤              ├─ 공유 또는 분할된 상태
               └─> Active B ─┘
```

액티브-패시브는 승격 시점의 데이터 손실과 복구 시간을, 액티브-액티브는 동시 쓰기와 라우팅 일관성을 해결해야 한다. 두 노드가 동시에 주 노드라고 판단하지 못하도록 리스나 펜싱 토큰을 적용한다.

### 데이터베이스 분산

```text
수평 파티셔닝: 사용자 1~N/2 → 샤드 A, 사용자 N/2+1~N → 샤드 B
수직 파티셔닝: 계정 테이블 → 계정 DB, 아이템 테이블 → 아이템 DB
복제:          Primary의 변경 → Replica 1, Replica 2
```

파티셔닝은 데이터와 쓰기 부하를 나누고 복제는 가용성과 읽기 확장에 사용한다. 목적이 다르므로 둘을 조합할 수 있으며, 샤드별 백업과 전체 시점 복구를 모두 시험해야 한다.

## 공부할 내용

1. 가상의 게임 서버에 부하를 주고 CPU, DB, 네트워크 중 실제 병목을 찾는 절차를 작성한다.
2. 로그인, 월드, 채팅, 경매장 상태의 응집도를 비교해 분산 경계를 제안한다.
3. 동기 호출을 비동기 메시지로 바꿀 때 성공 응답과 오류 처리가 어떻게 달라지는지 그린다.
4. 주요 컴포넌트마다 단일 장애 지점과 장애 전환 시간을 표로 만든다.
